# 【分红对账】：拿东财补新浪的漏（2026-09-18 设计）

## 1. 为什么要做

2026-09-18 拿东财 `RPT_SHAREBONUS_DET` 全量（56,191 条「已实施+有除权日」）
跟库里新浪的 59,081 条对了一遍：

| | |
|---|---|
| 两边都有 | 55,100 条 |
| **东财有、库里没有** | **1,050 条 / 237 只**（已剔除除权日差几天的 10 条、三项全 0 的 31 条）|
| 库里有、东财没有 | 3,982 条（其中 2,516 条是退市股——东财那张表退市股全空）|

缺的 1,050 条里 **1,043 条是北交所**（231 只）。沙箱验过：新浪对 920061 / 920547 /
833171 / 430047 一律返回"暂时没有数据"——**新浪对北交所覆盖不全**。

分红是复权因子的输入，**缺一条除权记录，那只票的复权序列整段错、而且不报错**。
这类错误没有任何现成的体检能发现，只能靠跟另一个源对账。

### 但影响面要说准

按"这条除权日有没有落在我们 `day_adj` 的覆盖区间内"再筛：

```
真缺 1,050 条 / 237 只
  其中落在 day_adj 区间内（现在就算错的）    7 条 / 6 只
     1991/1992/1993/1994/2001/2002/2006 各 1 条
     含送转 3 条：000001 1991-05-02 送4、000001 1992-03-23 送5、000504 1993-06-14 送3
  北交所那 1,043 条全部落在其 K 线起点之前   ← 北交所日K只到 2020-07（精选层），
     缺的是它们 2012-2019 在新三板时期的分红，所以当前回测一根K线都没算错
```

⇒ **现在补的收益很小（7 条），但一旦要补北交所更早的历史K线，这 1,043 条就是前提**。
而且这次对账本身值得做成常设——它是这类静默错误唯一的探测手段。

## 2. 三件事合成一件

用户 2026-09-18 定的三件事，其实是同一个能力的三层：

| 要的 | 落在哪 |
|---|---|
| ① 补那 7 条 | 对账任务跑一次就补上了 |
| ② 北交所 1,043 条 | 同上，一次补完（只加不删，补早了也不碍事）|
| ③ 做成常设【分红对账】 | 就是这个任务本身 |

所以：**写一个任务，跑一次就把 ①② 做完，③ 是它的常态**。

## 3. 设计

### 3.1 新任务【分红对账】`DividendReconcileTask`

```
拉东财全量（按年切片 1990-今年，约 120 个请求、3 分钟）
  → 跟库里 Dividend 按 (code, ex_date) 对齐，只比 progress='实施' 且有除权日的
  → 三类差异各自计数
  → 「东财有、库里没有」的**直接补进库**
  → 报告：补了多少、其中多少落在 day_adj 区间内（这部分要提醒重算回测序列）
```

`FetchActionId.FetchDividendReconcile`，季度频率，`Sources: [EmDataCenter]`。

### 3.2 ⚠ 写入必须按 `ex_date` 去重，不能按主键

`Dividend` 的主键是 `(code, announce_date)`，而**两边的"公告日"语义不同**：
新浪那列是页面上的"公告日期"，东财给的是 `PLAN_NOTICE_DATE`（预案公告日）。
直接按主键插，同一个方案会变成两行——库里凭空多出一次除权，复权序列直接错，
比原来缺一条还糟。

所以：**判重用 `(code, ex_date)`**，库里该票已有相同除权日的就跳过；
只有除权日在库里找不到（且 ±7 天内也没有）的才插。
`announce_date` 取 `PLAN_NOTICE_DATE`，没有就退回除权日。

### 3.3 Dividend 表加一列 `source`

`source TEXT`（'sina' / 'eastmoney'），老行为 NULL＝sina。三个用处：
① 补进去的行可追溯、可单独回滚；② 下次对账知道哪些是自己补的；
③ 出问题时能一眼看出"这条是谁给的"。

⚠ `ReplaceByCode`（新浪那条路）会**整只删旧写新**，会把补进去的东财行一起删掉。
这是对的——新浪那次如果真给出了这条，就该以新浪为准；如果仍然没有，下次对账再补回来。
对账是幂等的，不怕被删。

### 3.4 只补、不删、不改

东财有而库里没有 → 补。
库里有而东财没有 → **什么都不做**（3,982 条里 2,516 条是退市股，东财那张表根本没有；
其余多是 2025/2026 的新记录，东财滞后）。两边互补，谁也不能当谁的权威。
两边都有但金额不一致 → 只报告，不动数据（口径差异比数据错更可能）。

### 3.5 补完要重算

补进去的行带新的 `fetched_at`，【重算回测序列】本来就按"分红记录有更新"挑票，
所以补完跑一次那一项即可，不用特殊处理。任务结束时提示一句。

### 3.6 配股不在本期

东财的配股在 `RPT_F10_DIVIDEND_ALLOTMENT`，比例只在 `EVENT_EXPLAIN` 文本里
（"每10股配2.73股"）要正则解析，而新浪那边是结构化列。本期只对账分红。

## 4. 验收

1. 单测：`(code, ex_date)` 判重（含 ±7 天容差）、announce_date 回退、只加不删。
2. 离线整链：假的东财返回 + 真 SQLite，验证"库里已有的不重复插""缺的补上"
   "补完再跑一次不会再插"。
3. 实机：Debug 实例跑一次（会真发约 120 个东财请求），看报告数字跟这次对账对得上。
4. 正式实例跑一次，预期：补 1,050 条（其中 7 条落在 day_adj 区间内），然后重算回测序列。

### 5.2 写的时候踩出来的一个真 bug

判重原本是**整批** `Where(IsMissing)` 过滤，再把补上的登记进"库里已有"。
东财同一年里可能给出两条除权日只差一两天的记录（首次对账实测 10 条属于这种），
整批过滤时它们都还没进 `_mine`，于是**双双被判成"缺"**——补进去等于自己造了一次重复除权，
比原来缺一条还糟。测试 `同一年里除权日只差一两天的两条_只补一条` 抓到了，
已改成**逐条判、判完立刻登记**。

这条跟 §3.2「判重按除权日不按主键」是同一类错误的两个面：
一个是跟库里已有的撞、一个是跟同批内的撞，都会让库里凭空多出一次除权。

### 5.3 10 条测试覆盖什么

| 测试 | 守住的东西 |
|---|---|
| 东财有库里没有的就补进来 | 基本路径 + `source='eastmoney'` 可追溯 |
| 除权日库里已有就不补_哪怕公告日对不上 | §3.2 的铁律：**不能按主键判重** |
| 除权日差几天的算同一条 | ±7 天容差（实测两边记法有一两天出入） |
| 库里有东财没有的一律不动 | 只加不删——退市股在东财那边全是空的 |
| 跑第二次不会重复补 | 幂等 |
| 同一年里除权日只差一两天的两条_只补一条 | §5.2 那个 bug 的回归 |
| 一条都不缺时报无事可做 | 空转时不该报"补了 0 条" |
| 补进来的行进得了股息率口径 | 补的目的是让复权和股息率算对，所以必须被现有读取口径认出来 |
| 公告日撞了主键_改用除权日插进去 | §5.4.1 那个静默漏补的回归 |

### 5.4 实机验证（2026-09-18 14:24~15:05，隔离 Debug 实例）

#### 5.4.1 实机才暴露出来的第二个 bug：139 条被静默吞掉

第一轮日志报"补上 51,435 条"，库里却只多了 **51,296** 行——差 139 条被
`INSERT OR IGNORE` 无声吃掉。第二轮又报"补上 139 条"，库里**一行没多**。
也就是这 139 条会每轮被判成缺、每轮被吞、每轮报一次假的成功数，**永远收敛不了**。

根因：东财会给出"两条不同除权日、**预案公告日相同**"的记录。判重按除权日（§3.2）正确放行，
插入时主键 `(code, announce_date)` 撞上，`OR IGNORE` 直接丢弃。

修法两层：
1. `InsertMissing` 撞主键时**改用除权日当公告日重试一次**——除权日在库里本来就不存在
   （判重刚验过），撞第二次的概率极低；
2. 任务层记**真正插进去的行数**，跟"判成缺的条数"比，差额 > 0 就报
   `⚠ 另有 N 条判成缺口却没能写进去`。要么补上、要么吭声，不再有"日志报补了 N 条、库里一行没多"。

修完重跑：`补上 139 条` 且库里 `51,296 → 51,435`（+139，分毫不差），无 ⚠；再跑一轮
`库里一条都不缺`。回归测试两条：`公告日撞了主键_改用除权日插进去`、
`撞主键补进来的那条_下一轮不会再被判成缺`。

⚠ **这个 bug 离线测试测不出来**：8 条测试全绿、单元测试也全绿，因为假数据里压根没有
"同一预案公告日对应两个除权日"这种只有真源才有的形状。这正是
`feedback_verify_by_running_app` 那条的意义——测试测的是想得到的情况，实机跑出来的是想不到的。

#### 5.4.2 两条操作教训

· **`dotnet test` 不构建 Fetcher.exe**（它只构建测试项目和它引用的 Data/Scheduling/Tasks）。
  改完代码要实机验证必须单独 `dotnet build StockPlatform.Fetcher.csproj`，
  否则拷过去的还是旧 exe——白跑了一轮才发现。
· **等日志的循环必须有上限**：程序一重启 `fetch.log` 就清空归档，
  靠"出现第 N 次"计数的 `until` 循环会永远空转。
