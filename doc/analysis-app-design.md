# 分析程序 — 设计文档

状态：设计阶段，尚未开始实现。与 [数据平台设计](data-platform-design.md) 是配套文档，本文档只覆盖"分析程序"这一独立程序。

## 1. 定位

分析程序是三个独立程序中的第三个（另外两个是数据获取程序、以及网盘）：

```
数据获取程序 ──▶ （手动拷贝） ──▶ 分析程序（本文档）
```

- 分析程序**自己不抓取数据**，只负责：① 读取本地数据库、② 基于本地数据做分析、③ 展示结果和选择依据
- **状态变更记录（2026-07-07）**：曾经有一个独立的 `StockAnalyzer.UI`（实时盯盘几只自选股的小工具，配套 `StockAnalyzer.Logic`/`StockAnalyzer.Data`）。它原本用来给自选股打分的"7指标"分析逻辑，先被移植成本程序的第二种分析方法（见3.2节"金叉法"），确认功能已完全覆盖之后，`StockAnalyzer.UI`/`StockAnalyzer.Logic`/`StockAnalyzer.Data` 三个项目连同 `StockAnalyzer.sln` 里的引用一起被删除了——不再是"两个程序并存"，本仓库现在只有本程序一个分析入口，通过 Tab 切换七种分析方法，外加"查询""自选股"两个非分析方法的 Tab（见第5节）。**界面 Tab 顺序（本文档 3.2 各方法小节也按这个顺序编排）**：三角收敛 / 峰哥法 / 耀哥法 / 彬哥法 / 金叉法 / 阶梯低点法 / 短线法 / 查询 / 自选股

## 2.【已变更】数据来源：不做网盘同步，改成手动拷贝本地文件

**状态变更记录（2026-07-06）**：最初设计是分析程序自己从网盘同步 master/daily 文件、在本地合并（详见 [数据平台设计 6.3/6.4节](data-platform-design.md#63-消费者每台机器的分析程序职责) 和已实现过的 `SyncOrchestrator`）。后续调研发现，网盘自动同步这条路走不通——匿名（不登录）方式无法下载真实文件内容（见 [数据平台设计 6.5.1节](data-platform-design.md#651进行中未完成分享链接自动下载的可行性调研) 的最终结论：百度网盘的下载接口刻意要求登录态，不是签名算法能绕过的），而"手动网页下载+程序再合并"的两步流程用户觉得意义不大，索性简化成**用户直接手动把数据获取程序产出的数据库文件拷贝到分析程序的本地目录**，分析程序不做任何同步/合并逻辑，只读取这一个文件。

因此原来的 `SyncOrchestrator`、`local_sync_state.json`、`NetdiskShareInfo`/网盘链接展示、`ICloudStorageClient` 在分析程序里的使用，已经全部移除（`ICloudStorageClient`/`ManualUploadPrompter` 仍然保留给数据获取程序自己用，产出 master/daily 文件供其他用途，只是分析程序不再消费它们）。

**当前实现**：
- 分析程序固定从 `{程序所在目录}\data\local\current.sqlite` 读取数据（`AnalyzerPaths.CurrentDb`）——**就是 Fetcher 写入的那个文件本身**（2026-08-21 起：两个 exe 同目录、共用 `data/local`，不再拷贝也不再从 GitHub 下载，见[数据平台设计第2节](data-platform-design.md#2-总体架构两个独立程序)的 2026-08-21 变更记录）
- 界面上显示这个路径 + 一个"打开本地数据目录"按钮
- 状态栏显示"本地数据最新到 {日期}"（直接查询本地数据库里 `Bar` 表 day 粒度的 `MAX(period_start)`，不再依赖单独的同步状态文件）
- 提供一个"刷新"按钮：Fetcher 抓完新数据之后点一下，不需要重启程序就能重新读取最新内容和状态（`SqliteBarRepository` 每次查询都重新打开连接，不持有长期连接；库跑 WAL，抓取进行中也能读）
- 不做文件校验/版本比对——用户对拷贝进去的是不是最新文件自己负责，程序只是"如实读取当前文件里有什么"

## 3. 功能二：分析

### 3.1 触发方式：先选粒度和参数，再点击开始分析

分析不是无条件跑全部粒度，而是**用户先选择本次要分析的粒度，再点击"开始分析"**：

1. 粒度选择：**时 / 日 / 周 / 月**四选一（单选，不是多选/全跑）
   - 选"**时**"时，进一步需要选择具体的分钟周期（1/5/15/30/60分钟等，与数据平台设计里 Bar 表支持的 `granularity` 对应），**由用户选**，不写死默认值
2. 参数输入：规则1（及规则2，见3.2）用到的"前N根K线"，输入框设置，**默认60**（峰哥法四段式形态需要足够的窗口才找得到，N太小基本搜不到，见3.2.2节）
3. 都选好/填好之后，点击"开始分析"按钮，才真正对本地数据执行计算——不会在粒度或参数还没选定时就自动跑

**每次分析只针对用户选定的这一个粒度**，不会同时对时/日/周/月都跑一遍，所以不存在"多个粒度结果怎么汇总成一个总体结论"的问题。

### 3.2 分析规则（已确定，八种方法，通过 Tab 切换）

程序现在提供八种独立的分析方法，用户在界面上用 Tab 切换使用哪一种，彼此互不影响、各自独立扫描/展示结果。下面各小节按方法编号编排（跟界面 Tab 顺序不一致，见下）：三角收敛 / 峰哥法 / 耀哥法 / 彬哥法 / 金叉法 / 底仓法 / 阶梯低点法 / 短线法。

**界面 Tab 顺序（2026-08-20 按用户要求重排）**，权威顺序看 `MainWindow.xaml` 里 TabItem 的排列：

| 位置 | Tab | 说明 |
|---|---|---|
| 1 | **主动仓** | 原名"我的交易"，2026-08-20 改名。走短线纪律、每天要盯的那一小撮票 |
| 2 | **短线法** | 主动仓的选股法 |
| 3 | **底仓** | 长期吃分红、基本不动的那部分持仓（见 3.2.8 末尾） |
| 4 | **底仓法** | 底仓的选股法（3.2.8） |
| 5~7 | 每日晨检 / 自选股 / 查询 | |
| 8~ | 三角收敛 / 峰哥法 / 耀哥法 / 彬哥法 / 金叉法 / 阶梯低点法 / 因子法 / 板块热度 | 保持原有相对顺序 |

排这个顺序的逻辑是**两层仓位各自紧跟自己的选股法**（主动仓←短线法、底仓←底仓法），日常动线就是前四个来回切。

⚠ "主动仓"这个 Tab 名有一处**代码逻辑依赖**：`MainWindow.TabControl_SelectionChanged` 按 `TabItem { Header: "主动仓" }` 判断要不要 Reload（切过来时要能看到刚从别的页加进交易池的票）。改 Tab 名必须同步改那里，否则功能静默失效。

#### 3.2.1 方法一：三角收敛（类名 TriangleConvergence）

对形态本身建模的一个方法，实现是 `StockPlatform.Logic.Services.TriangleConvergenceAnalysisEngine`（趋势线拟合抽成了 `TriangleConvergenceDetector`，图表和规则共用同一份，不会对不上）。**固定只用日线**。跟其它方法不同，它有三个用户可调参数（在 Tab 上直接输入）：**形态窗口 Lookback**（在最近多少天内找摆动点、拟合趋势线，默认90）、**摆动点窗口 SwingWindow**（前后各多少天都不比它高/低，才算一个摆动高/低点，默认±3）、**R²下限 MinR2**（压力线拟合优度门槛，默认0.45，可输入小数）——这个方法的判定对"多长的窗口、怎样算摆动点、拟合要多严"本身就很敏感，所以做成用户可调，不像其它方法那样基本固定阈值。**3条规则必须全部满足**（AND关系）：

1. **三角收敛形态成立（对称收敛三角形，画法贴合人工连线）**：这条规则的画线方式是照着人工在真实图上怎么画三角形来实现的（参考 000066/000977 两张手绘案例图）——**不是**对窗口内全部摆动点做一次最小二乘。步骤：在最近 Lookback 天内先定位"阶段最高峰"和"阶段最低谷"，然后 **压力线只连"峰之后"逐个走低的摆动高点**（要求向下 斜率<0，且拟合优度 R² ≥ MinR2），**支撑线只连"谷之后"逐个抬高的摆动低点**（要求向上 斜率>0），两条线向右收口、且到今天为止尚未交叉（间距始终为正）。几个关键设计：
   - **为什么分段锚定**：这类股票通常先一波大涨（低谷→高峰，highs 一路走高），再在高位做三角形整理。如果把峰之前大涨阶段那些走高的高点也拟合进压力线，压力线会被带平甚至带涨，就画不出人眼看到的下降压力线了。所以压力线只取"峰之后"的高点、支撑线只取"谷之后"的低点。
   - **突破场景的锚点**：如果最高峰太靠近末尾（价格已经突破、峰后凑不够点），压力线改锚在"突破前"最高的摆动高点上，连接那之前的下降高点——这条线正是价格当前正在向上突破的那条（`TryFind` 里的 breakout fallback）。
   - **R² 只卡压力线**：那条干净下行的压力线是形态的决定性特征；支撑线只是价格下沿的包络，真实行情里常被中途回踩的低点带得拟合很松（R² 可能只有 0.1~0.2），强行要求支撑线也 R² 达标反而会把人一眼能看出的三角形筛掉，所以支撑线只要求"向上"、不卡 R²。
   - **窗口要够长**：因为要一直回溯到那波大涨起点的低谷，窗口太短就回溯不到真正的低点、支撑线会算成向下，形态不成立。两个案例的低谷距今都在 70~85 个交易日，所以默认 Lookback 给到 90。
2. **当前价格触及支撑线或突破压力线**：最新收盘价超出压力线当前位置 ≥1.5% 视为突破；贴近支撑线当前位置（偏离 ≤2%）视为触线企稳。二者满足其一即可。
3. **MACD配合确认**：触支撑线时要求 DIF 上穿 DEA 或 MACD 柱由缩短转为放大（支撑企稳）；破压力线时要求 MACD 柱转正或 DIF 上穿 DEA（突破确认）。

**关于结果数量与排序**：三角收敛是形态匹配，命中的不止一只。改成上面"分段锚定 + 对称三角形（压力向下+支撑向上）+ 未交叉"的画法之后，全市场入选数已经从早期宽口径的几百只降到几十只（默认参数下约 40~50 只），且**按"收敛质量"评分从高到低排序**，用户重点看排在前面的即可：评分（`StockScreenResult.SortScore`，0~100）= 一半看两线间距收窄的程度（收窄越多越好）+ 一半看价格有多少比例的时间被夹在两条线之间（越贴合三角形定义越好），只用于排序不参与是否入选的判定。想要更精可调高 R²下限。结果列表只显示3条全部满足的股票；历史数据不足或摆动点不够（凑不出趋势线）而无法计算的会被跳过，数量在分析完成后的日志里汇总。

#### 3.2.2 方法二：峰哥法（类名/代码注释仍用 Foundation）

**【2026-07-10 规则整体替换】** 旧版是"低位平台→高位平台→破位新低→再突破 + BOLL中线上 + MACD零轴上"的四段式形态（`FoundationBreakoutDetector`，已随本次改动删除）。按用户要求换成一个更直接的**两步筛选：近期涨停 + 涨停后持续放量**。**固定用日线**（涨停本身是日线概念，不再跟随3.1的粒度选择），**2条规则全部满足**（AND）：

1. **近 N 个交易日内出现过涨停**：最近 N 个交易日内（含今天）至少有一次**收盘涨停**（复用 `LimitUpClassifier`：主板±10%/双创±20%/北交所±30%/ST±5%，带0.3%容差）。取窗口内**最近一次**涨停日记为 L。**N 是界面可调参数（范围约1~15，默认15）**——用原来"前N根K线"那个输入框改的。
2. **涨停后持续放量**：以 L 为界，**L 到今天的平均成交量 ≥ 涨停前5日均量 × k**（k 为界面可调的"放量倍数"，默认1.5），**且 L 之后没有任何一天缩回到涨停前5日均量以下**（体现"持续放量"，不是放一天就歇）。若涨停就发生在今天（L=今天），退化为"涨停当天本身放量 ≥ 前5日均量 × k"——这是与用户确认的"甲"口径。

**条件详情图专门重做**（`FoundationChartBuilder`/`FoundationDetailViewModel`，复用 `DetailWindow`）：2面板——主图K线+MA5/10/20，把窗口内每个涨停日打红三角、最近一次涨停 L 标竖线；成交量面板画量柱+5日均量线，并标出 L 和"涨停前5日均量"基准线,正好对上两条规则。默认参数(N=15/k=1.5)全市场约命中 200~300 只(涨停+放量本来就常见),用户可调 N/k 收紧。

#### 3.2.3 方法三：耀哥法（原名触底回升法，类名仍用 BottomRebound）

跟金叉法一样**固定只用日线**（20日底部窗口、MA20都是按自然交易日设计的），实现是 `StockPlatform.Logic.Services.BottomReboundAnalysisEngine`（底部/连续上涨的判定单独抽成了 `BottomReboundPatternDetector`，图表和规则共用同一份，不会对不上）。**5条规则必须全部满足**（AND关系）：

1. **日线MACD**：MACD用默认参数(12,26,9)；DIF（快线）≥ -阈值（阈值是用户可调的"DIF阈值"，默认0——即DIF必须≥0；调大后允许DIF略低于0轴也算"接近0轴"）
2. **均线条件**：当前交易日收盘价同时高于 MA5、MA10、MA20
3. **底部上升形态**：
   - 以最近20个交易日（含今天）为观察窗口
   - 窗口内最低价（Low）所在的那一天，视为本轮底部
   - 该底部之后到今天之间（不要求紧贴底部），出现过至少一段连续 ≥3 天"收盘价一天比一天高"
   - 且当前股价已重新站上 MA5、MA10、MA20（跟规则2是同一个判定，这里是这个形态自己的定义，重复判一次）
4. **最近三天资金净流入**：最近3个交易日（含今天）的资金净流入都必须为正
5. **20天内MACD金叉**：以最近20个交易日（含今天）为观察窗口，窗口内DIF（快线）只要出现过至少一次由下向上穿过DEA（慢线），即算满足（不要求金叉发生在窗口末尾）

"DIF阈值"是这个方法唯一的用户可调参数，不像峰哥法"前N根K线"那样牵动好几条规则——20日观察窗口、最少连续上涨天数(3天)、资金净流入的3天窗口、MACD金叉的20天窗口都是固定常量（分别在 `BottomReboundPatternDetector`/`BottomReboundAnalysisEngine` 里）。

**关于第4条资金净流入**：这是全新的数据类别，跟已有的Bar（OHLCV）、FundamentalMetric（市值等快照）都不一样——单独建了 `NetInflow` 表（`Code, PeriodStart, MainNetInflow`，主键 `code+period_start`，见 doc/data-platform-design.md）。数据源**默认用新浪财经**（`SinaNetInflowFetcher`，取的是 `netamount` 字段——全部单量级净流入之和，不是"只算大单+超大单"的严格"主力净流入"，因为新浪这个多日历史接口没有单独暴露大单的历史明细，凑不出那个更窄口径的定义；`netamount`是对"资金净流入"更直白的理解）；东方财富的等价实现（`EastMoneyNetInflowFetcher`，字段 `f52`=主力净流入净额，严格等于大单+超大单）也保留在代码里但**默认没有被使用**——因为东方财富在用户实际使用环境里基本连不上，详见 doc/data-platform-design.md 3.7节的状态变更记录。`FetchOrchestrator` 在"拉取全部"/"拉取当天"时都会跑一遍（跟流通市值一样不受用户选的K线数据源影响）。跟第4节彬哥法的流通市值同样的处理方式：数据不存在时这条规则判不满足并显示"缺少主力净流入数据"，不会让整只股票报错跳过——如果本地数据库是升级前拉取的，需要重新执行一次拉取才会有数据。

#### 3.2.4 方法四：彬哥法（原名中盘起爆法，类名仍用 MidCapPullback）

七种方法里条件最多、涉及数据面最广的一个，实现是 `StockPlatform.Logic.Services.MidCapPullbackAnalysisEngine`。**12条规则必须全部满足**（AND关系，2026-07-17 从10条增到12条，见规则11、12），没有用户可调参数：

1. 上市板块不包含科创板（`MarketClassifier.Classify(code) != ShanghaiStar`，含688和689两种前缀）
2. 股票市场类型不包含北交所（`MarketClassifier.Classify(code) != Beijing`）
3. 股票简称不包含ST、*ST（`StockMeta.name` 直接做 `Contains("ST")` 判断，`*ST` 天然包含"ST"子串）
4. 最新交易日流通市值（不含限售股）大于80亿元且小于300亿元
5. 最近15个交易日（含当前交易日）内，涨停次数大于1次（按收盘涨停统计）——涨跌停幅度按板块+ST状态区分：主板10%/创业板科创板20%/北交所30%/ST股5%（见 `LimitUpClassifier`），留0.3个百分点容差应对价格最小变动单位导致的四舍五入误差
6. 月线MACD采用默认参数(12,26,9)，MACD柱值大于0
7. 周线MACD采用默认参数(12,26,9)，MACD柱值大于0
8. 当前交易日开盘价低于MA15
9. 当前交易日收盘价高于MA15
10. 前一交易日收盘价低于前一交易日MA15
11. **最新报告期股东户数环比上一报告期下降**（2026-07-17 新增，用户要求）——筹码集中的方向。读 `IShareholderRepository.GetCountSeries`（按报告期升序），硬条件=`series[^1].HolderNum < series[^2].HolderNum`。用户还提"最好接近近两年最低户数"——按"最好=软"处理：**只在依据文字里显示"距近2年最低高X%"供参考，不作硬门槛**。
12. **最新交易日融资余额较上一交易日增长**（2026-07-17 新增，用户要求）——资金加杠杆流入的方向。读 `IMarginRepository.GetBalanceSeries`（`MarginDetail` 表，按交易日升序），硬条件=`series[^1].MarginBalance > series[^2].MarginBalance`。融资融券每日数据来自交易所官方（上交所+深交所，见 doc/data-platform-design.md），日常已并入"拉取全部/当天"、历史用"回补融资余额"补。

**关于第4条流通市值**：`FundamentalMetric` 表（`Code, MetricKey, AsOfDate, Value, Source, FetchedAt` 的通用key-value结构）早就建好了，一开始没有任何数据获取程序往里写过东西——**这个状态在 2026-07-09 就结束了**，`MetricKeys.CirculatingMarketCap`（流通市值，单位固定是"元"）现在每次"拉取全部"/"拉取当天"都会写（`FetchOrchestrator.FetchMarketCapAsync`），不受用户选的K线数据源影响。数据源默认是 **`SinaListMarketCapFetcher`**——**整轮扫一遍新浪全市场股票列表**、用顺带返回的 `nmc` 字段（万元×10000→元），**不是逐只股票单独查询**（腾讯的 `TencentMarketCapFetcher` 和东方财富的 `EastMoneyMarketCapFetcher` 都只是保留在代码里的备用实现，目前没有任何 composition root 构造它们，详见 doc/data-platform-design.md 3.5节的状态变更记录）。

**第4条现在是真的在起筛选作用的硬条件，不再是"恒不满足的占位"**（2026-08-04 对 `publish/data/local/total.sqlite` 实测复核）：库里有 80,515 行 / 5,539 只股票 / 15 个交易日，覆盖 2026-07-09 ~ 2026-08-03。按每只票最新 as_of_date 的值分档——**1,328 只（24%）落在 (80亿, 300亿) 区间内 → 满足**，3,660 只 ≤80亿、551 只 ≥300亿 → 不满足。单位也复核过是"元"（600036 的 value ÷ 同日日线收盘 = 恒定的 20,628,944,429 股 = 招商银行A股流通股本），跟代码里 `80 * 1e8` / `300 * 1e8` 的阈值一致。**改这个区间会真的改变彬哥法的选股结果。**

**规则4跟规则1/2/3不一样，故意没有做成"数据缺失就跳过整只股票"**（像日线历史数据不足那样归为Error）：如果这样处理，市值数据缺失时会导致每一只股票都被跳过，看不出其余规则算得对不对。缺数据时的实际处理是 **`DataMissing=true`，被 `AllSatisfiedIgnoringMissingData` 把这一条整条排除**（跟第11/12条同一套机制），**不是**"当成一条普通的未满足条件判负"——两者对 `Passed` 的影响完全相反，所以一只完全没有市值数据的票依然可能 `Passed=true`。仍然缺数据的是新浪实时列表里查不到的那批（实测 5,853 只纯6位A股代码里有 314 只没有任何市值行，以退市/长期停牌为主）；如果是本地数据库还是升级前拉取的，第4条会显示"缺少流通市值数据"，重新拉取一次就能正常判定。

**关于第11/12条（股东户数、融资余额）**（2026-07-17）：这两条依赖的数据都是**需单独触发/回补**的——股东数据走"拉取股东数据"（季度级，`ShareholderCount` 表），融资余额走交易所官方接口（`MarginDetail` 表，日常并入"拉取全部/当天"、历史用"回补融资余额"）。很多时候本地还没有，所以缺数据（序列<2点）时标 `DataMissing=true`——走 `AllSatisfiedIgnoringMissingData` 被跳过、不拖垮其余条，数据同步到分析程序后自动生效。这跟第4条市值"缺数据判负"略有不同：市值缺失是"升级前旧库"临时状态，而这两类是可选/慢变数据、缺失是常态，用 DataMissing 跳过更合适。**注意同步**：`DailyIncrementExporter` 目前只带核心表（Bar/NetInflow/FundamentalMetric/公告/StockMeta），**MarginDetail/ShareholderCount 等新表不在每日增量里**，要靠"全量基线"才能同步到分析程序（若要让它们走每日增量，需扩 DailyIncrementExporter）。

#### 3.2.5 方法五：金叉法

移植自 StockAnalyzer 的7指标打分逻辑（原 `StockAnalyzer.Logic/Services/StockAnalyzerService.cs`，该项目已删除，见第5节变更记录；现在的实现是 `StockPlatform.Logic.Services.GoldenCrossAnalysisEngine`）。跟峰哥法不同：**固定只用日线**（7条里有"近20日压力位""近10日RSI"这类假设按自然交易日计算的规则，套到周/月/分钟线上语义会变，所以没有像峰哥法那样开放粒度选择），**不需要用户填"前N根K线"**（7条规则内部窗口都是各自写死的常量），判定也不是AND而是**7条里至少满足5条就算通过**：

| # | 名称 | 判定 |
|---|---|---|
| 1 | MA5 上穿 MA10 | 昨日 MA5≤MA10，今日 MA5>MA10 |
| 2 | MA10 开始拐头向上 | 今日MA10>昨日MA10，且昨日MA10≤前日MA10（由平/跌转涨） |
| 3 | MACD 金叉 | 昨日 DIF≤DEA，今日 DIF>DEA |
| 4 | KDJ 在20~50区域金叉 | 昨日 K≤D，今日 K>D，且今日K落在[20,50]区间 |
| 5 | RSI 从30附近向上突破50 | 近10日（不含今日）RSI最低值≤35，且昨日RSI<50、今日RSI≥50 |
| 6 | 成交量≥5日均量的1.5倍 | 今日成交量 ≥ 昨日5日均量 × 1.5 |
| 7 | 股价突破最近20日平台或压力位 | 今日收盘 > 前20日（不含今日）最高价 |

MACD/RSI/KDJ/MA 的具体公式见 `StockPlatform.Logic.Services.TechnicalIndicators`（KDJ(9,3,3)、RSI(14) 沿用 Wilder 平滑，跟原 StockAnalyzer.Logic 版本一致）。

**命名说明**：7条里严格意义上的"金叉"只有①③④三条（两条线交叉），②是均线拐头、⑤是RSI突破固定阈值、⑥是量能过滤、⑦是价格突破压力位，并不是每条都是"金叉"。"金叉法"这个名字是沿用用户习惯叫法（照顾①③④这几条最核心的信号），不是严格的技术定义，特此说明。

#### 3.2.6 方法六：短线法（类名 ShortTerm）

盘后、日线级别的**短线/波段入场筛选**，实现是 `StockPlatform.Logic.Services.ShortTermAnalysisEngine`。定位是"选出明天值得关注的启动票"，**适配 A股 T+1**——反正买了要过夜，分时/打板那种颗粒度性价比低、要求高，所以刻意不做，只在日线上做。**固定用日线**。前7条必须全部满足（AND，其中主力净流入/流通市值缺数据时按 `DataMissing` 跳过该条、不判整只股票失败，同耀哥法/彬哥法），第8条是过滤：

1. **均线多头启动**：收盘 > MA5 > MA10，且 MA10 拐头向上（今日MA10 > 昨日MA10）
2. **放量**：当日成交量 ≥ 前5日均量 × 放量倍数（默认1.5，可调）
3. **突破**：收盘价创近20日新高（最高价口径，跟金叉法条件7同口径）
4. **MACD动能确认**：MACD柱转正且放大，或 DIF 在0轴上方金叉
5. **主力资金净流入**：最新交易日主力净流入 > 0
6. **流通市值适中**：默认 30亿~300亿（区间上下限可调）
7. **不追高**：当日涨幅 ≤ 上限%（默认7，可调）
8. **过滤**：排除 ST/*ST、北交所

**近15日涨停次数是加分项，不作硬性入选条件**：只写进 `StockScreenResult.SortScore`，让有资金关注（近期涨停多）的票在结果里排前面（结果按它从高到低排序），不影响是否入选。放量倍数/涨幅上限/流通市值区间做成界面可调。

**条件详情图复用金叉法的详情窗口**（`GoldenCrossDetailWindow`/`GoldenCrossChartBuilder`）——短线法用到的指标（MA5/MA10、前20日最高价突破线、成交量对比5日均量、MACD）正好是那张图已经画的一个子集，且突破线用的是同一套"前20日最高价"口径，图和条件文字对得上，因此没有再单独做一套图表（这是本方法有意的例外，其它方法各自独立见 3.3 节末尾的说明）。

#### 3.2.7 方法七：阶梯低点法（类名 RisingLows，2026-07-10 新增）

用户口述形态,抓一段"**低点一级级抬高**"的上升结构里的回踩买点。实现是 `StockPlatform.Logic.Services.RisingLowsAnalysisEngine`,锚点定位抽到共享的 `RisingLowsDetector`(引擎判定和条件详情图画点用同一批锚点,避免图/规则不一致——跟三角收敛的 Detector 同一思路)。**固定用日线,9条必须全部满足(AND)**(最初8条,2026-07-13 按回测新增 C9,见下面的变更记录)。

整体轨迹(从左到右,天数=交易日,均可±5天): 起点低 → 拉升到**阶段顶** → 回落在**更高的低点金叉** → 反弹到 **P** → **回踩V**(又一个更高的低点) → 今日重新向上。核心是**三个依次抬高的低点**: 起点低 < 金叉低 < 回踩V低。

1. **阶段顶**: 金叉前约27交易日出现"金叉前60交易日内最高点"
2. **金叉**: 约14交易日前 MACD 金叉(DIF 上穿 DEA),且金叉发生在**零轴下方**(启动早期)
3. **更高的低点①**: 金叉附近最低点 略高于 其前约50交易日最低点(高出 0%~10%)
4. **反弹高点P**: 金叉后价格反弹到一个局部高点
5. **回踩V**: 自 P 回落 ≤17%,且 V 低点高于金叉低点(更高的低点②)
6. **MACD配合**: 金叉后 DIF 始终不下穿 DEA、回踩后 DIF 回升、今日 DIF/DEA 双双在零轴上方
7. **今日向上确认**: 今收 > 昨收,且今收高于回踩V底
8. **量能配合**: 回踩V日缩量(<前5日均量)。~~+ 今日放量(≥1.2×前5日均量)~~——今日放量的要求 2026-07-13 按回测数据删除，见下面的变更记录
9. **距前高留空间**: 今日收盘 ≤ 阶段顶最高价×(1−3%)，即距前面的最高点至少还有3%空间——破顶/贴顶属于追高，2026-07-13 新增，见下面的变更记录第 5 点

**阈值/天数都是拿两只样本(000977 浪潮、000066 长城)的真实数据校准出来的**: 金叉≈今天前14交易日、阶段顶≈金叉前27交易日、"略高"≤10%、回踩≤17%。用户最初口述是"约20天/略高0-1%/浅V≤1%",但按那套紧阈值这两只样本自己都会被排除——已确认取"能框住样本"的宽口径(方案A)。**条件详情图是专门做的**(`RisingLowsDetailWindow`/`RisingLowsChartBuilder`,3面板: 主图K线+MA5/10/20+把阶段顶/金叉/P/回踩V/三个抬高的低点标在图上 / MACD / 成交量),不复用其它方法的图。

**状态变更记录（2026-07-13）——按历史回测修改 C8、加入市场环境出手条件与买入纪律**

用本地数据做了一轮系统回测（86 个时间点 = 2024-02~2026-06 每月上/中/下旬各一个，全市场约 5100 只/点、43 万条观测；方法 = 把数据截断到历史时间点跑同一套引擎、无未来函数，看命中股之后 10 个交易日表现；入场按真实约束 = 信号盘后产生、次日才能买、T+1）。主要发现与对应修改：

1. **原版 8 条按"次日开盘买"衡量没有优势**（胜率 49.4%、收益中位数 0.00%）——纸面收益主要在信号日收盘→次日开盘的跳空里（平均 +1.58%），实际买不到。
2. **删掉 C8 里"今日放量≥1.2×前5日均量"**：回测显示这条是负贡献——赢家信号日量比中位 1.21、输家反而 1.39，放巨量更像追高陷阱。C8 现在只要求回踩V日缩量。
3. **加入市场环境"出手条件"**（`MarketEnvironmentCalculator`，市场级判断、不属于单只股票的 C1~C8；不满足时不拦截结果，只在界面/日志提示"今日信号仅观察"）。命中股的涨跌与大盘环境强相关：跌市月份命中几乎全军覆没，下面两个指标能把这类环境挡掉（宽度≤50% 时信号胜率 36.5%、热度≤1 时 44.2%）。
4. **买入纪律**（写在 Tab 的条件说明里，程序不自动执行）：次日开盘买；高开>3% 放弃；持有满 10 个交易日。依据：跳空>3% 的约占 15%，放弃后整体胜率 55.4%→60.1%；"等回踩(D2~D5挂信号价)再买"胜率持平但错过的两成信号恰是最强的（错过部分若直接买：胜率 81.5%/平均 +9.24%）；持有 5 日比 10 日胜率低 6~14 个百分点（收益集中在第 6~10 天兑现）。
5. **新增 C9"距前高留空间"（同日稍晚，源于用户看盘观察）**：原 8 条只约束回踩结构，不管当前价相对前高的位置，导致已突破阶段顶的股票（如 000977 在 2026-07-09 破顶后）仍持续命中——用户指出这属于追高。历史 276 笔按"信号日收盘距阶段顶最高价的位置"分桶验证：**贴顶(-3%~0)最差（胜率 50%）、破顶后 53.6%（平均收益虽正但全靠少数大牛股）、顶下 3%~15% 是最优区间（62%~70%）**，离顶太远(>15%)动能不足也变差。阈值扫描后取 **3%**（C9 = 今日收盘 ≤ 阶段顶最高价×0.97）：整体胜率 60.1%→65.1%、平均 +3.56%→+3.93%、中位 +2.01%→+2.67%，信号量保留六成，分年（72.7%/70.0%/61.1%）都稳定；m=5~8% 胜率略高但信号减半、平均下降；"近5日盘中未破顶"的附加条件无增益，未采用。2026-07-10 实况验证：当天 8 条口径命中 6 只，加 C9 后剩海德股份(-15.3%)、飞沃科技(-4.3%) 两只，与用户肉眼筛选一致。

**三个关键阈值的计算口径**（前两个在 `MarketEnvironmentCalculator` 里有唯一实现，界面 Tab 每次分析时计算并显示）：

| 阈值 | 计算方式 | 判定 |
|---|---|---|
| 市场宽度 >50% | 全市场（本地库全部股票，当天有K线且历史≥20根的）中，**收盘价 > 自身20日收盘均线(MA20，含当日)** 的股票占比 | 高于 50% 才出手 |
| 市场热度 >1.0 | **当日全市场 Σ(成交量×收盘价) ÷ 之前 20 个交易日同一合计值的平均（不含当日）**。用 量×收盘价 代理成交额，因为库里 Bar.Amount 未填(全为0) | 高于 1.0 才出手 |
| 次日跳空 ≤3% | **(次日开盘价 − 信号日收盘价) ÷ 信号日收盘价**。信号是盘后算的，这是次日早盘人工判断的纪律，程序不参与 | 高开超过 3% 放弃该信号 |

**配套验证辅助（同日）**：阶梯低点法 Tab 增加"截止日期"输入框（yyyy-MM-dd，留空=最新数据）——填了就把整个分析按"那天收盘往前"计算（引擎、市场宽度/热度、条件详情图全部截到同一天，等价回测的截断口径），供用户手工核对历史时点的命中结果。实现：`CutoffBarRepository`（Logic，包装 `IBarRepository` 截断读操作）+ `IBarRepository` 新增 `GetOverallLatestPeriodStartOnOrBefore`（截止日可能是周末/节假日，要据此回退到真正的最后交易日）。

修改后的整套规则历史表现（同一回测口径，含 C9 后 166 笔）：**胜率 65.1%、平均 +3.93%、中位 +2.67%**；对照原版信号按次日开盘买只有 49.4%/+0.55%/0.00%。**注意**：宽度 50%、热度 1.0、跳空 3%、距顶 3% 四个阈值是在同一批历史数据上选出来的，有过拟合成分，上线后需要前向跟踪验证；且相邻时间点的观察窗口部分重叠，样本不完全独立，真实胜率精度比表面数字略低。回测明细（每笔信号的 C1~C8、逐日涨跌、市场指标）当时保存在会话临时目录，未入库；回测工具的做法是用一个截断喂数据的 `IBarRepository` 包装（`FixedBarsRepository`）复用产品引擎，需要复现时照此重写即可。

#### 3.2.8 方法八：底仓法（类名 CorePosition）

**【2026-08-20 由"回调法"改造而来】** 原回调法（2026-08-03 建立）在一个引擎里同时判两类候选：底仓（高股息+低波动）和主动仓（跌到回测验证档位内）。按用户要求只保留底仓这一路，改名"底仓法"，实现 `StockPlatform.Logic.Services.CorePositionAnalysisEngine`（原 `PullbackAnalysisEngine` 已删除）。

**为什么可以整个替换掉**：主动仓选股全部交给【短线法】——那套 8 条硬条件有 89 个时点／28020 个样本的回测（3.35%／胜率66.8%），比原回调法的主动仓判定（0.96%／54.7%）强，去掉没有功能缺口。同时删掉的还有"距一年高点回撤≥10%"、两个止盈目标和止损价（底仓不用价格纪律，那三个常量挪到了 `TradeDiscipline`）、以及顶部的大盘 MA60 状态（底仓不择时，摆着只会诱导择时）。

**用户的底仓定义（2026-08-20）**：用来拿分红的、基本不动的那部分持仓；相对的是"常流通的主动仓"。这条定义解决了一个原本的矛盾——"往下分档加仓"和"-10% 止损"是互斥的，分成两层后各走各的纪律：底仓不设价格止损，退出条件是**分红中断或基本面变坏**；主动仓继续吃 ±10%。

##### ⚠ 证据等级：本方法没有回测支持

这一点必须写在最前面。本项目其它方法每个阈值背后都有一份回测表，**底仓法没有**。原因是口径不同：那些回测是"+10%止盈／-10%止损／最长持有120日"，而底仓持有期是**数年**，差一个量级。

尤其注意：原回调法那条"重基本面筛选（ROE／净利增长）是负贡献、所以只留净利+现金流"的结论**不再沿用**——它是短线口径下测出来的。持有数年的票不能是连亏公司，所以"近3年净利"从"仅提示"升级成了硬条件（第③条）。

要真正验证需要另做一轮长周期回测：用 `day_hfq`（后复权；前复权在十年尺度上会失真，见 `project_qfq_hfq`）算价差，加上 `Dividend` 表的实收分红，按持有 1/3/5 年分别统计。**这是独立的一个活，还没做。**

##### 8条硬条件（AND，全部满足才入选）

| # | 条件 | 说明 |
|---|---|---|
| ① | 净利润为正 | 最新一期财报归母净利润 > 0 |
| ② | 经营现金流为正 | 赚的是真钱 |
| ③ | 近3年归母净利：累计为正**且**最新年度为正 | ← 由"仅提示"升级为硬条件 |
| ④ | 20日均成交额 ≥ 1亿元 | 底仓不常动，但真要减仓时得出得去 |
| ⑤ | 股息率 ≥ **4.5%** | 用户 2026-08-20 定。要跟国债/定存拉开差距 |
| ⑥ | 经营现金流／净利润 ≥ 1.0 | 利润要变成真钱，这个分红才发得出来 |
| ⑦ | 日均波幅(60日) ≤ 1.5% | 底仓**没有价格止损**，低波动是为了分档加仓时拿得住 |
| ⑧ | 连续分红 ≥ **5年** | 用户 2026-08-20 定。← 新增，最关键的一条 |

**2026-08-20 去掉了原来的第⑤条"一手金额 ≤ 总资产15%"**（用户要求）。它防的是茅台那种高价股（一手13.5万，在55万本金下占24.5%，买第一笔就重仓），但 4.5% 股息率的池子里现价基本都在个位数到几十元——实测入选的 15 只里一手最贵的是青岛啤酒 5137 元，门槛却是 15 万，**它一只都没挡住过**。删掉前后入选名单完全一致，15 只一只不差。顶部那个"总资产"输入框也随之去掉（它的唯一用途就是推导这条的门槛）。

**为什么第⑨条最关键**：底仓赌的就是"未来还会不会继续分红"。只看近12个月的股息率完全分不出"连分十年的电力股"和"去年头一回分红、今年就停了"的票，后者的高股息率纯属巧合。算法上"今年还没到分红季"不算中断（A股多在4~7月实施上年度分红），只有去年和今年都没派息才判定中断——见 `DividendMetrics.ConsecutiveYears`。

**排序** = `SortScore` = **股息率×100**（越高排越前）。原来这个字段装的是"低于MA20的幅度"，对底仓没有意义。**扫描范围排除** ETF/指数/板块、ST与退市股、科创板(688)、北交所(8x/4x/92x)。

##### ⚠ 股息率的口径陷阱（2026-08-20 实测发现并修正）

`IDividendRepository.GetTrailingCashDividendPerShare()` 的滚动12个月窗口，在分红季前后会把**两个年度**的年度分红同时框进来，算出近一倍的虚高股息率。实测：

| 股票 | 滚动12个月口径 | 修正后 | 近5年均 | 实际情况 |
|---|---|---|---|---|
| 华邦健康 002004 | **10.11%** | 5.62% | 4.00% | 每年只派 0.20~0.25 元、现价 4.45 |
| 格力电器 000651 | **7.26%** | 未入选 | 4.06% | 2026 年只派 1.00 元 |

修正做法：股息率取**"滚动12个月"和"最近一个完整年度"的较小值**（`DividendMetrics.LatestYearDividend`）。取较小值而不是"哪个更准用哪个"——底仓买错的代价是拿几年，宁可漏掉也不要虚高；副作用是当年分红尚未实施完的票会被低估，这个方向的错误可以接受。两个口径都写进条件详情，差得多时用户看得见。

**这个修正把入选数从 29 只压到 15 只**，剔除的正是格力电器、中远海控、中国平安、平安银行、美的集团等滚动口径虚高的票。

**已知局限**：条件⑨只查"有没有分"，查不出"分多少"。15 只里有 2 只派息趋势为"波动"（连续分红没断但金额有过腰斩，如海澜之家 25年0.18→26年0.41、公牛集团 22年2.4→26年1.9），另有券商股（周期性盈利）入选。是否要再加一条"近5年派息不腰斩"待定——在没有回测的情况下继续叠加阈值有过拟合风险，当前按"没有证据就不加"处理，只在日志里提示。

**2026-08-20：派息趋势和近3年净利这两列改成只放结论，逐年明细改用柱状图**（用户要求）。原来这两列塞的是 `波动｜22年0.510 23年0.430 24年0.790 25年0.180 26年0.410` 和 `23年+29.52 24年+21.59 25年+21.66｜累计+72.77亿` 整串，列宽不够、扫一眼也读不出重点。现在逐年明细在每行的【条件详情】里画成柱状图（`CorePositionChartBuilder`），而且画的是**全部**历史而不是判定窗口那几年——柱子高低一眼就能看出"哪年腰斩了""是一贯分红还是最近才开始"，这正是底仓最该判断的事。

- `CorePositionCriteriaWindow`（底仓法专用）—— 上半部分两张柱状图并排，下半部分条件文字，中间可拖动分隔。

##### 新增的数据依赖

`IDividendRepository.GetAnnualCashDividendPerShare(since)`——全市场按年分组的每股现金派息（年份取**除权除息日所属年**，即钱到账那年；只算 `progress='实施'`）。批量返回是因为逐只调 `GetByCode` 是 5000+ 次查询。连续分红年数和派息趋势都靠它。

##### 配套的【底仓】页（2026-08-20 新增）

记录"用来拿分红、基本不动"的那部分持仓。

**数据存在自己的文件里**：`data\core-positions.json`（`CorePosition` + `JsonCorePositionStore`），**不是** watchlist.json 加个标记。三个理由：① 字段几乎不重叠——`WatchlistEntry` 一大半是信号来源字段（Method/Lookback/PriceAtPick/Criteria 快照），底仓不来自任何选股法；② 两个列表的标的本来就不该重叠（见下面的先进先出）；③ **最关键：混一份数据会污染晨检**——晨检那页是短线纪律（跌破MA5就卖／20天时间止损／15%回撤止损），底仓绝对不能进这套检查，共用一份 json 的话每处筛选都要多挂一个"排除底仓"条件，漏一处就会有一天早上跳出来叫你把底仓砍掉。分开文件从物理上不会漏。**本页不进晨检**（2026-08-20 用户确认）；以后若要加，只能加"分红预案变化／连续分红中断／有档位刚满一年"这三类事件提醒，不能加任何价格信号。

复用的是 `TradeLot`（底仓分档建仓，结构跟主动仓的金字塔建仓完全一样）、`TradeCostSummary`、`TradeFeeStore`、`TradeLotsWindow`（录成交窗口本来就只接 `IEnumerable<TradeLot>`，不绑定记录类型）。

**列刻意跟【主动仓】不同**——那边是止亏价、±10%、持仓盈亏；这边是：

- **建仓进度** = `已买入股数 / 计划买入股数（百分比）`，如 `2,000 / 3,200 股（62%）`。计划股数 = 目标年化股息 ÷ 每股股息。**底仓的仓位按现金流倒推，不走凯利**——凯利要有胜率和赔率两个输入，底仓压根不做胜负判断。没设目标时只显示已买股数。
- **成本股息率（yield on cost）** = 每股股息 ÷ 含费持仓均价。买得越早越便宜这个数越高，而且不随股价波动（分母是成本不是现价）。现价股息率回答"现在该不该加仓"，成本股息率回答"我这笔持仓每年实际给我多少回报"。
- **累计已收股息**：按每笔买入日分别判有没有权（用**股权登记日**：登记日收盘在册才有权，`record_date` 缺失时退回 `ex_date` 前一日）。
- **免税日**：看**最晚那笔买入**——分档建仓每档的免税时钟各自独立起算，整个底仓全部跨过一年取决于最后补的那档。
- **总回报 = 价差（含费）+ 累计已收股息**。必须加上股息：除权当天股价下调、账面浮亏自动变深，但那笔钱已经进口袋了，**只看价差会让一只拿了三年的高股息股被系统性低估**，看报表的人会误判底仓在亏钱。
- **连续分红中断标红** —— 底仓没有价格止损，分红中断就是它的退出信号。

**2026-08-20 精简了表格列**（用户逐项要求）——删掉的和为什么：

| 列 | 处理 | 原因 |
|---|---|---|
| 计划档数 | **删除**（连字段一起） | 除了当"2/4档"的分母之外没有任何作用：不参与计算、不做提醒。真正有信息量的是按股数算的百分比 |
| 持仓 | 删除 | 建仓进度的分子就是持仓股数，有没有建仓看那里就知道 |
| 目标（目标股数） | 移到【录成交】窗口 | 它把年化股息又写了一遍，跟旁边"目标年化股息"列重复 |
| 目标年化股息 | 移到【录成交】窗口 | 设目标和录买入笔数本来是同一件事的两半（"每年想收多少" ↔ "所以要买到多少股"），放一起填更顺 |
| 成本股息率 / 年化股息 | 删除（属性保留） | 没录成交时整列都是"—"。属性留着给顶部汇总的"组合成本股息率""年化股息合计"用 |

`PlannedTranches` 字段删除后，老的 `core-positions.json` 里可能还留着 `plannedTranches`，`System.Text.Json` 反序列化会自动忽略未知字段，不用迁移。

**【录成交】窗口对底仓多一行**（`TradeLotsWindow` 构造函数的 `targetAnnualDividend`/`dividendPerShare` 两个可选参数）：填目标年化股息，旁边实时显示 `→ 目标 3,200 股（每股股息 0.410 元），还差 1,200 股`。"还差多少股"挂在 `UpdateSummary` 上，增删改成交行时跟着变——底仓是分档建仓的，"还差多少"比"目标多少"更能指导下一笔买多少。主动仓打开同一个窗口时这一行整个折叠：那边的仓位走凯利，没有"目标年化股息"这个概念。

##### 红利税（财税[2015]101号 / 财税[2012]85号）

持股期限 = 取得股票之日 → **转让交割该股票之日前一日**：

| 持股期限 | 计入比例 | 实际税负 |
|---|---|---|
| ≤1个月 | 全额 | 20% |
| 1个月~1年（含1年） | 50% | 10% |
| **>1年（严格超过）** | — | **暂免** |

派息时对持股1年以内的**暂不扣缴**（股息全额到账），等转让时由中登按持股期限算出税额、券商从资金账户扣收。所以底仓一直不卖、跨过1年，这笔税不仅免掉，期间根本没被扣过。1年整仍属10%那档——最早免税卖出日 = 买入日 + 1年 + 2天（`(S-1) > D+1年` ⟹ `S ≥ D+1年+2天`），差一天就是 10% vs 0，实操再留几天更稳。实现见 `DividendMetrics.TaxRate` / `TaxFreeSellDate`。

⚠ **先进先出**（85号文第四条）：同一证券账户内先买入的视为先卖出。所以同一只票如果既有底仓又做波段，卖波段那笔会按 FIFO 认定成卖掉了最早买入的**底仓**份额，把底仓的免税时钟往后推、甚至触发倒扣税。**在软件里给成交打标记改变不了券商和中登的认定**——要真隔开只能"同一只票不两头做"，或者底仓和主动仓分开用两个证券账户。这一点在底仓法的条件详情和 ⓘ 说明里都写明了。

### 3.3 结果数据形状

八种方法共用同一套结果结构，用 `Criteria` 数量和 `Passed` 的判定方式区分（不需要为每种方法单独定义类型）：

```csharp
public class StockScreenResult
{
    public string Code { get; set; }
    public string Name { get; set; }
    public string Granularity { get; set; }   // 峰哥法跟随用户选择；其余五种（三角收敛/耀哥法/彬哥法/金叉法/短线法）固定 "day"
    public bool Passed { get; set; }          // 三角收敛/峰哥法/耀哥法/彬哥法/短线法：全部满足（缺数据条跳过）；金叉法：7条里至少5条满足
    public List<CriterionResult> Criteria { get; set; }   // 三角收敛固定3条；峰哥法固定3条；耀哥法固定5条；金叉法固定7条；彬哥法固定12条；短线法固定8条
    public double? SortScore { get; set; }    // 三角收敛=收敛质量(0~100)；短线法=近15日涨停次数；其余方法为 null。结果表按它排序
}

public class CriterionResult
{
    public string Name { get; set; }
    public bool Satisfied { get; set; }
    public string Basis { get; set; }         // 文字依据（延续已删除的 StockAnalyzer.Logic 里 ConditionResult.Basis 做法）
    // 图表依据见第4节，双击时按 Code + Granularity 单独查询K线绘制
}
```

这个形状延续了已删除的 `StockAnalyzer.Logic` 里 `StockAnalysisResult`/`ConditionResult` 的设计思路（代码本身已不在仓库里，见第1节的变更记录），`ResultRowViewModel`（界面层）按 `Criteria.Count(c => c.Satisfied)` 和 `Criteria.Count` 通用计算"满足数"，不关心具体是哪种方法产出的结果，所以七种方法能共用同一套**结果列表**（DataGrid）。但双击后的**详情图表窗口基本是各自独立的**（`TriangleConvergenceDetailWindow`/`DetailWindow`/`GoldenCrossDetailWindow`/`BottomReboundDetailWindow`/`MidCapPullbackDetailWindow`，分别用 `TriangleConvergenceChartBuilder`/`ChartBuilder`/`GoldenCrossChartBuilder`/`BottomReboundChartBuilder`/`MidCapPullbackChartBuilder` 建图）——各方法看的指标完全不同（三角收敛的压力/支撑趋势线+MACD vs BOLL vs MA5/MA10/KDJ/RSI/成交量 vs MA5/MA10/MA20 vs 日K+MA15+涨停标记/周线MACD/月线MACD三个独立面板），共用一套图表 UI 会导致图上画的指标和判断依据文字对不上（金叉法早期就踩过这个坑，图上用的是峰哥法那套BOLL+MACD，压力线还用错了价格口径），所以图表这块特意没有强行共用，只共用了不涉及具体指标的轴同步/缩放逻辑（`ChartAxisSync`）——彬哥法的三个面板粒度不同（日/周/月），彼此之间甚至不联动缩放，各自独立。**唯一的例外是短线法**：它的指标（MA5/MA10、前20日最高价突破线、成交量对比5日均量、MACD）正好是金叉法那张图已经画的一个子集，且突破线同口径，所以短线法直接复用 `GoldenCrossDetailWindow`——是"指标能对上才复用"，不违背上面这条原则。

### 3.4 结果展示 + 批量分析进度条

- 列表形式展示（DataGrid），至少包含：代码、名称、是否入选、满足的规则数、更新时间；顶部/旁边显示"当前分析粒度：{用户选的粒度}"，避免结果列表和实际用的粒度对不上
- **批量分析需要进度条**：点击"开始分析"后，如果本地股票数量较多（比如全市场级别），逐只计算需要时间，界面要展示"正在分析 第x/共y只"这样的进度提示，跟第2.2节下载数据的进度提示是同一个交互模式，避免用户以为程序卡死

## 4. 功能三：查看选择依据（图表化）+ 行情详情

### 4.1 交互

**状态变更记录（2026-07-08）**：最初是"双击结果列表某一行"触发详情窗口。改成结果表格每行右侧加两个按钮——**"条件详情"**（原来双击打开的那个，展示该股票**为什么**满足/不满足各条规则）和**"行情详情"**（新增，见4.4节，纯行情图，不涉及任何方法的判断依据）。改动原因：双击这个手势不够直观（用户容易只点一下，且双击和"想看两种不同东西"之间没有明确的手势区分），改成两个按钮之后，两种详情各自独立触发，意图更清楚。五个方法的结果表 + 自选股列表，六张表格都是这个模式。

条件详情不是现有 StockAnalyzer 那种纯文字/数值的依据（如"昨日 MA5=8.61 MA10=8.65"），而是**优先用图表表达**，让人一眼看出走势和信号点，文字数值作为图表的辅助/兜底。

### 4.2 图表内容（已确定，对应3.2节的3条规则）

双击某只股票，弹出详情窗口，展示**本次分析所用粒度**（即第3.1节用户选定的时/日/周/月）下的图表：

- **主图**：K线（蜡烛图）+ BOLL 三轨（上轨/中轨/下轨，中线对应规则2）+ 前 N 根K线的最高点水平线（对应规则1，直观看到"是否突破"）
- **副图**：MACD，画出 DIF/DEA 两条线 + 零轴参考线（对应规则3，一眼看出快慢线是否在零轴之上）
- 在"突破"发生的那根K线上打标记（比如箭头/圆点），三条规则各自满足与否也可以用颜色/图标在图上加简单的✓/✗提示，具体交互效果留到实现阶段调整

### 4.3 技术选型：OxyPlot（已确定）

选型标准是"能画K线蜡烛图"，之前列的三个候选里 **OxyPlot** 原生支持 `CandleStickSeries`，成熟稳定，确定用它。BOLL三轨、MACD/零轴都可以用 OxyPlot 的 `LineSeries`/`AreaSeries` 叠加在同一个 `PlotModel` 上（K线主图）或单独一个 `PlotModel`（MACD副图，多图联动/共享X轴的具体做法留到实现阶段处理）。

**状态变更记录（2026-07-08）——K线颜色反了，涨跌颜色对调**：四张"条件详情"图（峰哥法/耀哥法/彬哥法/金叉法）的K线蜡烛图从一开始就没有显式设置涨跌颜色，用的是 OxyPlot `CandleStickSeries` 的默认值——`IncreasingColor`（收盘>开盘，即"涨"）默认是墨绿色，`DecreasingColor`（收盘<开盘，即"跌"）默认是红色，这是美股的习惯（涨绿跌红），跟国内刚好反过来。已改成显式设置 `IncreasingColor=Red, DecreasingColor=Green`（涨红跌绿），四张图 + 新增的"行情详情"图（4.4节）全部统一。同时把K线宽度从默认的0.8倍相邻间距调窄——先调到0.6倍，反馈还是偏胖，又调到0.3倍（默认值的约三分之一），更接近常见炒股软件的样子。

**状态变更记录（2026-07-08）——悬浮信息改成表头，不再叠在图表上**：每个面板原来的OHLC/指标数值是一个悬浮在图表左上角的半透明小方框（`Border` 叠在 `PlotView` 上面，`Margin="40,4,0,0"`），实测反馈这个方框会挡住它自己正在描述的那根K线/均线（价格线靠图表上方时最明显）。改成图表自己专属的一行表头（`Grid.RowDefinitions` 拆成 Auto+*，表头行放数值文字，图表行放 `PlotView`，两者不再重叠），信息和图表完全不会互相遮挡，效果也更接近典型股票APP"上面一行数字随手指/鼠标滑动、下面是走势图"的样式。四个"条件详情"窗口（DetailWindow/GoldenCrossDetailWindow/BottomReboundDetailWindow/MidCapPullbackDetailWindow）全部改成这个布局。

**状态变更记录（2026-07-08，第二次）——图例挪进表头，日期只在最上面一个面板显示**：表头改完之后又发现两个问题——① 每个面板自己的图例（比如"MACD柱(正)/MACD柱(负)/DIF/DEA"）用的是 OxyPlot 自带的 `Legend`，画在图表内部左上角，跟刚改好的表头数值文字紧挨着甚至压线，看起来很挤；② 每个面板的表头都各自重复显示一遍"日期: xxxx-xx-xx"，五个面板的日期其实是同一天（除了彬哥法的周线/月线面板，它们粒度不同、自己独立滚动），没必要重复。两处一起改：
- 去掉所有面板的 `PlotModel.Legends`（不再用 OxyPlot 自带图例），改成表头 `Grid` 拆成两列（`*` + `Auto`）——左边放数值文字，右边放一个手写的 WPF 图例（小色块 `Rectangle` + `TextBlock`，颜色跟对应 ChartBuilder 里画那条线/柱用的颜色手动对应），两者在同一行，互不重叠
- 日期只在最上面那一个面板（K线主图）的表头里出现一次；其余副图（MACD/KDJ/RSI/成交量，以及彬哥法的周线/月线MACD）只显示自己的数值，不重复日期——反正它们的十字线跟主图联动在同一天上（彬哥法的周/月面板虽然不联动，但同样去掉了日期文字，只留数值，减少视觉噪音）
- K线数值+均线数值也从原来的2-3行合并成1行（比如金叉法主图从"日期/OHLC/MA5+MA10"三行合并成一行），配合右边一行图例，整个表头正好是一行高

**状态变更记录（2026-07-08，第三次）——图表自己的标题也挪进表头，放在最前面**：每个 `PlotModel` 原来自带一个 `Title`（比如"K线 / MA5 / MA10"、"MACD"），由 OxyPlot 画在图表内部左上角，跟表头是两个独立的东西。现在把这个标题也挪进表头，放在最左边（数值文字和图例之前）——`PlotModel` 不再设置 `Title` 属性（避免图表内部和表头重复画两遍），标题文字直接写死在对应窗口的 XAML 表头里（在4个"条件详情"窗口里是固定的；在4.4节"行情详情"窗口里，副图内容可切换，所以主图标题写死，副图标题是代码里根据当前选的指标生成的）。表头布局从"数值(*) + 图例(Auto)"两列变成"标题(Auto) + 数值(*) + 图例(Auto)"三列。

### 4.4 行情详情（新增，2026-07-08）：典型股票APP样式，跟方法/条件无关

"条件详情"回答"这个方法为什么选中了它"，是每个方法各自的图（BOLL/MACD/KDJ/RSI/成交量等指标组合因方法而异，见3.2节）。"行情详情"回答一个更简单的问题——"这只股票现在长什么样"，不依赖是哪个方法选的，五张结果/自选表格共用同一个实现（`QuoteChartBuilder`/`QuoteDetailWindow`）：

- 固定看**日线**，跟点开它的那个方法当时用的粒度无关——这是"看这只股票现在的样子"，不是复原某次分析
- 主图：K线（涨红跌绿）+ MA5/MA10/MA20，副图：成交量（同样涨红跌绿）——没有BOLL带/压力线/MACD/KDJ/RSI这些方法专属的东西
- 抬头一行：代码+名称、最新收盘价、涨跌额/涨跌幅，价格和涨跌幅按国内习惯涨红跌绿着色——不需要判断依据文字栏，所以窗口比条件详情简单（没有右侧文字面板）
- 悬浮信息同4.3节的表头做法，不叠在图表上

**状态变更记录（2026-07-08，第二次）——K线粒度可切换 + 两个副图可独立切换指标**：

- **K线粒度**：界面上加了"分时/五日/日K/周K/月K"五个按钮。**日K/周K/月K已实现**——切换后用 `IBarRepository` 按对应粒度重新查询该股票的K线（周/月线本来就是本地聚合好存着的，见 data-platform-design.md），整个主图+两个副图一起重新 Build 一遍（不做增量更新，简单可靠）。**分时/五日暂不支持**（按钮置灰+ToolTip说明）——这两个是"当天/最近5天分钟级实时行情"，这套系统目前只抓日线历史数据，没有接入任何分时/实时数据源，做这个需要先新增一条数据链路（大概率是另一个东方财富接口+专门的抓取/展示逻辑），是一个独立的、更大的功能，先不做
- **两个副图可独立切换指标**：原来固定只有"成交量"一个副图，现在有两个，默认"成交量"+"MACD"，每个副图表头左边是一个下拉框（成交量/MACD/KDJ/RSI四选一），切换后只重新算这一个副图要显示的指标，主图和另一个副图不受影响（但因为三个面板共用一套横轴联动，代码实现上还是整体重新 Build 一遍，只是用户看到的效果是"只有这个副图变了"）。抬头的"最新价/涨跌幅"固定按日线计算，不随下面图表切换的粒度变化——这是"现在的实际价格"，不是"图表这一根的价格"
- 实现上，`QuoteChartBuilder.Build` 现在接收两个 `QuoteSubIndicator`（切换用的枚举：成交量/MACD/KDJ/RSI）参数，副图的图例和悬浮信息格式化函数也是按当前选的指标动态生成的（`QuoteChartBuilder.LegendFor`/每个副图各自的 `Func<int,string>` 格式化函数），不像其它窗口那样能把图例写死在XAML里

**状态变更记录（2026-07-08，第三次）——参照真实股票APP截图重做了两处：K线图的最高/最低价标注（五个窗口都加了），行情详情窗口K线上方的整块信息区（只有这个窗口改，其它"条件详情"窗口不变）**：

- **K线最高/最低价标注（全部5个窗口的主K线图都加了）**：在当前默认可见范围内找出最高价和最低价，各画一条从图表左边界延伸到那根K线位置的虚线，末端标上具体数字——不用自己数哪根K线最高/最低，跟常见炒股软件的做法一样。新增 `ChartBuilder.AddHighLowAnnotations` 共享方法，ChartBuilder/GoldenCrossChartBuilder/BottomReboundChartBuilder/MidCapPullbackChartBuilder/QuoteChartBuilder 的主图都调用它。范围按初始默认可见的那一段算，不随后续手动缩放/平移动态重算（跟"压力线"等其它固定参考线的处理方式一致）。
- **行情详情K线上方信息区（只有这个窗口改）**：
  - 新增一行行情统计——开/最高/最低/昨收/量/额/换手（固定按日线算，跟下面图表显示的粒度无关）。"现手"（逐笔实时成交手数）没做——这套系统只有日/周/月线，没有能提供这个数字的数据源，不硬凑
  - K线图表头从"标题+悬浮文字+图例色块"改成"标题（固定显示"K线"）+ 一行带颜色的MA当前值"：默认显示最新一根K线的日期/OHLC/涨跌幅 + MA5/10/20/30当前值，每个MA值直接用它自己线的颜色染色（不再需要单独的色块图例），后面跟一个涨跌箭头（比前一根K线的MA值高就↑（红），低就↓（绿））。鼠标悬浮到图表上时，这行文字跟着变成悬浮那一天的数据——默认（无悬浮）显示最新数据，这点跟其它"条件详情"窗口默认显示"将鼠标移到图表上查看"提示语不一样，是行情详情这里专门改的
  - K线主图新增 MA30（原来只有5/10/20），颜色用深红色（`QuoteChartBuilder.Ma30Color`），凑齐参照截图里的"5/10/20/30"四条均线
  - 副图（成交量/MACD/KDJ/RSI）的表头样式不变，仍是原来的下拉框+悬浮文字+色块图例
- 用真实数据验证：行情统计7个字段跟数据库里最新一根日线的字段逐一核对一致；MA5/MA30文字的颜色分别核对是蓝色(#0000FF)和深红色(#8B0000)，跟图上线的颜色一致；5个窗口的主K线图都确认至少有2条带文字的最高/最低价参考线

**状态变更记录（2026-07-08，第四次）——K线间距再调窄一次 + 主K线图不画横纵坐标**：

- **K线宽度**：0.8（默认）→0.6→0.3→**0.5**，反馈"0.3还是间距太大"，说明0.3把候选值调过头了（宽度越窄，相邻K线之间看起来空隙越大），落在0.6（偏胖）和0.3（偏空）中间的0.5。五个窗口统一改
- **主K线图不画横纵坐标**：参照真实股票APP截图——K线图本身干干净净，不画价格刻度也不画日期刻度，价格靠最高/最低价标注（见第三次变更记录）和表头数值，日期靠表头。用 OxyPlot `Axis.IsAxisVisible = false`（只关渲染：轴线/刻度/网格线/文字全部不画，不影响 `IsPanEnabled`/`IsZoomEnabled`——拖动、滚轮缩放照常能用）。只对**主K线图**这么处理，其它面板（MACD/KDJ/RSI/成交量/周线月线MACD等）的坐标轴保留，不在这次改动范围内
- 用真实数据验证：5个窗口的主图都确认横纵三根轴（日/月两层X轴 + Y轴）`IsAxisVisible` 都是false，`IsPanEnabled`/`IsZoomEnabled` 都还是true；其余面板的坐标轴逐一确认没被误改，仍然可见

## 5. 功能四：自选股跟踪（勾选加入自选，记录挑选依据，供后续跟踪/优化算法）

### 5.1 需求背景

用户看好某只从上面七种方法里筛选出来的股票时，需要能"留痕"——记录清楚是哪个方法、依据哪天的数据算出来的，这样过一段时间回来看这只股票走势如何，就能判断这个方法/参数当时判断得准不准，用于后续调整算法。

### 5.2 交互

- 五个方法各自的结果 DataGrid 都加了一列"选"（`DataGridCheckBoxColumn`，绑定 `IsSelected`），以及一个"加入自选"按钮
  - **状态变更记录（2026-07-08）**：`DataGridCheckBoxColumn` 默认要点两下才能勾选上（第一下WPF会先用来让单元格获得焦点/选中，只有已经聚焦的单元格才会把点击继续传给里面的复选框）。修的方法是在 `Window.Resources` 里给 `DataGridCell` 挂一个隐式样式，在鼠标按下的Tunneling阶段（`PreviewMouseLeftButtonDown`，比复选框自己的点击处理更早触发）就让单元格提前获得焦点，这样同一次点击的后半段就能直接落到复选框上，一次点击就能选中。隐式样式（不带 `x:Key`）对本窗口所有 DataGrid 的所有单元格自动生效，包括自选股表格。
- 用户在结果里勾选想跟踪的股票（可多选），点击"加入自选"，勾选的行会被写入自选列表（同一批操作里跟已有记录重复的会被跳过，见5.4节去重规则），操作完成后无论是否真正写入都会把这些行的勾选状态清空（避免下次分析后误以为还处于"已勾选待加入"状态）
- 新增第5个 Tab"自选股"，展示所有跨方法加入的股票：代码/名称/方法/数据日期/当时价格/满足数/加入时间，配"刷新"和"移除勾选"两个按钮
- 切换到"自选股" Tab 时会自动刷新一次（`MainWindow.TabControl_SelectionChanged`，专门判断 `e.AddedItems[0] is TabItem { Header: "自选股" }`——`SelectionChanged` 也会从 Tab 内部的下拉框等控件冒泡上来，不能只看事件有没有触发，得看具体选中的是不是这个 TabItem）
- 双击自选股列表里的某一行，会重新弹出该方法对应的详情图表窗口——**图表本身用最新的K线数据重新画**（这样能看出加入自选之后走势如何），但**文字判断依据用加入自选那一刻的快照**（见5.5节），这两者故意不是同一个时间点的数据，这正是"跟踪"要看的东西

### 5.3 数据存哪里、存什么

不写入 `current.sqlite`（那是 Fetcher 产出的共享数据文件、分析程序只读，见第2节），而是分析程序自己的状态，存在 `{程序所在目录}\data\watchlist.json`（`AnalyzerPaths.WatchlistPath`，故意放在 `LocalDir` 外面、跟 `current.sqlite` 分开，避免以后被误当成"可以直接删了重新拉"的那类文件）。用一个扁平JSON数组，没有用SQLite——现实里也就是几十到上百条手动挑选的记录，不值得为此单独开一张表。

每条记录（`WatchlistEntry`）：

```csharp
public class WatchlistEntry
{
    public Guid Id { get; set; }              // 用于"移除勾选"定位这条记录——重新反序列化后对象引用不再相等，得靠这个
    public string Code { get; set; }
    public string Name { get; set; }
    public string Method { get; set; }        // "三角收敛"/"峰哥法"/"耀哥法"/"彬哥法"/"金叉法"
    public string Granularity { get; set; }   // 只有峰哥法用户可调，其余四种固定 "day"
    public int? Lookback { get; set; }        // 峰哥法（"前N根K线"）和三角收敛（"形态窗口"）用到；其余方法为 null
    public double? DifThreshold { get; set; } // 只有耀哥法有意义（DIF阈值）
    public DateTime DataDate { get; set; }    // 算出这条结果时用到的最新一根K线日期——不是加入自选的时间
    public double PriceAtPick { get; set; }   // DataDate那天的收盘价
    public DateTime AddedAt { get; set; }     // 真正点"加入自选"按钮的时间
    public int SatisfiedCount { get; set; }
    public int TotalCount { get; set; }
    public List<CriterionSnapshot> Criteria { get; set; } // 加入自选那一刻，各条规则是否满足+文字依据的快照
}
```

`DataDate`/`PriceAtPick` 来自 `StockScreenResult` 新增的两个字段（`DataDate`/`LastClose`）——五个分析引擎产出结果时顺带算好，不是watchlist专属逻辑，只是恰好只有watchlist用到。

### 5.4 去重规则

按 `(Code, Method, DataDate.Date)` 三元组去重——同一只股票、同一方法、同一天的数据只会存一条记录，重复运行分析、重复勾选同一批结果不会越攒越多；但同一只股票不同方法各存一条（不同方法判断依据不一样，值得分别跟踪），同一方法不同数据日期（比如隔几天又选中一次）也各存一条（能看出"这只股票被这个方法连续选中了几次"）。

### 5.5 双击详情重建逻辑

点开自选股列表某一行时（`MainWindow.WatchlistGrid_MouseDoubleClick`），从 `WatchlistEntry.Criteria` 快照重建一个 `StockScreenResult`（`Passed` 固定给 `true`，因为原始判定结果本身已经不重要，只是要把文字依据传给图表窗口），再按 `Method` 分发到对应的详情窗口构造函数（`DetailWindow`/`GoldenCrossDetailWindow`/`BottomReboundDetailWindow`/`MidCapPullbackDetailWindow`），K线数据统一用 `vm.BarRepository` 按当前最新数据重新查询——如果这期间股票停牌/退市导致查不到K线，会弹提示而不是抛异常崩溃。

### 5.6 验证方式

构造真实的 `MainViewModel` + 四个方法的 Tab ViewModel，对真实 `total.sqlite` 跑一次金叉法分析、勾选一条真实结果，走一遍"加入自选→写入 watchlist.json→切到自选股Tab刷新→点按钮重建详情窗口"的完整链路，确认每一步产出的数据字段都跟源头（`StockScreenResult`）对得上，且真实构造出的 `GoldenCrossDetailWindow`/`QuoteDetailWindow` 不抛异常；`JsonWatchlistStore` 的增/去重/删单独用构造出的假数据验证过。

### 5.7 个股分析笔记（新增，2026-08-27）

**需求**：用户问"能不能在本地保存个股的定期分析数据，下次只分析最新的"。拆开看是**两件事**，答案不同：

| | 做法 | 理由 |
|---|---|---|
| **客观数据** | 存进数据库 | `FinancialReport` 的科目从 8 个扩到 52 个（见[数据字典](data-dictionary.md)）。营运资金拆解、净利率归因、收现比、有息负债、ROE 全都能直接算，**不必留档** |
| **分析判断** | 存 markdown 文件 | "利润下滑里哪部分可逆"、"负债率改善其实来自转债转股而非经营"、"下次要盯什么"——这些是推理产物，**算不出来**，只能写下来 |

一句话：**库存数据，笔记存判断。**

### 存哪里

`data
otes\{code}.md`，一票一份（`AnalyzerPaths.NotesDir` / `StockNoteStore`）。

用 markdown 纯文本而不是数据库表：笔记是给人读写的，要能直接拿编辑器打开、能贴表格和链接；几十只票几十个小文件，上 SQLite 没有任何好处。

⚠ **默认不在版本控制里**：`.gitignore` 忽略了整个 `publish/`，所以这些 .md 不受 git 保护，误删就没了。要纳入版本控制得在 `.gitignore` 里加 `!publish/data/notes/` 之类的例外——但那意味着笔记会跟着仓库推到远端，如果远端不是私有的，持仓判断就公开了。**这个取舍留给用户决定，代码不替他选。**

### 交互

入口在【行情详情】窗口顶部的 **"分析笔记"** 按钮（放在"其他数据"左边——看完数据顺手记结论是自然动线）。所有列表页的行都有"行情详情"，所以从任何地方都能到达。

- **有笔记的票，按钮显示"分析笔记 ●"** —— 不点开就知道这只票记过东西
- 新建时给一个模板，模板开头就写着"能从库里算出来的数据不要抄到这里"——半年后回来看，最容易犯的错就是把可重算的数据抄一份进笔记，然后两边不一致
- **【插入今日小节】** 按在正文最前面插入 `## yyyy-MM-dd` 段，最新分析在最上面，不用滚到文件底部；当天已有小节则提示不重复插
- Ctrl+S 保存；有未保存改动时关窗会拦一下问（手打的东西误关一次就白写了，数据类窗口关掉无所谓）
- **内容清空后保存 = 删除该文件** —— 空笔记留着会让"哪些票有笔记"的判断失真

### 为什么不做成【其他数据】里的一个页签

`StockDossierWindow` 的页签是按数据表动态生成的，笔记塞进去会变成"行情详情 → 其他数据 → 第 N 个页签"三层深。笔记是**要动手写**的东西，埋那么深就不会写了。独立窗口 + 一个按钮直达。

### 没做的

`StockNoteStore.CodesWithNotes()` 已经能返回"哪些票有笔记"，但还没接到任何列表页（比如在自选股/底仓表格里加一列 ● 标记）。需要的话再加，接口是现成的。

### 5.8 财务分析（新增，2026-08-27）

**需求原话**：先做了 5.7 的"分析笔记"之后，用户澄清："其实我想做的是对财务数据进行分析，就分析成我们更容易看明白的数据。" —— 笔记只是存判断的地方，不解决"看懂"这件事。

**定位：把 52 个财务科目翻译成人能一眼看懂的判断，不是再列一张比率表。** 具体是三件事：

| | 做法 | 反例 |
|---|---|---|
| ① 数字变判断 | 每行都带"这意味着什么" | 只显示 `现金流/净利 = 0.33` 没用；要同时说"利润没变成现金，窟窿在经营性应收 13.72 亿、存货 9.25 亿" |
| ② 自动归因 | 把变化拆到成因上 | "净利率掉 5.90pct"没用；"其中毛利率只解释 1.70pct（结构性、回不来），4.20pct 在毛利以下（费用和浮亏、部分可逆）"才有用 |
| ③ 抓出容易误读的地方 | 主动点出反直觉的组合 | 资产负债率降 3.5pct 看着是好事 —— 但同期有息负债较上期末涨 23.8 亿、短期借款翻倍，降的功劳属于可转债转股。**单看那个比率会得出相反结论** |

实现：`StockPlatform.Logic.Services.FinancialAnalyzer`（纯计算、不联网）产出 `FinancialAnalysisReport`；界面 `FinancialAnalysisWindow`（左表格 + 右趋势图 + 底部异常项汇总）。入口在【行情详情】顶部的 **"财务分析"** 按钮 —— 所有列表页的行都有"行情详情"，所以从任何地方都能到。

#### 五节结构

1. **赚钱的规模 vs 赚钱的效率** —— 营收、归母净利（含单季拆解与单季同比）、毛利率、净利率
2. **净利率的变化掉在哪** —— 拆成"毛利率贡献"和"毛利以下贡献"，再列四费明细和公允价值变动
3. **利润有没有变成现金**（最该看的一块）—— 经营现金流、覆盖率、收现比、营运资金占用拆解
4. **扩张的钱从哪来** —— 经营造血占比、投资/筹资、资产负债率、有息负债
5. **回报与估值** —— 年化 ROE、PB、PE(TTM)、股息率

每节末尾给一句结论（"整节看下来该得出什么"，不让用户自己拼）；没什么可说时**不硬凑**（格力的第 2 节就是空的，因为它净利率几乎没变）。

#### 阈值写死在代码里，不做配置项

一上来做成可配置，用户还得先去想每个数填多少。先按常规财务分析的经验值定、每条在注释里写明依据，用一段时间发现哪条老是误报再调。

| 指标 | 警戒 | 严重 | 依据 |
|---|---|---|---|
| 经营现金流 / 归母净利 | < 0.6 | < 0.3 | 健康的制造业常年 0.8~1.2 |
| 收现比 | < 1.05 | — | **基准是 1.13 不是 1.0**：收到的现金含增值税、营收不含税。这点极易看错，把 1.02 当成"正常" |
| 经营造血占资金来源 | < 20% | — | 低于此说明扩张靠借钱/融资 |
| 归母净利同比 | < −15% | < −30% | |
| 毛利率同比 | < −1.5pct | — | 毛利率是最难改善的指标 |
| 年化 ROE | < 5% | < 3% | 低于 5% 股东回报接近理财产品 |
| 资产负债率（非金融） | > 70% | — | |

判定为"严重"的行会集中汇总到窗口底部的异常项区，并在表格里加粗标红。

#### 三个容易做错的口径（都是实测踩出来的）

**① 存量项目不能只跟去年同期比。** 流量（营收/利润/现金流）是区间累计值，跟上期末比没有意义，所以只看同比；但存量（资产负债率/有息负债/借款）必须**同时给"同比"和"较上期末"**。实测 603501：有息负债 vs 去年同期是 65.24→58.19（降），vs 上期末却是 36.97→58.19（半年翻着涨）—— 只看同比会把"最近半年在大举借钱"完全掩盖掉。

**② 营运资金占用要用现金流量表附注的口径，不能拿资产负债表两个时点相减。** 附注口径含合并范围变动，且"经营性应收项目"覆盖应收账款+票据+预付+其他应收。实测 603501 两种口径差了近一倍：存货 5.89 vs 9.25 亿、应收 7.12 vs 13.72 亿。

**③ 同比必须拿同一个月份的报告期比。** A股定期报告是年内累计口径（一季报=Q1、半年报=Q1+Q2…），2026-06-30 要对 2025-06-30，不能跟上一期 2026-03-31 比。单季数据用"本期累计 − 上期累计"算。

#### 趋势图的两个设计决定

- **只取跟本期同月份的报告期**（最多 8 期）。混着比会画成锯齿 —— 一季报低、年报高不代表变差变好。
- **所有序列共用同一条报告期轴，某期算不出来放 `NaN` 占位而不是删点。** 原来是直接过滤掉算不出的点，于是各序列点数不同、索引各自重编号，几张图并排时同一列对应的不是同一期。实测 603501：2023H1 归母净利为负，"现金流/净利"那条算不出来被删，那张图 x 轴就只剩 7 个标签、22/06 和 24/06 直接相邻，看着像连续的还跟上面几张图对不齐。**横向扫描多张图的前提就是 x 轴一致，宁可留空也不能错位。** 柱状图遇 NaN 不画柱、折线遇 NaN 断开。
- 比率类序列截到 [−3, 3]：603501 在 2023H1 净利仅 1.53 亿、比率 20.44，一个点就把整张图的纵轴压平。超出这个范围只需知道"极端"，不需要具体值。

#### 金融机构走简版

银行/券商/保险没有"营业成本"，毛利率算不出来；"存货""收现比""营运资金占用"对它们也没意义。用**数据本身**判定（营业成本缺失或为 0）而不是查行业表 —— 行业表覆盖率不满，漏判会让整份报告显示一堆 n/a。判定为金融机构时跳过第 2 节和现金流里那几项，并在标题标注"金融机构（简版指标）"。

#### 验证方式

计算层**先脱离 UI 端到端验证，再做界面**。用两只性质相反的票回归：

- **603501 豪威集团**（恶化型）：异常项 4 条，正确抓出"营收持稳但盈利能力塌了""现金流比利润跌得更狠""负债率改善来自转债转股"
- **000651 格力电器**（健康型）：异常项 **0 条**。同样是"现金流跌得比利润狠"，格力只给 Warn（覆盖率 1.42 仍优秀），603501 给 Bad（0.33 已破线）—— 说明阈值不是一刀切

顺带一个发现：格力 2020H1/2021H1 的经营现金流是负的（−45 亿 / −61 亿），说明这家公司现金流本来就大幅波动。**同一个"现金流/净利 = 1.4"对格力正常、对一家常年 0.9~1.1 的公司可能就是异常** —— 这种基准差异只有把 8 期摆在一起才看得出来，也是趋势图存在的意义。

验证过程还发现我手算的四个数是错的（营运资金占用 14.98→22.44、收现比 1.02→0.99、覆盖率 0.35→0.33、Q2 单季 6.61→7.17 亿）—— **手抄必错，自动算不会**，这本身就是这个功能的价值。

### 5.9 界面主题：浅色 / 深色 / 跟随系统（2026-08-29 新增）

两个程序（Fetcher 和 Analyzer）共用一套主题，**默认深色**。顶部有【主题】下拉，切换立即生效、不用重启；选择存在 `data/ui-theme.json`，两个 exe 装在同一目录、共用同一个 `data/`，所以在哪个程序里改，另一个下次启动也是这个主题。「跟随系统」读 Windows 的"设置 → 个性化 → 颜色 → 默认应用模式"，系统切换时程序会自动跟着变。

实现放在 `src/StockPlatform.Desktop/Shared/Theme/`，跟单实例守卫一样用 csproj 的 `Compile`/`Page` + `Link` 链接进两个项目（不是各复制一份）：

- `Colors.Light.xaml` / `Colors.Dark.xaml`：只有画刷，键名 `Theme.*` 一一对应。窗口 XAML 里所有颜色都写成 `{DynamicResource Theme.*}`，`ThemeManager` 换字典时 WPF 自动重刷。**必须是 DynamicResource**，StaticResource 加载时就把值定死了。
- `Controls.Dark.xaml`：深色专属的控件模板。WPF 内置模板把浅色渐变/悬停高亮写死在模板里，只设 Background/Foreground 压不住，所以按钮/输入框/下拉/页签/滚动条等都换了一套极简模板。浅色不加载这份。
- `Controls.Common.xaml`：两个主题都加载。表格列头/单元格样式必须放这里——窗口里有二十几处列级 `HeaderStyle`（只为给列头挂 ToolTip），列级 Style 一出现 App 级隐式样式就整份失效，只能让它们 `BasedOn` 一个**换主题时不被替换的**样式对象。代价是浅色下列头不再是 Windows 原生渐变，改成纯色版。
- `ThemeManager` / `ThemeBrushes` / `ThemeSwitcher`：分别是切换入口、代码里用的语义画刷（同一个 SolidColorBrush 实例改 Color，绑定它的文字会自动变色，不用 ViewModel 重发 PropertyChanged）、以及那个下拉控件本身。

图表（OxyPlot）不吃 DynamicResource，单独由 `ChartTheme` 处理：各 ChartBuilder 建 model 时调一下 `ChartTheme.Track(...)`，它订阅 `PlotModel.Updated`——OxyPlot 每次绘制前都会 Update 一遍，那一刻坐标轴和序列都已加齐，正好上色（坐标轴文字、网格、图上直接标的数值、零轴/十字线，并把纯黑这类在深底上看不见的线按亮度提亮）。改之前先把原配色整份快照下来，切回浅色时照着还原，所以浅色下图表跟做主题之前完全一样。

> 这里踩过一个坑，别改回去：最初想用 `EventManager.RegisterClassHandler(typeof(PlotView), FrameworkElement.LoadedEvent, …)` 一处安装全局接管，**一次都不会触发**——WPF 的 Loaded/Unloaded 是 BroadcastEventHelper 广播的，不走类处理器。当时的表现极具迷惑性：图的底色变深了（那是 PlotView 控件自己的 Background 跟着主题走），但画布里的数值标签还是黑的，很容易误判成"配色没调好"而不是"整段代码没跑"。

**窗口标题栏**（连同边框和右上角三个按钮）是非客户区、由 Windows 自己画，WPF 的样式和画刷都够不着，只能用 DWM 的 `DWMWA_USE_IMMERSIVE_DARK_MODE` 属性通知系统（属性号在 Win10 20H1 以后是 20、1809~1903 是 19，所以先试 20 再退回 19）。新开的窗口靠一个挂在 `Window.SizeChanged` 上的类处理器自动跟上——**不能用 Loaded**，原因同上面图表那条。

**故意不跟随主题的地方**：行情详情（K线）窗口。那是通达信风格的黑底专业看盘窗，本来就自带一整套深色配色（`QuoteChartBuilder`），两个主题下都保持原样；`ChartTheme` 见到图自己设了 `PlotModel.Background` 就跳过。

现在项目结构很简单：`StockPlatform.Logic`/`StockPlatform.Data`（共享库，被 Fetcher 和 Analyzer 两边引用）+ `StockPlatform.Fetcher`（数据获取）+ `StockPlatform.Analyzer`（本文档，含三角收敛/峰哥法/耀哥法/彬哥法/金叉法/阶梯低点法/短线法七种分析方法，外加查询/自选股两个 Tab）。分析程序**只读**打开本地总数据文件做查询分析，不写入——数据库文件本身是用户手动拷贝进来的，分析程序不做任何写操作。
