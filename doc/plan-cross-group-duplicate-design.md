# 计划项支持跨组重复

2026-10-27 起草。**方案，等确认后再动手**（`PlanRunner` 那两处已先改，见下）。

## 一、要达到的模型

> **调度只管什么时候跑，任务只管做自己的事。**
> 一个任务放在哪个组，就按那个组的时间跑；要在不同时间跑两轮，就在两个组里各放一份。

一句话：**组的时间 = 这一份的执行时间，没有例外、没有隐式补充。**

## 二、现状跟这个模型差在哪

### 差异一：同一个动作不能出现在两个组里

界面注释写着「跨组唯一，右边依赖列才指得清是谁」，模板 `Apply` 会把别组的同名项**搬走**。所以想让一个任务早晚各跑一轮，做不到。

### 差异二：有一条**隐式**的第二到点

`FetchPlan.DueAnchorAt` 里，「每工作日」的组除了自己设定的时刻，还会被自动补上一个 **17:00（收盘）**：

```csharp
var offsets = new List<TimeSpan> { offset };
if (offset < MarketCloseOffset) offsets.Add(MarketCloseOffset);   // 设定时刻早于 17:00 就补一档
```

这是 2026-09-04 为「收盘前跑到的当日数据不完整」加的。它确实解决了那个问题，但代价是**组的时间不再等于执行时间**：

- 「早间（开盘前）」组设的是 08:15，实际每天跑 **08:15 和 17:00 两轮**
- 昨天的日志就是证据：`17:01:33 ▶ 计划：开始【回购公告进展】`
- 光看计划界面，没人能看出来它一天跑两次

**这正是"不清晰"的根源**：想让任务跑两轮，不是在计划里摆两份，而是靠一条藏在代码里的规则。

## 三、改法

### 改动 A：支持跨组重复

数据结构本来就支持（`FetchPlanItem` 是对象，各自带 `LastStart`/`LastOutcome`，`AlreadyRanOn` 读的是自己那份）。要改的只是几处**假设了唯一**的查找。

`AllItems` 全部 21 处用法里，18 处是 `foreach` 遍历或 `Where` 过滤，天然支持重复。真正要改的 5 处：

| 位置 | 现在 | 改成 | 为什么 |
|---|---|---|---|
| `PlanRunner.DependencyFailedThisRound` | 取第一份，它失败就拦 | **每一份都失败**才拦 | 早间组那份跑成功了，数据就在库里，没理由拦后面的项 |
| `PlanRunner.WarnIfSoftDependencyStale` | 取第一份判新鲜度 | **任一份**本轮成功就不提示 | 同上，否则天天挂假警告 |
| `FetchPlanTemplates.Apply` | 把别组的同名项**搬过来** | 只在**本组内**找，没有就新建，不动别组 | 铺模板不该把人在别组摆好的那份偷走 |
| `FetchPlan.MigrateRetired` | 取第一个含该动作的组搬家 | **目标组已经有了就不搬** | 否则会把早间组那份搬进日更组 |
| `FetchPlan` 等价项展开（1106 行） | 取第一份，没启用就搬走 | 同样只认本组 | 同上 |

不用改的：

- `Normalize` 补齐动作全集（`AllItems.Select(i => i.Action).ToHashSet()`）——它只判断"这个动作在计划里有没有"，有两份照样算有
- 界面编号 `Number = 组号.序号`——两份本来就在不同组，编号天然不同，依赖列也指得清
- `PlanItemViewModel` 那一堆 `IsXxx`——判的是项自己的 `Action`，跟唯一性无关

**并发安全**：`PlanRunner` 是严格串行的（共用限流器、SQLite 写锁、而且大部分任务打同一家服务器），两份最多排队先后跑，不会并发写库。

### 改动 B：去掉隐式的 17:00 补档

`DueAnchorAt` 里那两行删掉，`MarketClose` 常量一并退役。此后：

- 组设 08:15，就只在 08:15 跑
- 想要收盘后那轮，**在日更组里再放一份**——这才是"在计划里看得见"的表达方式

改动 A 是改动 B 的前提：没有跨组重复，去掉补档就等于砍掉一轮。

### 改动 C：界面入口

光有内核没用，得有办法摆出第二份。在计划项的右键菜单加一条「**复制到其他组**」，二级菜单列出其余各组：

- 复制出来的是一份**全新的项**（不带上一份的运行记录），默认不启用——没经过确认的项不该自己跑起来，跟 `Normalize` 补新动作的做法一致
- 插在目标组末尾，顺序由人拖
- 同组内已经有了就灰掉那个菜单项（同组放两份没有意义：同一时间跑两遍）

顺带把 `MainWindow.xaml` 里「跨组唯一」那句注释改掉。

## 四、迁移：现有计划怎么办

去掉补档会让早间组的【回购公告进展】从"每天两轮"变成"每天一轮"。要保持原行为，得在日更组补一份。

放进 `MigrateRetired` 那套一次性迁移里（它本来就是干这个的），只做一件事：

> 凡是 `NotBefore < 17:00` 的「每工作日」组，组里**启用着的**每一项，在日更组补一份同样启用的 —— 因为它们此前确实靠补档在收盘后跑过一轮。补完报一行说明。

这样老计划的行为一字不变，只是从"隐式"变成"摆在明面上"。
按现在的计划，受影响的只有早间组那一项。

## 五、风险

| 风险 | 处置 |
|---|---|
| 两份同时到点 | 不会并发——`PlanRunner` 严格串行，先后跑而已 |
| 任务本身不幂等？ | 日更这些任务本来就按"本地缺什么抓什么"做增量，第二轮多数直接 `NothingToDo` 秒过。这正是"任务只管做事"的前提，不是新引入的假设 |
| 两份的运行记录互相覆盖 | 不会，记录在各自的项上；任务内部的抓取状态（如 `FinancialFetchState`）本来就该共享——早上抓过的晚上不重抓，正是想要的 |
| 人不小心放了三四份 | 界面不拦（职责上这是人的选择），但同组内重复会灰掉 |
| 去掉补档后有人少跑一轮 | 靠改动 D 的一次性迁移兜住；迁移会报出改了什么 |

## 六、测试

1. **跨组重复的调度**：同一动作放两个组、两个不同时刻，各自按自己的时刻到点，互不影响（`AlreadyRanOn` 分别判）
2. **前置判据**：一份成功一份失败 → 不拦后面的项；两份都失败 → 拦
3. **软前置提示**：任一份本轮成功 → 不提示
4. **模板 Apply**：铺模板不会把别组那份搬走
5. **去掉补档**：`NotBefore=08:15` 的组，17:00 不再产生到点
6. **迁移**：老计划（早间组有启用项、日更组没有）跑一次迁移 → 日更组补上一份，行为跟补档时代一致
7. 全量 `dotnet test`（改了 `FetchPlan`/`PlanRunner`，按惯例必跑）

## 七、实现记录（2026-10-27 已完成）

A / B / C 全部落地，编译 0 错误，全量 2443 个测试通过。

| 改动 | 落点 |
|---|---|
| 硬前置：每一份都失败才拦 | `PlanRunner.DependencyFailedThisRound` |
| 软前置：任一份成功就不提示 | `PlanRunner.WarnIfSoftDependencyStale` |
| 手动执行前的前置询问：任一份跑过就不问 | `MainViewModel` |
| 模板只认本组、不搬走别组那份 | `FetchPlanTemplates.Apply` |
| 挪组迁移：目标组已有就不搬 | `FetchPlan.MigrateRetired` |
| 等价项展开：别组那份一律不碰 | `FetchPlan`（RetiredInto 那段） |
| **收盘到点退役** | `FetchPlan.DueAnchorAt`，`MarketClose` 常量删除 |
| **一次性迁移补偿** | `FetchPlan.MigrateCrossGroup` |
| 右键「复制到其他组」 | `MainViewModel.CopyPlanItemToGroupCommand` + `CopyTargets`，`MainWindow.xaml` 的 ContextMenu |
| 右键先选中行 | `MainWindow.xaml.cs.PlanGrid_PreviewMouseRightButtonDown` |

两个实现时才发现的坑：

- **ContextMenu 不在视觉树里**，子项绑不到 `RelativeSource AncestorType=Window`，拿不到 MainViewModel 上的命令。解法是把命令和参数打包进 `CopyTargetViewModel`，再靠 DataGrid 的 `Tag` 把 MainViewModel 递进去。
- **WPF 的 DataGrid 右键不改变 SelectedItem**，不处理的话会"在 A 行右键、复制走 B 行"。加了 `PreviewMouseRightButtonDown` 先选中。

测试：`PlanCrossGroupTests` 新增 8 条（两份各走各的时间、不再多出收盘档、模板不搬走、迁移的三种情形）；`PlanRobustnessTests` 里三条写死收盘档的老测试改写成反面断言（设定时刻之外不再多出到点）。

**还没做的**：把【拉取财报预约日】【拉取业绩预告/快报】【拉取财务报表】真的排进早间组——那是计划配置（`publish/data/fetch-plan.json`），要等 Fetcher 关掉才能改，或者用新加的右键菜单自己点。
