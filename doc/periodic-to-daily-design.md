# 季度组再挪三项进日更 设计方案

2026-10-21 · 状态：方案待确认，未写代码 · 前一份：doc/financial-daily-design.md

## 1. 范围

| 任务 | 从 | 到 | 理由（一句话） |
|---|---|---|---|
| 【拉取分红送配】 | 季度定期 | 每日收盘后 | 分红是复权因子的输入，按月更新时回测序列 day_adj 会在除权日后静默错到下个月 |
| 【拉取股东数据】 | 季度定期 | 每日收盘后 | 已按实际披露日判"要不要抓"，但每月 1 号才跑，月中披露的股东户数要等一个月 |
| 【导入手工数据】 | 季度定期 | 每日收盘后 | 填完回填清单第二天自动写回；它硬依赖的【金融监管指标】已在日更 |
| 【重解析已有PDF】 | 季度定期 | 按需启动 | 只有改了解析规则才需要；监管指标有活的那天本来就先重解析一遍 |

三项的"要不要抓"判据**都不改**，改的只是排期。

## 2. 日更组里的位置

日更组尾部现在是：`… 龙虎榜席位 → 拉取财务报表 → 金融监管指标`。改成：

```
… 龙虎榜席位 → 拉取财务报表 → 金融监管指标 → 导入手工数据 → 拉取分红送配 → 拉取股东数据
```

- **导入手工数据**紧跟监管指标：硬前置，同组前一项最稳。1 秒，纯本地。
- **分红在财务报表之后、不在【重算回测序列】之前**。考虑过排到重算前面（当天抓、当天重算），没这么做：
  - 分红平日要十几分钟（见 §4），排在中间会把后面的板块、板块指数合成往后推；
  - 实施公告一般比除权日早好几个交易日，当天抓到、**次日**日更的【重算回测序列】就会把它算进去，
    仍在除权日之前——晚一天不产生错值。
  - 重算侧不用改：它本来就按"Dividend 的 fetched_at 比 day_adj 新"认出要重算的票（`SqliteAdjSeriesAuditor.CodesWithStaleEvents`）。
- **股东数据排最末**：三项里最不急的，季度高峰约一小时，排最后不挡任何东西。
- 财务报表仍在这三项之前——披露高峰日它最重要，不该等分红和股东跑完。

顺序硬约束（写进模板测试）：财务 < 监管指标 < 导入手工数据；预约日 < 财务、股东（软前置）。

## 3. 现有计划怎么迁

同上次：`FetchTaskCatalog.DefaultGroupOf` 改归属、`DailyOrder`/`PeriodicOrder`/`OnDemandOrder` 改列表、
`FetchPlan.Regrouped` 加四行（启用状态和模式照搬，不替用户改）：

| 动作 | 搬到 | 迁移时的处理 |
|---|---|---|
| ImportManual | 日更 | 照搬。⚠ 名单里要排在 BankRegulatory **之后**（`TemplateIndexIn` 按组里已有项定位，监管指标得先到位） |
| FetchDividend | 日更 | 照搬 |
| FetchShareholder | 日更 | 照搬 |
| StepReparseBankPdf | 按需启动 | 按需组是「手动」，`Normalize` 会把它取消勾选——这正是"按需"的意思，想跑点那一行的【执行】 |

加载时日志各打一行“已从「季度定期」挪到「…」”。你现在的计划里日更组最后一项是监管指标，
按模板序算，三项会依次落在它后面。

## 4. 天天跑要花多少

| 任务 | 平日 | 高峰 / 特殊日子 |
|---|---|---|
| 导入手工数据 | 1 秒 | 同 |
| 拉取分红送配 | 估计每天 60~100 只、约 10~15 分钟（90 天兜底轮换 ≈ 61 只/天 + 当天公告命中的） | 4 月底年报分红预案集中：公告命中可能上百只；每轮上限 400 只 ≈ 1 小时 |
| 拉取股东数据 | 没新披露时几乎不发请求；100 天兜底 ≈ 55 只/天 × 2 个请求，约 2 分钟 | 季报高峰约 1 小时（目录里的实测） |

⚠ 分红那行的"平日"是按判据推算的，**没实测过**。另有一处会扎堆：本地分红水位里有 3294 只是 09-07 抓的、
2410 只是 09-18 抓的，90 天兜底到期在 12-06 和 12-17 前后，那两周每天会顶着 400 只的上限跑约一小时，
之后轮换自然摊平。股东数据 09-02 有 5550 只，但三季报披露期会把绝大多数刷新掉，100 天到期时剩不了多少。

**分红保留每轮 400 只的上限**——跟财务报表不同：分红值取新浪，新浪对整域限流（09-18 上午整域 456 过），
一轮放开几千只风险大；没抓完的第二天照样在名单里，跟你定的"第二天接着取"是一个意思。
这一条要你拍板，见 §7。股东数据本来就不设上限，不动。

## 5. 报错（沿用两项现有行为，跟财务报表口径一致）

- 两项都是抓一批存一批，已抓的不会因后面失败而丢；
- 连续 3 批（90 只）全部因限流失败就收工记成「跳过」——计划先跑别的，隔一段冷却再回头试，不挡后面的任务；
- 收工那句已经只报只数（"本轮 191 只、有分红 184 只、改写 2,908 条、失败 0 只"），不列代码；
- 没抓成的票水位没动，第二天日更照样在名单里；手动点【执行】随时可补。

## 6. 文案和测试

**目录文案**：三项的频率说明改成"每工作日"；分红那句"⚠ 抓完要再跑一次【重算回测序列】"改成
"次日日更的【重算回测序列】会自动算进去"；重解析那项改成"按需：改了解析规则后手动点"；
`SqliteAdjSeriesAuditor.CodesWithStaleEvents` 注释里"每月触发一次全量重算"改成"每天只重算当天抓过分红的那几十只"。

**单元测试**（`PlanTemplateTests`）：
- 模板：日更组尾部依次是 财务 → 监管指标 → 导入手工数据 → 分红 → 股东；季度组不再有这四项；重解析在按需组且未启用；
- 迁移：老计划四项都在季度组 → 加载后到位、启用状态/运行记录照搬、再加载不动；
- 【龙虎榜席位】那条用例跟着改成"排在当天核心数据之后"（它后面变成 5 项）。

**实机**（Debug、OfflineMock + BarSource=Mock，零联网）：股东数据已有 `MockShareholderProvider`；
**分红没有离线模拟源**（查过 Data/Remote 和 App.xaml.cs），要补一个 `MockDividendProvider`，连同分红公告索引也要拦住
（索引走东财 datacenter，不拦会发真请求）。跑一遍计划看迁移日志、五项依次跑完、收工只数；验完还原 Debug 数据。

## 7. 要你定的

1. **分红是否保留每轮 400 只上限**——我建议保留（理由见 §4）。
2. 分红排在财务之后还是【重算回测序列】之前——我建议之后（理由见 §2）；排之前的代价是平日日更中段多十几分钟。

## 8. 实施补记（2026-10-21）：导入手工数据的自动导入规则

实机验证时发现两个问题，按用户定的改法修了：

- **清单不存在算没活**（原来算失败）——所有指标都齐全时根本不会生成清单，挪进日更后会天天报红。
- **自动跑只导“人改过、这一版还没导过”的清单**：`待手工回填清单.state.json` 记生成时刻和上次导入的版本，
  判据在 `ManualFillImportRule`。原来监管指标一生成清单、紧接着的自动导入就会把所有 OCR 值标成“已核对”。
  手动点【执行】照旧清单在就导（`TaskRunArgs.Manual`，只有“手动执行”那条路传 true）。
- **改过没导的清单不覆盖**：监管指标重新生成前先看一眼，免得把人填的数静默扔掉。
- 没有记录的旧清单（生产上现在那份）自动跑不导，改过的话手动点【执行】，导完会补上记录。
