> 2026-09-22。**方案稿，未动任何产品代码。**
>
> ⚠ 另一个会话正在同一个 checkout 上迁【重取前复权】（`RunRepairQfqAsync` 已删、
> `QfqRepairTask.cs` 新增，`BarFetchTaskBase.cs` 等在它的未提交改动里）。
> 本方案的实施要等那边落地并提交。

## 0. 结论先行：它应该是**分派器**，不是搬家

第一版方案（本文档 v1）设计的是"把十一段整体搬进一个 `FetchYearTask`"。**那是错的形状。**

用户提出的形状更对：**【拉取区间数据】本身不抓任何东西，只是带着"年份区间"这个参数
去调已有的各个任务**。三条理由：

1. **已经有一模一样的先例**：【重新拉取失败】就是这个形状——它自己不抓东西，
   读统一待办清单、按 `taskId` 分派给各任务自己补（`ITaskBacklogRunner`）。
   两者的差别只在**分派依据**：那边是"待办清单"，这边是"年份区间"。
2. **十三段全都已经有对应的新框架任务了**（见 §2 的对照表）。搬家等于把这些任务的逻辑
   再写一遍——而"两份判据迟早分叉、分叉的表现是某个口径的K线值悄悄不一样"正是
   这一批迁移里最贵的那类错。
3. **目录里这一项自己的注释早就指了这条路**：
   「要只补某一类历史时，用对应项的「首次整段回补」模式更省」。
   子任务本来就会干这件事，缺的只是"补到哪一年"这个参数。

## 1. 它现在是什么形状

`FetchOrchestrator.RunFetchYearInternalAsync`（约 190 行），一次跑十一段，顺序固定，
每段的目标都是**现算**的：按「本地最早是哪天」加 `BarProbeFloor` 水位算缺口，
已经补到的整只跳过、连请求都不发。所以中断重跑不会重抓已有数据。

但它**没有断点**，也没有 `MaxItems`/`Deadline`（老编排器方法只收一个 `ct`），
不支持"今天跑一半、明天接着跑"。中断后从第 1 段重走，并且会丢三样**收尾才落盘**的东西：

| 丢什么 | 落盘时机 | 后果 |
|---|---|---|
| **`BarProbeFloor` 水位** | `RecordProbeFloors`，每段末 | 本轮探明的"数据源没有更早数据"结论全丢，下次**重新发一遍空请求**。2026-09-07 实测过这个坑：5558 只 × 3 个粒度、四个半小时、零写入 |
| **待重取前复权名单** | `RecordRangeFillForQfqRepair`，整个方法末尾 | ⚠ **静默的数据质量问题**：新补的那段用数据源当前基准、库里较新那段用旧基准，接缝处是假跳空（实测有票虚增 50%），名单没记下就没人知道要修 |
| **失败名单** | `FinishFetchRun`，末尾 | 这一轮失败的票不进待办 |

**一句话**：中断后数据不会半截错，但**修复线索会丢**。

## 3. 「区间」怎么表达：`FirstBackfill` + 窗口参数，**不加新模式**

`FetchMode` 现有语义：

- `FirstBackfill` = **不看水位线、只补缺的**，「整段」有多长**由各项自己的数据源决定**
  （K线从开市首日、分档资金流只有 120 个交易日）。

"补 2016~2022" 就是 **`FirstBackfill` 再加一个调用方指定的窗口**——语义上是把"整段"
从"数据源能给的全部"收窄成"这几年"，不是另一种行为。所以：

- **不加 `FetchMode.RangeBackfill`**。模式是会两两组合的，多一个就多一片要想清楚的格子。
- `TaskRunArgs` 加 `YearStart` / `YearEnd`（可空，null＝按各任务自己的"整段"）。
- 顺带加 `OverwriteQfq`（"不看本地已有什么、整段按当前基准重写"，只有前复权那一路吃）。

加法跟 `LookbackYears`/`Keywords` 那两次一样。⚠ `MainViewModel` 构造 `TaskRunArgs` 时
**按动作过滤**——2026-09-21 实机验证踩过：`Keywords` 给每个任务都传，于是每一项都打一句
"关键词格是空的"。

## 4. 分派器本身：**无状态**，跟【重新拉取失败】同款

```
FetchYearTask : FetchTaskBase<int>            // 自己不抓，只让出边界
  ├ 校验年份区间（沿用现有的钳制：A股开市首日、各数据源自己的起点）
  ├ 按固定顺序遍历 §2 的任务表
  │    └ 每个任务：ITaskRunner.RunAsync(id, args with { YearStart, YearEnd }, ...)
  │       跑完 yield 一次 → 这就是可停边界
  └ 收尾：汇总"哪几项补了多少、还剩什么"
```

**不记"跑到第几项"**。理由跟【重新拉取失败】不记一样：每个子任务的目标都是从库现算的，
重跑一个已经补完的子任务，它会把所有票都跳过、一个请求都不发。
显式游标只会带来"游标跟实际数据不一致"这一整类新的失效模式
（【板块指数合成】的 `BoardIndexState` 就是前车之鉴：一个维度就配了三条失效判据加四道保险）。

### 4.1 三样"丢修复线索"的东西自动消失

这是这个形状**白拿**的好处：

| 原来丢的 | 改后归谁 |
|---|---|
| `BarProbeFloor` 水位 | 各K线任务自己按批落（新框架里本来就是这么做的） |
| 失败名单 | 各任务自己按 `taskId` 记（09-13 拆分失败名单时就定了） |
| 待重取前复权名单 | 归**前复权任务的区间模式**——它知道自己刚补了哪些票的哪一段 |

### 4.2 数据源占用怎么办

调度侧按**计划项**登记占用（`SourceOccupancy`/`SourceAdmission`，见 `IFetchTask` 类注释：
"准入判断移出任务"）。`ITaskRunner.RunAsync` 直接建任务跑，**不重新登记**——
【重新拉取失败】现在就是这么干的，外层那一项拿着 `QuotaGroup.Mixed`，内层不再抢。
本项同样声明 Mixed，沿用即可。

⚠ `ITaskRunner.RunAsync` 现在的签名不带 `TaskRunArgs`（只有 actionId/progress/ct），
要加一个带 args 的重载。

## 5. 代价：丢掉"共享一次预取"

目录里 2026-09-02 的评估结论是"故意保持复合"，理由是：

> 各段共享同一次"每只标的本地最早是哪天"的预取，拆开的话每段都要把这几 GB 的库各扫一遍。

**这个形状确实会丢掉它**，得说清楚代价再决定：

- 每个K线类任务各做一次 `GetEarliestPeriodStartByCode`（全表 `GROUP BY`）。
  `SqliteBarRepository` 自己的注释记着："批量版是 GROUP BY 全表，2540 万行的库上要几十秒"。
- 涉及的任务约 7 个 → **几分钟量级**，对一轮 1.7 小时的活是个位数百分比。
- 而且这些任务**日常单独跑时本来就各做一次**，不是新增的代码路径，只是连着跑时重复了。

> **用户 2026-09-22 拍板：不实测，这点时间可以接受。**
> 也就是说 2026-09-02 那条"故意保持复合"的理由**到此作废**——当时它是拆不拆的决定因素，
> 现在用几分钟换掉"整段逻辑写第二份"的风险，换得过。
>
> 真要优化也是后话：把预取做成进程内缓存、由分派器开头预热、各任务命中。
> 那是**优化**，不该影响形状的选择。

## 7. 验证方案

⚠ 跑真源要 1.7 小时、几千个请求，**不能靠真跑来验**。

1. **离线模拟跑通全流程**：`BarSource: Mock` + `OfflineMock: true`，Debug 数据目录，
   零联网跑一遍完整分派，确认顺序、边界、进度与心跳都对。
2. **可停可续的实证**（核心收益，必须有）：跑到一半点【停止】，记下 `BarProbeFloor` 行数
   与待重取名单；重跑，确认 ①不重抓已有数据 ②水位和名单**没有回退**。
3. **等价验证**：同一个库拷贝各跑一遍老路与新路，比对 `Bar` 各粒度行数、`BarProbeFloor`、
   待重取名单、失败名单。
   ⚠ **假仓储验不到真 SQL**——新写的仓储方法都要配一条打在真 SQLite 上的测试
   （2026-09-21 在【板块指数合成】上栽过：2003 个测试全绿，真机第一次跑炸了 950 次）。
4. 全量单元测试。

③ 是主要工作量，但它**可以一个任务一个任务地做、各自独立验证、随时停**——
比"一次搬十一段"安全得多。这也是这个形状相对搬家的又一个好处。

### 10.2 迁移中补上/修掉的四件事

1. **退市股漏补（静默的回测幸存者偏差）**。`LocalStockCodes()` 走
   `SqliteStockMetaUpsert.GetAll`，而那个方法**只返回 `type='stock'`**（被 20 多处共用，
   混进别的类型会污染选股候选池，动不得）。照它取名册，区间回补会整批漏掉退市股，
   而老路专门有一段管这事。已改：整段回补那一路用 `GetByTypes(stock, delisted)`。
2. **老实现漏了【重算回测序列】**。老路末尾只重合成板块指数，但板块指数读的是 `day_adj`，
   而 `day_adj` 是拿不复权算的——不重算的话"历史变长了"这件事传不过去。分派表里补上了。
3. **后复权原来不能整段回补**（限死只有不复权可以）。判据 `RawBarCompletenessRule`
   比的是"两头都跟前复权比"，跟口径无关，后复权一样会卡在前面那几年。已放开。
4. **水位表接回来**（见 §11）。

## 11. 水位表：接回来了读，但**没有写**

`BarProbeFloor` 记的是"数据源确认这只标的在这天之前没有K线"。没有它，
"那些年还没上市"的票每轮都要重新试一遍——2026-09-07 实测一万六千个请求、四个半小时、写入为零。

迁移中一度**没人读它**（新框架的任务都不碰这张表）。已接回来：基类新增 `PlanGaps`，
走的是 Logic 层现成的 `YearGapCalculator`（老路用的同一个函数，**没有写第二份判据**）。
它一次做三件事：水位抬起点 / 本地已覆盖就跳过 / 缺口里没有交易日就跳过
（最后这条 2026-07-30 实测省掉 19 分钟、1150 个请求）。

⚠ **写入没有重建**。唯一的写入方是老路的 `RecordProbeFloors`，随这次删除一起没了。
后果不是错值——水位是**数据源的属性**、不是我们库的状态，已有的 17541 行永远成立，读它安全；
后果是这张表**不再长大**：新上市的标的、以后新探明的空区间不会被记下来，下次还要再试一遍。

补写入的话判据现成（`ProbeFloorPlanner`，有测试），落点在
`BarFetchTaskBase.FetchOneAsync`（那里知道"请求成功且返回 0 行"）。
**故意单独做**：它改的是所有K线任务共用的抓取路径，该单独验。
