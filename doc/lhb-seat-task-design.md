# 【龙虎榜席位】拆成独立任务 + 按日整日替换（2026-09-17）

承 `doc/block-trade-task-design.md` §7.9 留下的第二个同类问题。**但调研下来病因和修法跟大宗
不完全一样，§7.9 的判断要更正三处**，先摆在最前面。

---

## 0. 更正 §7.9：`seq` 不是东财给的，重复也不是主因

### 0.1 `seq` 早就是本地自赋的

§7.9 写「末列 `seq` 是东财给的序号、跨抓取会变」——不成立。
`EastMoneyLhbSeatProvider.AssignSeq` 从 2026-09-03 接入那天起就是本地算的：
按 `(日期, 代码, 买卖, 上榜原因)` 分组、组内**按净额降序**编 0..N，
而且那个方法的注释里已经写明了理由：「按净额而不是按接口返回顺序，是为了幂等」。

所以 §7.9 提议的「`seq` 由落库时自赋（按净额降序）」——**已经是现状**，改不动任何东西。

### 0.2 真正的病因：单次抓取内部的跨页重复

`seq` 虽然自赋，但它是**位次**——取值取决于「这一组里有几行」。
只要一次抓取里同一张榜多收了一行，整组的编号就会多出一位，
上一次落库的高位 `seq` 行就没人覆盖得掉，永久留在库里。

那么「同一张榜为什么会多收一行」？——**按月切片 + 非唯一排序键的跨页错位**：

```
sortColumns = TRADE_DATE,SECURITY_CODE     ← 一天一只股有 5~10 行，这个键远非唯一
月片一次查 13~60 页，offset 分页
⇒ 并列行在两次翻页之间被后端重新排序，同一行出现在两页上，另一行被整个跳过
```

这正是 `project_em_sort_key_must_be_unique` 记着的那个坑，只是这次它藏在 `seq` 后面。

### 0.3 重复只是一半，另一半是**遗漏**

跨页错位从来是成对的：多收一行 ⇔ 漏掉一行。实证（2026-09-17 沙箱出口实抓）：

| 交易日 | 接口 count | 库中行数 | 库内重复 | **接口有、库里没有** |
|---|---|---|---|---|
| 2021-05-26 | 494 | 494 | 2 | **2** |
| 2016-03-25 | 494 | 494 | 7 | **7** |
| 2017-09-12 | 590 | 590 | 1 | **1** |
| 2019-04-10 | 890 | 890 | 1 | **1** |
| 2020-01-22 | 887 | 887 | 1 | **1** |
| 2022-07-19 | 618 | 618 | 1 | **1** |
| 2025-08-27 | 881 | 881 | 1 | **1** |
| 2026-09-04 | 660 | 682 | 22 | 0 |
| 2018-06-15 / 2023-02-28 / 2024-02-07 / 2026-09-15 | — | — | 0 | 0 |

⚠ **`count` 校验抓不住这个病**：12 天里库中行数**全部等于**接口自报的 count，
内容却是「多一份副本、少一行真数据」。这跟大宗那轮的结论不同，直接影响验收判据的选择。

### 0.4 量级：46 行 → **3579 行**

§7.9 只数了「跨抓取批次」的重复（46 行），因为大宗的判据是「同批次内的同内容行是真实拆单」。
**那条判据对龙虎榜席位不成立**——同一张榜上同一个席位、买卖额分到分都一样的两行不是真实记录，
是跨页副本。按抓取时刻拆开看：

| 重复组的抓取时刻 | 组数 | 多出来的行 | 是什么 |
|---|---|---|---|
| 首尾同属 2026-09-03/04 那次全量 | 3228 | **3537** | **单次抓取内部**的跨页重复 ← 主体 |
| 2026-09-07/09/14/15 → 09-16 跨批次 | 36 | 46 | §7.9 数到的那些 |
| 合计 | 3267 | **3579** | 0.20% |

按交易日年份铺开是 2016~2026 **每年 200~460 组**，不是「只在 2026-09-01~09-04」。

### 0.5 结论：存量**不能**走离线模拟

大宗那轮能离线（§7.7），前提是「已证实没有遗漏，库里是真值的超集，副本删掉就是真值」。
龙虎榜席位不满足：**3579 行真数据根本不在库里**，本地怎么算也算不出来。

⇒ 存量只能**真抓一遍**。请求量见 §4。

## 1. 改按日抓本身就是修复

不是「按日抓 + count 校验兜底」，而是**按日抓之后页边界基本消失**：

| 单个「交易日 + 买卖侧」的页数（pageSize=500） | 日侧数 |
|---|---|
| 1 页（**没有页边界，跨页错位无从发生**） | 4941 |
| 2 页 | 257 |
| 3 / 5 / 7 页 | 6 |
| 合计 | 5204 |

实验证明（2021-05 买方榜，沙箱实抓）：

| 抓法 | 收到 | 去重后 | 内部重复 | 跟对方比 |
|---|---|---|---|---|
| 月片（13 页，旧排序键） | 6226 | 6212 | **14** | 月片独有 14 行 |
| **逐日**（18 天，每天 1 页） | 6226 | **6226** | **0** | 逐日独有 14 行 |

逐日抓到的那 14 行，正是月片漏掉的（样例：000983 的 2021-05-07 那张榜，
月片把「日涨幅偏离7%」那张榜的 3 行重复进来、把「连续三日累计20%」那张榜的 4 行挤掉了）。

**剩下 263 个多页日侧**再加两道保险：排序键加长（§2.3）+ count 校验（§2.2）。

## 2. 设计

模板照搬 `BlockTradeTask` / `BlockTradeDayWriter` / `PartialDayRepair`，只标出**差异**。

### 2.1 一批 = 一个交易日（买 + 卖两侧都收齐）

```
FetchAsync      → 逐交易日：买方榜翻完所有页 + 卖方榜翻完所有页 → 两侧都跟 count 对上 → yield 这一天
SaveBatchAsync  → 整日替换：DELETE WHERE trade_date=? + INSERT 本批（同一事务）
```

⚠ **差异点**：大宗一天一个接口，这里一天**两个接口**。只有一侧抓全的天**整天不落库**——
删掉一整天只写回买方，卖方就永久没了，而且行数判据只会觉得「那天本来就少」。

`seq` 仍由 `AssignSeq` 在整天收齐后自赋（不改），整日替换让它天然幂等。

### 2.2 count 校验

`EastMoneyDataCenterClient.QueryAsync` 的 `onTotalCount` 回调现成。买卖两侧各自核对。

⚠ 它**不是**这次的主保险（§0.3 已证 count 对得上内容也可能错），只兜「某页被限流截断」。

### 2.3 排序键加长

`TRADE_DATE,SECURITY_CODE` → `TRADE_DATE,SECURITY_CODE,NET,BUY,SELL,OPERATEDEPT_CODE`

只对剩下那 263 个多页日侧有意义。实抓验证过接口接受 6 列排序、结果与旧键一致
（2024-02-07 买方 3085 行 / 7 页，两种键各跑两遍，四份结果零差异）。

### 2.4 安全阀

`count == 0` 且库里那天已有行 → **不删**，记警告跳过。（同大宗 §3.2）

### 2.5 模式

| `FetchMode` | 抓哪些天 |
|---|---|
| `Incremental` | 库里最大日期 − 7 天 → 今天 |
| `SpecificDay` | 只抓 `args.Day`（⚠ 目录条目必须同时声明 `FetchActionParams.Date`） |
| `FirstBackfill` | 2016-01-04 → 今天（**存量清理就用它**） |
| `FillBacklog` | 返回空——界面那层在分派前就把它截给 orchestrator 了（大宗 §7.5② 同款） |

回看 7 天而不是大宗的 30 天：龙虎榜没有「事后才算的滞后字段」那类东西
（`rise_prob_3day` / `times_3day` 是席位的滚动统计、永远在变，回看多少天都追不平），
7 天只为兜住盘后陆续发布和交易所补录，代价 14 个请求。
整日替换是幂等的，这个数字随时可以调大。

`MaxItems` = 本轮最多抓几天、`Deadline` 到点收尾——5500 页的回补正需要这两个。
交易日历驱动，日历为空时退回按自然日（不猜，见 `project_trading_calendar_pitfall`）。

### 2.6 残缺日待办

接缝跟大宗**完全一样**：`LhbSeat` 已经在 `SqliteDailyTableAuditor` 里配了
`OwnerTaskId: RetryTaskIds.LhbSeat`，`DailyRefetcherFor` 里已有 LhbSeat 分支。
分支**保留**、内容换成共用的 `LhbSeatDayWriter`（大宗 §7.5① 的理由：两个调用方、
里面藏着「抓不全就不落库」那条规矩）。`PartialDayRepair` 直接复用，不改。

## 5. 存量清理

**只能真跑一次 `FirstBackfill`**（理由见 §0.5：离线补不回那 3579 行）。

动手前：单独备份 `LhbSeat` 一张表（178 万行，约 300MB；库本身 24GB 不整份复制）。

### 验收判据

⚠ **不能拿「行数不变」或「行数 == 逐日 count 之和」当判据**——现在库里行数**已经**等于
接口 count（§0.3），错的是内容。要看的是：

| 项 | 现状 | 期望 |
|---|---|---|
| **唯一指纹数** | 1777687 | **↑ 约 +3579 → ≈1781266** ← 主判据：副本换成了真行 |
| 总行数 | 1781266 | ≈ 不变 |
| 一张榜 ≥6 个席位的榜数 | 766 | **≈ 0**（真实多席位的榜极少）← **主证据** |
| ~~同榜同席位同金额的重复组~~ | ~~3267~~ | ~~**0**~~ **这条作废，见下** |
| 抽查日 vs 接口逐行 | 7/12 天有差 | **全部 0 差异** |

抽查日至少含 2021-05-26、2016-03-25、2021-05-07（已知缺行的那几天）。

### ⚠ 「同榜同席位同金额的重复组 → 0」这条判据作废（2026-09-17 回补中途实测）

回补跑到 2017-08 时中途验了一次已完成的 401 天，这条**没有归零**（644 → 328），
但查下去发现**剩下的那些是东财返回的真实内容，不是错位造成的重复**：

```
2016-01-05 300493 卖方榜（共 5 个席位）
   seq=0 国信证券深圳泰然九路      net=-225542
   seq=1 国信证券浙江分公司        net=-241000
   seq=2 机构专用                 net=-362544.96  ←
   seq=3 机构专用                 net=-362544.96  ←
   seq=4 机构专用                 net=-362544.96  ←
```

这张榜**总共就 5 个席位**，完全符合龙虎榜前五的规则。机构席位不披露具体营业部，
几家机构卖出同样金额就长这样——**同内容不等于重复**。

跨页错位造成的重复会让榜**超过 5 个席位**，所以真正的判据是上表里的
**「≥6 席位的榜数 → 0」**（实测 98 → 0，完全归零）。拿「同内容行」当判据会永远报假警报。

### 中途实测（401 天，2016-01-04 ~ 2017-08-23）

| 项 | 回补前 | 回补后 | |
|---|---|---|---|
| 行数 | 208507 | 208507 | 不变（删重复 + 补遗漏正好抵消）|
| **唯一指纹数** | 207705 | **208022** | **+317** ✅ |
| **≥6 席位的榜** | 98 | **0** | ✅ |
| 备份指纹丢失 | — | **0** | ✅ 没删真数据 |
| `seq` 连续性 | — | 0 张不合规 / 46030 | ✅ |

⚠ `seq` 的判据是 **`0..N-1`**（`AssignSeq` 从 0 编起），按 `1..N` 判会报出四万多张假不合规。

## 6. 测试

大宗那张表照搬，加 LhbSeat 特有的两条：

| 用例 | 锁住什么 |

## 8. 顺带：龙虎榜主表（`Lhb` / `StepLhb`）也迁（2026-09-17 用户定）

### 8.1 它**没有**席位表那个病——三道闸已经都在

| 项 | `LhbSeat`（病） | `Lhb`（没病） |
|---|---|---|
| 排序键 | `TRADE_DATE,SECURITY_CODE` ← 不唯一 | `TRADE_DATE,SECURITY_CODE,EXPLANATION` ← **已唯一** |
| 落库 | `INSERT OR REPLACE`，靠主键 | `ReplaceDays()` ← **已是整天替换** |
| 主键末列 | `seq`（位次） | `reason`（业务字段） |

`EastMoneyLhbProvider.QueryAsync` 的注释里已经把这个坑写得清清楚楚
（「键不唯一时同键行在页与页之间的先后不保证，**会既重复又丢行**」，个股题材表实测 1500 行里
重复 15 行同时丢 15 行）。**2026-09-09 换东财那轮它被修好了，2026-09-03 写的席位 provider 没跟上。**
这就是为什么同一张榜的两个表，一个干净一个脏。

⇒ 主表是**纯框架搬家**，不改抓取口径、不动数据。

### 8.2 但它有三条写入路径，口径不一致

| 入口 | 抓法 | 落库 | 派生偏离值 |
|---|---|---|---|
| 增量（`FetchLhbRangeAsync`） | 月片，31 交易日 ≈ 2~3 个请求 | `ReplaceDays` | **有** |
| 只抓某一天（`explicitDay`） | 单日 | `InsertOrIgnore` | **无** |
| 整段回补（`RunStepBackfillLhbAsync`） | 逐日 | `InsertOrIgnore` | **无** |
| 补残缺日（`DailyRefetcherFor`） | 单日 | `InsertOrIgnore` | **无** |

后三条写进去的新行 `deviation` 是空的，而增量路径会算。搬家时**统一到增量那条的口径**
（派生 + 整天替换），四个入口共用一个 `LhbDayWriter`。

⚠ 这是这次搬家里**唯一一处行为变化**，故意的：口径分叉本身就是要修的东西，
而且统一的方向是「向已经正确的那条看齐」。不统一的话新框架里会继续留着四份。

### 8.3 `LhbTask` 的形状

| `FetchMode` | 抓法 | 一批＝ |
|---|---|---|
| `Incremental` | 回看 31 个交易日（滞后字段 `d30_chg` 要 30 个交易日才有值），**按月切片** | 一个月片 |
| `SpecificDay` | 那一天，绕过空日名单 | 一天 |
| `FirstBackfill` | 2004-06-25 → 今天，按月切片（268 片） | 一个月片 |
| `FillBacklog` | 只补待办里欠着的残缺日（2026-09-18 收口，原先编排在 orchestrator） | 一天 |

⚠ 跟席位表的差异：**主表保留月片**，不改按日。理由是它本来就没有跨页错位的风险
（排序键已唯一），而月片让增量从 31 个请求降到 2~3 个。整天替换的粒度不受切片粒度影响——
`ReplaceDays` 按行里的日期整天替换，一个月片覆盖的是那个月的所有天。

空日名单（`IDailyFetchNoDataRepository.LhbDataset`）的判定逻辑原样搬：目标日里一行都没回来、
且早于 3 天前的，记进名单不再重试。

## 9. 实现记录（2026-09-17 落地时的偏差）

## 11. 中断文案按模式分岔（2026-09-18）

§10 那句错话真实地影响了一次决策——用户看到「下次从水位线接着走即可」才放心停掉了跑到
459/2603 的回补。**这不是措辞瑕疵，是把"进度会保留"这个不存在的保证说给了人听。**

### 怎么改的

`OnStoppedAsync(TaskRunStats)` 拿不到 `args`，而"中断之后怎么接着走"恰恰是按模式分岔的。
所以两个任务各加一个字段，在 `FetchAsync` 开头记下本轮模式：

```csharp
/// <summary>本轮跑的是哪个模式——OnStoppedAsync 拿不到 args，
/// 而"中断之后怎么接着走"恰恰是按模式分岔的。</summary>
private FetchMode _mode;
```

| 模式 | 中断时说什么 |
|---|---|
| `Incremental` / `SpecificDay` | 「下次从水位线接着走即可」（对它成立，整日替换幂等） |
| **`FirstBackfill`** | 「⚠ 但「整段回补」不看水位线，**进度不保留**：要补齐只能再跑一整遍（已修好的天会被再抓一次，结果不变）；改用「增量」补不上——它只从水位线往前回看 N 天，够不着中间没跑到的那段。」 |

`LhbSeatTask` 的 N=7、`BlockTradeTask` 的 N=30，都从各自的 `LookbackDays` 插值，不写死。

### 为什么两个任务都改

同一份逻辑的镜像（`BlockTradeTask` 是模板、`LhbSeatTask` 照抄的），
**各写一遍就会各改错一遍**——这正是当初抽 `BlockTradeDayWriter` / `PartialDayRepair` 的同一条理由。
所以两边都改、两边都锁测试。

### 测试

两个 `*TaskTests` 各加两条，`FakeFetcher` 加 `CancelAt`（抓到第 N 天时触发取消），
订阅 `OnProgress` 捕文本：

| 用例 | 断言 |
|---|---|
| `整段回补中断_要说清进度不保留` | 含「进度不保留」且**不含**「下次从水位线接着走」 |
| `增量中断_说从水位线接着走` | 反过来 |

**验过测试不是空跑**：把 `BlockTradeTask` 的判据临时改成恒假（等效退回旧行为），
`整段回补中断_要说清进度不保留` 立刻红，报的正是那句旧文案：

```
Assert.Contains() Failure: Sub-string not found
String:    "大宗交易中断。已落库的 1 天是完整的（每天整日替换、各自一个事务）。下次从水位线"···
Not found: "进度不保留"
```

全量 1691 条全绿。改动量：两个任务各 +13/−2 行，两个测试文件各约 +50 行。

⚠ **没有做的**：让整段回补真的支持断点续跑（记一个回补进度水位线）。
那是功能不是文案，要先出方案；现在只是**把话说准**，不是把进度保住。
