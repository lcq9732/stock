# 偿付能力充足率「整表成对取」设计方案

2026-10-23。改的是 `BankReportParser` 里保险两项偿付能力充足率的取值规则。
起因：中国平安 601318 四期报告的 `core_solvency` 全是空的，人工清单让人去翻，而正确的数
就印在报告里、程序也读得到。

---

## 一、现象与影响面

拿本地已下载的 5 家保险公司 × 4 期（共 20 份 PDF）跑产品代码 `BankReportParser.Default.Parse`，
`core_solvency` 缺失的有 **7 份**（另有 3 份是别的原因，见第七节）：

| 代码 | 公司 | 缺失的期 |
|---|---|---|
| 601318 | 中国平安 | 2024-12-31、2025-06-30、2025-12-31、2026-06-30（**四期全缺**） |
| 601601 | 中国太保 | 2024-12-31、2025-12-31 |
| 601628 | 中国人寿 | 2025-06-30 |

同期的 `comprehensive_solvency` **全部解析成功**，且值是对的。所以不是"读不出这份 PDF"，
是这一个指标被规则挡掉了。

## 二、根因：两条规则叠加

以 601318 的 2026 中报为证，把不同页分别喂给同一套扫描逻辑：

```
只喂 p85（集团偿付能力表）  → core=165.6  comp=198.1   ← 两个都对
只喂 p48（子公司偿付能力表）→ core=133.8  comp=185.5   ← 平安寿险口径
只喂 p15 + p85              → 只剩 comp=198.1，core 没了
喂全文                       → 只剩 comp=198.1@p15
```

1. **每个指标各取"第一次命中"**（`ScanAll` 里的 `seen`，BankReportParser.cs:692）。
   平安把「集团综合偿付能力充足率 198.1」提前印在 p15 的财务摘要页，而那一页**没有核心**
   那一行。于是综合锁死在 p15，核心继续往后找，先撞上 p48 的子公司横排表，取到平安寿险的 133.8。

2. **跨表保护 `DropCrossPageSolvency`**（BankReportParser.cs:741）。它发现核心(p48)和综合(p15)
   隔了 33 页，判定两者不是同一张表、口径对不上，于是**丢掉核心**。

保护本身是对的——133.8 是子公司数，入库就是错值，当初定的就是"宁可空着也不给错的"。
问题在于它**只会丢，不会回头去找那张两行俱全的表**：p85 的「集团偿付能力」表核心、综合
相邻两行、口径一致，但那时两个 key 都已被前面的页占了位，根本轮不到它。

## 三、判据选型（被淘汰的几个）

| 候选判据 | 为什么不行 |
|---|---|
| 放宽 `MaxPageGap` | 等于把 p48 的子公司数放进来，正是当初要防的那个错 |
| 认「集团偿付能力」标题 | 只有平安这么排版。太保/国寿/新华的正式表都没有"集团"字样，实测 15 份里只命中平安那 4 份 |
| 数一行里有几个数字（2 列 = 主体表，6 列 = 子公司横排表） | 太保的值是整数（190、256），列数判据在它身上退化；国寿附注里的整数版也是 2 列，分不开 |
| 取最靠后的那张表（附注里的详表） | 601318 2024 年报的 p324、601628 的 p66 都是附注里的**整数精度**版本（140 对 139.54），取了会掉精度 |

## 四、选定方案：用综合偿付能力当锚，整表配对

**核心观察**：摘要页的综合偿付能力是主体/集团口径（它是公司最想摆在前面的那个数），
现状已经**稳定取对**了 15/15 份。拿它当锚去全文找"同一页里综合等于锚值、且核心也在"的表，
那张表的核心就是配套的同口径数。

### 算法

在 `ScanAll` 末尾，把现在的 `DropCrossPageSolvency(result)` 换成 `ResolveSolvency(result, lines)`：

1. 取锚 `anchor` = 结果里的 `comprehensive_solvency`。**没有锚就原样退回** `DropCrossPageSolvency`，
   走今天的老路（这保证改动不会让任何现在能用的场景变差）。
2. 按页分组，对每一页调 `TryReadSolvencyPair`：只认行首 6 字内的「核心偿付能力充足率」和
   「综合偿付能力充足率」两个标签，各取第一次命中的值，取值复用现有的 `FirstNumberAfterStandard`。
   两个都拿到才算**成对页**。
3. 成对页过滤三道：
   - `|comp - anchor| ≤ 0.01` —— 同口径。容差卡得这么死是故意的：国寿 p66 的整数版 191
     与锚 190.94 差 0.06，正好被排除，保住 p20 的高精度值。
   - `core ≤ comp` —— 核心资本必然 ≤ 实际资本，这是定义决定的。脏页守门用。
   - `core` 落在现有合理区间 (30, 1000)。
4. 剩下的按页码升序取第一个，把它的 core **写入或替换** result 里的 `core_solvency`，
   `SourcePage` 记成那一页。
5. 一个都不剩 → 退回 `DropCrossPageSolvency`。

`comprehensive_solvency` 这一行**不动**（值本来就等于锚，改动面最小，也不惊动已经人工核对过的存量）。

### 为什么这比页距判据强

页距问的是"这两行离得近不近"，锚值问的是"这两行说的是不是同一个主体"。后者才是当初真正
要防的那件事——防的是"集团综合 + 寿险子公司核心"的混搭。配对成功时两个数同表同行相邻，
口径一致是结构保证的，不再依赖排版。

（`BankReportReparser`，一个网络请求都不发），把本地 160 个代码目录的 PDF 重解析一遍，

## 八、不在本次范围

- **601336 新华 2024 年报全空**（core 和 comp 都没解析出来）。这是**另一个真 bug，已定位**，
  跟配对规则无关：

  ```
  PdfPig  : 行数=64    页数=4    含「偿付能力充足率」0 行 → ScanAll 什么都没有
  poppler : 行数=8005  页数=291  含「偿付能力充足率」15 行 → core=124.07@p9, comp=217.55@p9
  ```

  这份 PDF 有 291 页，PdfPig 只读出 4 页 64 行——但**非空**，于是 `PdfLineExtractor` 认定
  "这条路成了"，poppler 兜底永远轮不到。兜底链的接受判据是"行数 > 0"，而不是"读得像不像样"。

  修法要点：接受判据得带上覆盖率（读到的页数 / PDF 总页数），低于阈值就继续试下一条路。
  按五层职责，这个阈值应该由调用方通过 `PdfExtractOptions` 给，组合器仍然只管排顺序。
  动手前先做一次全库统计——这个坑不限于保险，银行和券商的报告同样可能被 PdfPig 读残，
  得先知道面有多大。建议跟本方案同批修，但**分开两个提交**。
- **601319 中国人保**。它是「数字被转曲」的那一家（`LooksLikeDigitsStripped` 的注释里就记着），
  走 OCR 兜底。本方案的探测关掉了 OCR，所以上表没有它的数据——它的缺口跟配对规则无关。
