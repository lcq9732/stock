### 1.1 09-23 收尾：把迁移留下的死代码清掉

迁完的第二天做了一次死代码收敛。**七项迁走只是让它们没人调，本体还留在原地**——
按项目一贯做法（没有调用方的老实现要删，留着是留陷阱），这些得跟着清：

| 清掉的 | 为什么它死了 |
|---|---|
| `RunFetchIndexConsAsync` | 服务的【指数成分/权重】是退役项，09-22 那个 `case` 一删就没人调了 |
| `RunBackfillAmountTurnoverAsync` + `ReportBackfillProgress` | 2026-07-13 的一次性修复（补 newfqkline 换接口前入库的 amount/turnover 全 0 的日线），跑完就再没有调用方，界面上也从来没有入口 |
| `FinishFetchRun` | 老三种抓取模式共用的收尾。这件事现在由 `FetchTaskRegistry.RecordRun` 一处做掉 |
| `SetFailedTodo`／`ComputeUpdatedFailedCodes` | 两个都只是一行转发到 Logic 层的 `FailedTodoRule`，唯一调用方是 `FinishFetchRun` |
| `ReportCompareProgress` | 老K线内核的粗粒度心跳，随内核一起没了调用方 |
| `FetchStats` 类、`BeginStep`、`TaskLabel` | 只服务 `Steps.cs` 里的单项入口 |
| **`FetchOrchestrator.Steps.cs` 整个文件** | 见下 |

`Steps.cs` 的文件名是「【拉取全部】拆出来的单项入口」，而单项入口一个不剩了，
183 行里活代码只剩 `LocalStockCodes` 一个方法（`GetPendingMoneyFlowCount` 在用），
其余全是逐项的墓碑注释——而那些信息在各新任务类的注释和这份文档里都有。
把那个方法搬进主文件，文件删掉。

**顺带翻出一个静默的坑**：`FinishFetchRun` 是 `manifest.LastFetchAt`／`LastFetchKind`
唯一的写入方，删之前它就已经没有调用方了——也就是说**从最后一项迁走那天起，这两个字段就没人写了**。
而 `GetDataStatus` 还在读它们喂给【数据状态】页，于是界面上那句
「上次抓取：时刻（哪一项）」一直停在最后一次老路运行的陈旧值，
旁边的「最近任务运行」清单（读 `LastRunByTask`）却天天在变——**同一行里两个数对不上，一个错都不报**。

修法是让 `FetchTaskRegistry.RecordRun` 顺带写这两个字段：所有任务都从那儿过，一处写、54 项全覆盖。
三处（`LastRunByTask[name]`、`LastFetchAt`、`LastFetchKind`）**共用同一个 name 和同一个 now**，
两边就不可能再对不上。语义沿用老路：空转和失败的轮次照样记
（"刚检查过、没有新数据"本身就是一条有用的最后检查时间），逐项成败仍看 `LastRunByTask`。
用例在 `TaskRunRecordingTests`，实机也验过：跑一项之前那两个字段停在 09-22 11:43 的
「回填"无更早数据"水位」（最后一个走老路的项），跑完变成当天时刻 +「ETF指数映射」，
且与 `LastRunByTask` 里那条的时间戳完全相等。

这类"少写一处状态"的毛病，编译器、单元测试、界面都不会喊——只有在删掉最后一个写入方时才撞见。

- 界面里两个**不可达**的 case：【指数成分/权重】（已退役）、【拉取财务报表】（2026-09-10 起
  注册表分支就在 switch 之前，永远轮不到它）。

## 2. 新增的框架件

| 件 | 层 | 干什么 |
|---|---|---|
| `IFetchTaskDispatcher` | Scheduling | 任务调任务的口子。**收 `Action<IFetchTask>` 订阅回调**，不收 `IProgress<string>`——理由见 §3.1 |
| `FetchTaskBase.ForwardFrom` | Scheduling | 把子任务的事件**原样**转发出去 |
| `FetchTaskBase.ForwardStatus` | Scheduling | 订阅数据源的 `OnStatus`（限流退避/重试） |
| `BackfillWindowRule` | Logic | 把各任务自己的「整段」**收窄**到指定年份，只收窄永不放宽 |

## 3. 验证中翻出来的问题

⚠ **这一节是这份文档的重点**：下面每一条都是**单元测试测不出来的**——不是"没写测试"，
是它们的性质（多久没出声、请求发去了哪里、重跑会不会重抓）在单元测试里不存在。
发现它们的是**离线模拟跑整轮**，一共跑了 11 轮。

### 3.1 分派器把子任务事件压扁，丢掉了心跳（我引入的）

进度有两条通道：写日志的走 `IProgress<string>.Report`，只喂静默看门狗不写日志的走
`QuietWatchdog.IBeatOnlySink.BeatOnly`。第一版分派器把子任务的事件桥成 `IProgress<string>`
再转发，**Quiet 心跳在这一层被整条丢掉**。

后果：任何靠 `ReportQuiet` 喂狗的子任务（"一批很快、但要跑几百批"那类）在分派器下跑都显得是哑的。
实测【补全退市名单】探测 1342 只连哑 5 分 3 秒，整轮被看门狗掐断、**后面 8 项一项没跑**。

**修法（用户指出的）**：新框架本来就支持 Task 套 Task——任务只管发事件，外面**原样转发**即可
（注册表的 `RunAsync` 一直留着 `subscribe` 口子）。所以端口改成收订阅回调，
基类加 `ForwardFrom`。⚠ 不转发 `OnStateChanged`：外层的状态由骨架发，
把子任务的 Completed 也播出去，订阅方会以为外层这一轮做完了。

> 中间我走过一次弯路：先假设是 `ProgressSink` 没实现 `IBeatOnlySink`，去改了基类的 sink。
> 那是**在错的层打补丁**——框架没问题，是复合任务没做对。已撤回。

### 3.2 「不看水位线」被做成了「本地有了也重抓」

`FetchMode.FirstBackfill` 的语义是"不按'续到今天'那条线走"，但**已经有的那段仍然不该再抓**。
给资金净流入、后复权、不复权加这个模式时，三处都理解成了"所有票同一个窗口、全抓"。

实测：同样的区间连跑两轮，第二轮资金净流入**又写了 156 万行**、后复权/不复权各重抓 5995 只
写入 0 行。模拟源下只是慢一两分钟，**真源下资金净流入是 1 小时 45 分整轮白跑**。

后复权那次还多错一层：先在 100 年的大窗口里算缺口、**再**收窄，顺序反了——算出来的是
"区间之外那部分缺口"，收窄后仍非空。**必须先定窗口（含年份收窄）、再在这个窗口里判缺口。**

判据统一进 `BarFetchTaskBase.PlanGaps`（新增逐只窗口的重载），四路K线 + 资金净流入
走同一个 `YearGapCalculator`。

### 3.3 退市股在区间回补里被整批漏掉（静默的回测幸存者偏差）

`LocalStockCodes()` 走 `SqliteStockMetaUpsert.GetAll`，而那个方法**只返回 `type='stock'`**
（它被 20 多处共用，混进别的类型会污染选股候选池，动不得）。照它取名册，区间回补会整批漏掉退市股，
而老实现专门有一段管这事（`FetchDelistedForRangeAsync`，注释写明"消除回测幸存者偏差"）。

已改：整段回补那一路用 `GetByTypes(stock, delisted)`；日常增量不变（数据源早就不给退市股新数据了）。

### 3.4 离线开关有四个洞，验证时白发了约 750 个真请求

`App.xaml.cs` 里那段注释早就写着：

> 为什么是一个总开关而不是每类一个：验证要的是"这一轮一个真请求都不发"，**逐类去配必然漏**。

然后又漏了四处：`EtfRawBarTask` 和 `DelistedSupplementTask` 各自 `new TencentBarFetcher(...)`
硬写死、退市名单的 `CninfoStockListProvider` 硬写死、公告那两个 provider 根本**没有模拟实现**。

修法不是补这四处（那还是"逐类去配"），而是：
- 抽 `ProbeBars(concurrency)` 工厂放在总开关旁边，所有"不走 BarSource、自己拿一个K线取数器"
  的任务从它拿。现在 `App.xaml.cs` 里除了数据源清单本身，**没有第二处 `new TencentBarFetcher`**。
- 名单 provider 跟着开关走。
- 新写 `MockAnnouncementProvider`（一个类同时实现检索和详情两个接口）。

### 3.5 `DelistedSupplementTask` 只在"判定为已退市"时出声

它的探测循环有四条出路，另外三条（探测失败／从未上市／还在交易）一声不吭，
而每只都要发一个请求。候选里连着一批不是退市股，它就是全哑的。
**这是它自己的老 bug**，单独当计划项跑同样会被掐。已改成每只 `ReportQuiet` 一次
（喂狗、不写日志——几千行会把日志刷爆，而日志走 UI 线程）。

### 3.6 `BarProbeFloor` 一度只读不写

这张表记的是"数据源确认这只标的在这天之前没有K线"，没有它，"那些年还没上市"的票每轮都要
重新试一遍（2026-09-07 实测一万六千个请求、四个半小时、写入为零）。

唯一的写入方是老编排层的 `RecordProbeFloors`，随【拉取区间数据】整段删掉之后表就只读不写了。
已重建，而且**落点从"每阶段末"改成"每批"**——老实现是阶段末才落，中途停就整段丢。

⚠ 喂判据输入时**每只现查一次自己的最早日**，不用整轮缓存的快照：这一轮前面的批可能刚补进
更早的历史，拿旧快照会把水位记高，而记高了那只票的历史就**永久跳过且不报错**。

### 3.7 四个任务不订阅数据源的 `OnStatus`

资金净流入／融资余额／龙虎榜／大宗交易——它们都**已经是新框架任务**，不会随别的迁移自动补上。
后果：被限流退避时日志里一个字都没有，抓得慢看着就像卡住。
（大宗那个还多一层：实现类有 `OnStatus`，但**接口 `IBlockTradeDayFetcher` 没暴露**。）

### 3.8 日志自相矛盾 / 措辞错

- 资金净流入的 `Describe(mode)` 漏了 `FirstBackfill` 那一支，掉进兜底：同一轮里前一句报
  「整段回补，窗口 2024-01-01~12-31（不看水位线）」、后一句报「增量（按各自水位线续抓）」。
  数据是对的（5977 只 × 262 行正好是全年交易日数），但两句话说的是相反的事。
- 后复权/不复权先报「还差 5995 只」（全历史口径）、紧接着报「已经齐了」（收窄后的实际计划）。
  已改成报**这一轮真要抓的只数**。

## 4. 验证覆盖

**跑通了**：14 步分派全程零真请求、3 分钟；断点续有实证（重跑 32 秒，该跳的全跳）；
【重新拉取失败】的分派 + 事件转发；5 项本地维护各自的正常/空/失败路径。

**没验到的**：

- **跟老实现的等价对照**。老路已删，而删之前没做真机 A/B——顺序错了，
  当时应该先对照再删。只能靠"分派器本身不抓数据、14 步调的都是各自已在生产跑的任务"兜底。
- **【优化数据库】和【重解析已有PDF】的长耗时路径**。模拟环境里库是空的、没有缓存 PDF，
  两项都是 0 秒跑完。前者是全库唯一的"真·黑盒"（单条 `CREATE INDEX` 十几分钟、中间无法插进度），
  它的 liveness 播报只有真跑起来才看得出。
- **3.7 那四个任务的 `OnStatus`**：2026-09-23 补验了**通路**——离线模拟下
  资金净流入 20 行、融资余额 15 行、龙虎榜 8 行 `[模拟源] …` 都进了日志（改之前这些话全进黑洞）。
  大宗 0 行是预期：`MockBlockTradeProvider` 只声明事件不发话，真源有内容可发。
  ⚠ **真限流下的退避消息仍没验过**——那要真发请求才有，不该在用户机器上发。
  但限流器的话走的是同一个 `OnStatus`，通路已证。

  > 补验时踩了一下自己的坑：第一轮把这几项设成了「只补待办」模式，清单空就直接返回、根本没抓，
  > 日志里 0 行。那不是接线没生效，是**测试环境搭错了**。改成增量模式重跑才验到——
  > "没看到预期输出"要先怀疑自己的场景，别急着改产品代码。

### 4.1 这两条是模拟环境天然造不出来的

- **【优化数据库】的长耗时路径**要一个**没建过索引的大库**：生产库索引早建好了、跑起来也是秒完，
  空库更是 0 秒。造这个场景得复制 23.8 GB 再删索引。
- **【重解析已有PDF】**要本地有缓存的 PDF。

不是"忘了验"，是代价和风险都不小。真要验，得拿生产数据单独造一次场景。

## 5. 一条给下次的规矩

这一轮 8 类问题里，**没有一类是单元测试能发现的**。它们的共同点是：性质在时间维度或副作用维度上
——多久没出声、请求发去了哪里、重跑会不会重抓、心跳有没有穿过某一层。

所以**迁移完不等于做完**，离线模拟跑整轮是必须的一步，而且要：
1. 跑**两轮**（第二轮什么都不改），验重跑不重抓；
2. 事后**反查**日志里有没有真源痕迹，而不是只看模拟源出现过；
3. 长耗时的那几项，模拟环境要造得让它们真的跑起来（空库等于没验）。
