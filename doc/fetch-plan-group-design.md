# 抓取计划：给原子任务加一层「组」（设计稿，2026-09-02）

> 状态：**设计稿，未落地任何代码**。
> 前一份 [fetch-plan-atomic-tasks-design.md](fetch-plan-atomic-tasks-design.md) 把复合动作拆成了 26 个原子项，
> 这一份解决拆完之后"表太长、看不出哪些是一件事"的问题。

---

## 1. 问题：拆对了，但排版塌了

拆完之后计划页是 26 行平铺，每一行都自带一整套调度参数（启用 / 重复 / 不早于 / 模式 / 参数）。
实际情况是：

- 日常那 13 行的「重复」**全都是"每工作日"**，「不早于」**只有第一行填了 18:00**，其余 12 行是空的；
- 季度那几行的「重复」全都是"每月 1 号"；
- 于是 26 行里有 20 多个格子在重复同一件事，真正每行不同的只有"任务名 + 模式 + 参数"；
- 更要命的是**看不出结构**：扫一眼看不出"这 13 项是收盘后那一串"，得逐行读名字自己拼。

用户的原话是"感觉好乱了"，提案是：把复合项恢复成父任务、原子项作为子任务，
**父管触发时间，子管参数和顺序**。这个方向是对的，下面把它做实。

---

## 2. 底线：不能把拆分的好处还回去

分组之后必须仍然成立的五件事——它们正是当初拆的理由：

| 好处 | 分组后怎么保住 |
|---|---|
| 能挑着跑 | 子项各自有「启用」，也各自有【执行】按钮 |
| 一项失败不拖累其它项 | **执行单位仍是子项**，失败/跳过/重跑都按子项记录 |
| 顺序能自己排 | 组内子项可拖；组之间也可拖（整组移动） |
| 空闲窗口塞得进小任务 | 空闲调度挑的仍是**子项**，不是整组 |
| 耗时看得见 | 每个子项有自己的实测耗时；组头显示这一组的合计 |

**⇒ 一句话：组是「排期单位」，不是「执行单位」。**
它跟被我们退役掉的复合动作有本质区别——复合动作是一次不可干预的调用，
组只是"这几项共用一个开始时刻和重复规则"的写法。

---

## 3. 两个方案

### 方案 A：只在界面上分节（改动小）

数据结构不动，仍是一串独立项；给每个动作打一个"所属分类"标签，
表格用 `DataGrid.GroupStyle` 按标签分节显示，节头写一句"每日收盘后（13 项）"。

- 优点：改动极小，一天能落地，没有存储格式变更。
- 缺点：**只解决了"看不出结构"，没解决"20 多个格子在重复"**——每行照样摆着重复规则和时间框，
  用户提的"父管触发时间"实现不了。节头也没法折叠成一行。

### 方案 B：真父子模型（推荐）

计划从"一串项"变成"一串组，每组一串项"。**重复规则和触发时刻上移到组**，
子项只保留"启用 + 模式 + 参数 + 顺序"。

- 优点：正对痛点——折叠起来整个计划页只有 4 行；每行不同的东西才留在子项上。
- 缺点：存储格式变了（要迁移）、`PlanRunner` 的遍历要改成两层、界面从 DataGrid 换成分组视图。
- 代价可控的理由：调度语义本身**没变**（仍是按顺序、串行、子项粒度），改的是"时刻从哪儿取"。

下面按方案 B 展开。

---

## 4. 数据模型

```csharp
// 一组：共用触发时机的一串任务
sealed class FetchPlanGroup
{
    string Name;                 // 「每日收盘后」「季度定期」…（可改名）
    bool Enabled;                // 整组开关：没勾则整组不跑，哪怕子项勾着
    RepeatKind Repeat;           // 每工作日 / 每周 / 每月 / 仅一次 / 空闲时 / 手动
    DayOfWeek Weekday;           // Repeat=每周 时用
    int DayOfMonth;              // Repeat=每月 时用
    TimeOnly? NotBefore;         // 这一组不早于几点开始；null = 接着上一组跑
    bool Collapsed;              // 界面折叠状态（存起来，下次打开保持）
    List<FetchPlanItem> Items;   // 顺序即组内执行顺序
}

sealed class FetchPlan
{
    List<FetchPlanGroup> Groups; // 顺序即组间执行顺序
}
```

`FetchPlanItem` 相应**减负**：`Repeat`/`Weekday`/`DayOfMonth` 从子项上删掉（上移到组）；
`NotBefore` **保留**但改成"可选的组内锚点"，见 6.3。运行记录（LastStart/LastEnd/LastOutcome/
RecentDurationsSec）全部留在子项上——这是"执行单位是子项"的直接体现。

### 默认四组

| 组 | 重复 | 不早于 | 成员 |
|---|---|---|---|
| 每日收盘后 | 每工作日 | 18:00 | 13 个原子项 + 板块行情与成分（插在板块指数合成前） |
| 收尾重试 | 每工作日 | 21:00 | 重新拉取失败 |
| 季度定期 | 每月 1 号 | 09:00 | 行业分类 → 指数成分 → 指数权重 → ETF映射 → 股东 → 分红 |
| 空闲时补 | 空闲时 | — | 财务报表、重取前复权、重算回测序列 |
| 按需 | 手动 | — | 拉取区间数据、优化数据库、导入手工数据、监管指标、PDF重解析… |

折叠之后计划页就是 5 行。这比拆分前的 18 行还清爽，而展开任意一组就能看到里面每一步。

## 5. 调度语义（PlanRunner 怎么改）

现在的主循环是"在 Items 里按顺序找第一个该跑的项"。改成两层，**判定逻辑一条都不变**，
只是取值的来源从子项换成组：

```
for 每个组 (按组顺序):
    组没勾选 / 重复规则不落在今天 → 跳过整组
    组的开始时刻 = 组.NotBefore（null 则接着上一组）
    for 每个子项 (按组内顺序):
        子项没勾选 → 跳过
        这一期已经成功跑过 → 跳过        ← 仍按子项记录
        今天失败过 → 跳过（明天再试）     ← 仍按子项记录
        硬前置今天失败了 → 记一条跳过
        跑它
```

几条要点：

- **「已跑过/失败过」永远按子项判**。否则会退回"整组失败就整组重来"，把拆分白拆了。
- **空闲填充仍挑子项**：重复=「空闲时」的组，其成员参与空闲调度（每个子项自己的冷却、
  自己的"能不能只跑一部分"）。
- **时间轴**：组头显示"18:00 → 21:12（合计 3 小时 12 分）"，合计＝组内启用子项的实测耗时之和；
  展开后每个子项仍显示自己的预计时段。
- **一轮收尾**（排自动重试的那个时机）＝所有组都没有待跑项时，跟现在一致。

## 6. 三个边界情况

### 6.1 跨组依赖

【重算回测序列】在「空闲时补」组，它的硬前置【个股日K·不复权】在「每日收盘后」组。
**依赖按动作查，不按组查**——现在的 `DependsOn`/`SoftDependsOn` 是动作级的，天然跨组，不用改。

### 6.2 一个动作只能属于一个组

否则"这一项今天跑过没有"会有两个答案。界面上把某项拖进另一组＝从原组移走。
如果真需要同一个动作在两个时段各跑一次（例如白天补一次断档、晚上再跑一次），
那属于"同一动作两份配置"，超出这一版范围——需要时再给子项加一个"实例 id"。

### 6.3 子项要不要能自己设时间

保留一个**可选**的子项「不早于」，留空＝跟组走。有真实用例：
【龙虎榜】要等交易所当晚发布，可能比组的 18:00 更晚；
【重新拉取失败】要等 21:00。
语义是"在组的时刻之上再往后推"，只能更晚不能更早（更早没有意义，因为组内是串行的）。
界面上默认不显示这个框，点组头的"高级"才展开——不能让它变回"每行一个时间框"。

## 7. 迁移

`fetch-plan.json` 从"一串 Items"变成"一串 Groups"，要做一次结构迁移：

1. 目录里给每个动作标一个 `DefaultGroup`（每日 / 收尾 / 季度 / 空闲 / 按需）。
2. 读到老格式（顶层是 `Items`）时：按 `DefaultGroup` 把各项装进对应组，**组内保持原有的相对顺序**。
3. 组的重复规则和时刻：取该组里**第一个启用项**的 `Repeat` 和 `NotBefore`。
   组内其它项如果有不同的时刻，作为子项锚点保留（6.3）；重复规则不同的，
   按"重复规则决定它属于哪个组"重新归组（比如某项被用户改成了「空闲时」→ 进空闲组）。
4. 迁移完写回新格式，并在日志里逐组说明"哪几项归到了哪个组、时刻取自谁"。
5. 老格式**只读一次**，之后都是新格式。为防误判，迁移前把原文件备份成 `fetch-plan.bak.json`。

## 8. 界面

```
▾ ☑ 每日收盘后          每工作日  不早于 18:00     18:00 → 21:12（14 项，合计 3h12m）   [执行整组]
     1  ☑ 股票名册与流通市值    新浪列表      —              3分钟   ✔ 18:03 完成      [执行]
     2  ☑ 资金净流入            新浪          增量           30分钟  ✔ 18:33 完成      [执行]
     …
    14  ☑ 当日覆盖率体检        本地          —              2分钟   ▶ 执行中…         [执行]
▸ ☑ 收尾重试            每工作日  不早于 21:00     21:00 → 21:10（1 项）
▸ ☑ 季度定期            每月 1 号 不早于 09:00     下次 10-01（6 项）
▸ ☑ 空闲时补            空闲时                     空档里自动补（3 项）
▸ ☐ 按需                手动                       （5 项，不会自动跑）
```

- 组头承载：折叠箭头、整组启用、重复规则、不早于、组的时间轴/状态、【执行整组】。
- 子行承载：序号、启用、任务名（带 ⓘ 说明）、数据源、模式、参数、预计、状态、【执行】。
  **子行不再有重复规则和时间框**（除非展开"高级"）。
- 拖动：组头拖动＝整组移动；子行拖动＝组内换位，拖到别的组头上＝转组。
- 折叠状态存进 json，下次打开保持。

实现上 `DataGrid` 做嵌套比较别扭，建议换成 `ItemsControl`（组）+ 内层 `DataGrid`/`ItemsControl`（子项），
或者用 `TreeView` + 自定义 `ItemTemplate`。这是这一版里最花时间的部分。

## 10. 取舍与风险

- **不要让组重新变成执行单位**。一旦有人写出"整组失败就整组标失败"，
  拆分的全部收益（失败隔离、空闲填充、细粒度重跑）就没了。这条要写进 `PlanRunner` 的类注释。
- **组不是数据源分组**。按数据源分组听起来很整齐，但用户排计划时想的是"什么时候跑"，
  不是"跟谁抢配额"——配额那件事由串行执行本身兜住了（`QuotaGroup` 字段仍只作提示）。
- **迁移只有一次机会**：老格式读错就等于用户排的计划丢了。所以迁移前备份，
  并且迁移逻辑要有单元测试覆盖"用户改过时刻/改过重复规则/加过自定义顺序"这几种真实情况。
- 如果嫌阶段 3 太重，可以先落地方案 A（纯 UI 分节）作为过渡——但要清楚它解决不了
  "每行都摆着重复规则和时间框"这个真正的噪音源。
