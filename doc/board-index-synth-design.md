# 【板块指数合成】· 设计方案

2026-09-21 起草。

---

## 0. 先纠正一个前提

我在上一轮反复说"它单事务写 468 万行，是已知的 WAL 炸弹，值得单独开题"。**这个说法是错的**，
而且代码里 2026-09-12 就已经改正过了（`SynthesizeBoardIndexCore` 的注释）：

> （当时记的"单事务写 468 万行"是误判：这个循环一直是一个板块一个事务。）

2026-09-11 那次 WAL 涨到 162 GB 的真实成因是：**一个残留进程握着库两个多小时**，而 SQLite 的
autocheckpoint 是**被动**的——只要有任何读连接活着就跳过，于是这一轮的 468 万行全堆在 WAL 里。
同日已经在这一项末尾加了主动回收（`SqliteMaintenance.CheckpointWalAndDescribe`），拿到 busy
会明确报出来，那正是"有人握着库"的唯一早期信号。

所以"为 WAL 炸弹单独开题"这个理由不成立。下面是重新评估之后**真正**剩下的东西。

---

## 1. 重新评估：两件事，价值差很多

### (A) 迁到新任务框架 —— 机械、低风险、收益**比前七项都小**

它已经具备新框架想给的大部分东西：

| 新框架的好处 | 它现在的状态 |
|---|---|
| 批边界收尾 | 落库已经是**一个板块一个事务**，边界现成 |
| 判据在 Logic | `BoardIndexSynthesizer` 本来就是 Logic 层纯函数、有真库验证 |
| 统一心跳 | 已有 `ProgressThrottle` 按**时间**报（板块之间成分股数差一个量级，按个数报会哑到 2 分 35 秒） |
| 自己补待办 | 它没有待办（`RetryTaskIds` 里没有它） |

真正新增的只有：`MaxItems`/`Deadline` 能在板块边界干净收尾，以及编排器再瘦一块（约 60 行）。
这一项估时 3 分钟，收尾能力的价值有限。

### (B) 增量合成 —— 这才是真问题

它**每轮全量重算**：950 个板块 × 约 4,900 根 ≈ **468 万行，每个工作日重写一遍**。
而真正变化的，通常只有**最新那一天的一根**。

---

## 2. (B) 的正确性分析：什么时候能增量、什么时候必须整段重算

指数是**路径依赖**的：每天的指数涨幅 = 当天有数据的成分股各自 `(今收/昨收−1)` 的均值，
从基点 1000 累乘（见 `BoardIndexSynthesizer`）。所以：

**能增量的那一半**：追加一天只需要"上一根 close × (1 + 当天成分股平均涨幅)"——
前面的历史一个字都不用动。

**历史会整体失效的三种情况**：

| 失效来源 | 为什么 | 怎么发现 |
|---|---|---|
| ① **成分股名单变了** | 历史每一天的"平均涨幅"都是按当前名单算的，名单一变整条历史都变 | 存一份名单指纹（排序后哈希），比一下 |
| ② **成分股的 `day_adj` 被重算** | 【重算回测序列】会重写因子，历史收益率跟着变 | 那一项跑完落一个"指数需全量重算"的标记 |
| ③ **某只成分股补上了以前缺的日子** | 那几天的均值变了 | 比"库里该板块成分股的 `day_adj` 最早日期"有没有往前挪 |

**判据**（给每个板块存一条合成状态：名单指纹 + 最后一根日期 + 成分最早日期）：

```
指纹变了 或 有全量标记 或 成分最早日期往前挪了  → 整段重算
否则                                          → 只追加 [最后一根+1, 今天]
```

**代价**：一张小表（950 行）或 manifest 里一份字典。
**收益**：468 万行/天 → **约 950 行/天**（每个板块一根）。3 分钟 → 几秒。

⚠ 增量那条路**必须留一条兜底的全量入口**（模式选「首次整段回补」就整轮重算），
否则判据万一漏了某种失效来源，错的历史会一直留着——这一项的输出没有任何别的地方会校验。

---

## 3. 分两步

| 步 | 内容 | 风险 |
|---|---|---|
| ⑧-1 | 迁到新框架（一批＝一个板块，行为一字不改） | 低 |
| ⑧-2 | 增量合成（指纹表 + 重算触发 + 全量兜底模式） | **中**——判据漏一种失效来源就是静默的错值 |

⑧-1 先做，它跟 ⑧-2 不冲突，而且做完之后 ⑧-2 改的是一个 200 行的任务类、不是 3,000 行的编排器。

---

## 4. 要拍板的一条

**⑧-2 做不做？** 它是这一项唯一有实质价值的改动（每天少写 468 万行），但它把一个
"每次全量重算、所以永远不会错"的任务变成"靠判据决定要不要重算"——而这一项的输出
**没有任何别的地方会校验**（板块指数只有本地这一份，没有官方值可对）。

我的看法：值得做，但要配两样东西——①「首次整段回补」模式作为全量兜底；
② 【重算回测序列】跑完自动置标记。两样都做了，风险就落在"名单指纹算错"这一个点上，
而那个点可以单测。

---

## 5. 落地与真机验证（2026-09-21）

两步都已落地。验证在**生产库的拷贝**上做（23.8 GB，1031 个板块、555 万根板块指数日K），
共跑了四轮，每轮都是产品代码走完整计划链路。

### 5.1 效果

| 轮次 | 做了什么 | 结果 | 耗时 |
|---|---|---|---|
| ① 全量（建状态） | 整段重算 1031 | 写 5,554,079 根 | **40 分钟** |
| ② 增量（第一次） | 判据对，SQL 错 → 见 5.2 | 写 0 根、950 条错误 | 15 秒 |
| ②b 全量（重建状态） | 整段重算 1031 | 写 5,554,079 根，**跟①逐根一致的行数** | 38 分钟 |
| ③④ 增量（等价验证） | 整段重算 81、**只追加 950** | 写 1,200 / 1,800 根 | **各 19 秒** |

那 81 个「整段重算」是**从来没合成出K线的板块**（成分股数据不够，本来就没状态），
每轮产出 0 根——不是判据判错。

**每个工作日的成本：468 万行 / 40 分钟 → 约 1000 行 / 19 秒。**

### 5.2 ② 暴露的真 bug：`QueryForAppend` 的 SQL 根本执行不了

```
错误：板块「半导体」(BK1036) 合成失败：SQLite Error 1:
      'ORDER BY clause should come after UNION ALL not before'.   × 950
```

判据是对的（950 个板块正确判成「只追加」），但取基准那条 SQL 写错了——SQLite 不允许
`UNION ALL` 的分支自带 `ORDER BY`/`LIMIT`，第一段必须套进子查询。

⚠ **根因不是这行 SQL，是测试形状错了**：`BoardIndexAppendEquivalenceTests` 里的
`FakeBars.QueryForAppend` 是照接口约定用 LINQ 实现的，等价性验得很漂亮，
但**真 SQL 一行都没执行过**。2003 个单元测试全绿，真机第一次跑就炸 950 次。

> **规矩**：仓储方法的行为约定，必须有一条**打在真 SQLite 上**的测试；
> 假仓储只用来测调用方的逻辑。已补 `SqliteBarRepositoryAppendTests`（8 条，
> 含"基准在两年半前的长期停牌票"）——这组在修之前必然红。

失败模式本身是**安全**的：950 个板块响亮报错 → `States.Invalidate` 作废状态 →
下一轮自动退回全量。事后查库：`BoardIndexState` 清零、`Bar` 里 5,554,079 根**一根没少**。

### 5.3 ③④ 「追加 == 全量」在真数据上的等价验证

单元测试里的等价性是拿 6 只造出来的假票验的。真机上再验一遍：

1. 挑 150 个板块（**刻意覆盖两端**：成分股数 5 ~ 3870，中位 45）；
2. 快照它们最后 8 根（第④轮 12 根）指数日K，删掉，把 `BoardIndexState.last_bar_date` 往回拨——
   状态必须跟库里对得上，否则判据会判 Full，那就验不到追加那条路；
3. 跑增量，让产品代码把这几天**用追加的方式**重算出来；
4. 逐根比 `open/high/low/close/volume/amount/turnover`。

```
③ 逐根比对 150 个板块 × 共 1200 根 × 7 个字段：一致 150、不一致 0、最大相对偏差 0.000e+00
④ 逐根比对 150 个板块 × 共 1800 根 × 7 个字段：一致 150、不一致 0、最大相对偏差 0.000e+00
⑤ 逐根比对 200 个板块 × 共 1000 根 × 7 个字段：一致 200、不一致 0、最大相对偏差 0.000e+00
```

**不是"误差在容忍范围内"，是逐位相同。** 写入根数也精确对上（150×8=1200、150×12=1800）。

### 5.4 附带查清的一件事：短跑收尾时 WAL 回收报 busy

增量之后一轮只跑 19 秒，于是**每轮收尾都报**「WAL 没能回收……有别的连接握着这个库」
（WAL 剩 9~12 MB）；而 38~40 分钟的全量轮从来不报。

**真凶是界面自己的全表扫描。** `MainViewModel.RefreshFailedCodeCount` 要对 `Bar` 做六遍
全表 `GROUP BY`（其中两遍按 `fetched_at`，`Bar` 上没有任何索引覆盖它），25 GB 库上要好几分钟，
而它在**程序启动时**和**每项任务跑完后**各跑一轮。短任务收尾时它还卡在 `ExecuteReader` 里，
长任务收尾时它早跑完了——时间差就是这么来的。

排查中错过一次：先假设是本进程的**空闲连接池**，加了 `ClearAllPools()` 再重试——真机上
busy 依旧。那种连接是**正在用**的，根本不在池里。（这条重试留下了，但只在真要报警前才做。）

**改法**：判据从「busy 就报」改成「**busy 且 WAL 已经大到该管了（≥64 MB）才报**」。
理由是 2026-09-10 那次事故的特征不是"某一轮 busy"，而是"**一轮比一轮大、一直涨到 162GB**"——
盯大小才盯得住它，盯 busy 只会每天误报一次、把用户支去关一堆根本没开的程序。

测试相应重写（`WalCheckpointTests`）：`busy` 原始值仍要如实返回；**busy + WAL 小 ⇒ 不报**；
**busy + WAL 撑过 64 MB ⇒ 必须报**（测试里真的把 WAL 灌到 80 MB，没有为了好测把阈值做成可注入的）。

第五轮真机复验：日志干净，告警消失，追加结果照旧逐位一致。
