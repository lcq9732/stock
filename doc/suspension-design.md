# 停复牌数据（2026-09-30）

## 0. 为什么要

体检只能看到"那天没有日K"，分不出是**停牌**还是**漏抓**：

- 【当日完整性体检】把当天没日线的票一律记成待办。停牌股天天挂在【重新拉取失败】名单里、半夜白抓一轮
  （2026-09-29 的 300527、600293、600363 就是这样；sh563830 那天却不是停牌——混在一起就看不出谁是真漏）。
- 【全库数据体检】的历史空洞要白补两轮，才被判"数据源确实没有"、进白名单。

交易所官网公布停复牌记录，是第一手来源。拿它**解释缺口**：全天停牌的日子不再记成待办。

## 1. 来源（2026-09-30 沙箱实测）

| | 上交所·股票 | 上交所·基金 | 深交所 |
|---|---|---|---|
| 接口 | `query.sse.com.cn/commonSoaQuery.do?sqlId=GW_PL_JYTS_TFPXX` | `query.sse.com.cn/sseQuery/commonSoaQuery.do?sqlId=SSE_PL_JYTS_TFPXX_JJ` | `szse.cn/api/report/ShowReport?SHOWTYPE=xlsx&CATALOGID=1798` |
| 查询 | `startStopDate`/`endStopDate`（**yyyyMMdd**），返回与区间**有交集**的全部停牌 | `startDate`/`endDate`，同左 | `txtKsrq`/`txtZzrq`（yyyy-MM-dd） |
| 分页 | pageSize 给 1000 照给，超了看 `pageHelp.total` 翻页 | 同左 | xlsx 不分页；JSON 接口固定每页 10 条（不用） |
| 最早 | 2010 年（2005-01 空） | 同左 | 2008 年（2004-01 空） |
| 坑 | 出错时整包在 `(...)` 里、`success:"false"`；要 Referer | 字段名不同（secCode/startStopType） | **不给区间整表导出截断在 65,536 行**；空月份返回只有表头的 xlsx |

三路都按**自然月**问，一个月一个请求。

**取到的全存**（2026-09-30 用户定）：股票、ETF、债券、可转债、LOF、B 股每一行都留，接口的每一列都有对应字段（上交所股票 9 列、基金 13 列、深交所 6 列）。体检按 Bar 代码查，没有日K的品种自然查不到；以后要用（比如可转债停牌）或要核对，不用再回官网重抓。最初版按名册过滤、只存 9 列里判据要用的几列，当天改掉了。

## 2. 哪天算"全天停牌"——逐日比对定的

判据：`Logic/Services/SuspensionRule.FullDays`。拿官网记录跟本地 `day_raw` 逐日比对：

### 上交所（股票、基金同一套）

- `LXTP` 连续停牌，或 `stopTime=WH`（临时停牌·全天）：`[开始日, 结束日]` **两头都含**。
- 其余 `stopTime`（915、13、AM、PM）是盘中停一段，不算。
- 2010~2025 每年 1、7 月抽样：判为全天停牌的 **8.7 万天，没有一天有日K**。盘中停那类 2015/16 年有 57 天没日K——
  不算停牌的后果只是照旧进待办，不会误判。

### 深交所（2007~2026 全量 28 万天，对不上 2 天）

- 全天停的日子 = `[生效起点, 复牌日)`：停牌时刻是「开市」（或 09:30 前）当天就算，盘中才停的从次日起；**复牌日当天有交易**。
  「1小时」「半天」「盘中临时停牌」自然算出 0 天。
- 「取消停牌 / 今起复牌 / 复牌 / 取消特停 / 今起恢复交易」是**复牌记录**。老数据的日期可能写在**停牌时间**那一列（300332 在 2016-10-26）。
- 没写复牌时刻的停牌（长期停牌、特停），终点取最早的：之后第一条复牌记录、之后第一条别的停牌事件
  （000016 在 2008-03-12 特停、次日来一条「1小时」＝只停了一天）、**本地停牌后第一根日K**。
- 同一天叠两条按天取并集（159561 在 2025-01-24）。

### 为什么敢拿"本地停牌后第一根日K"当终点

官网有**开了头没收尾**的记录：000656 在 2017-07-19 记了一条停牌，下一条复牌记录在 2023 年，中间六年天天有成交。
不截断的话这六年全被当成停牌。而这份数据**只用来解释缺口**——停牌后一旦出现日K，之后的日子本来就不归这条记录解释。

⚠ 验证的诚实说明：用日K截断的那部分，对账时有循环成分；真正独立的验证是"写明了起止 / 配上了复牌记录"的那些，
在加截断之前 2024~2026 年就是零误判。

### 深交所 2007-11 以前的记录没有日期（入库比取回少约 1.2 万条，是已知的、不修）

2026-09-30 首次整段回补：深交所取回 70,756 条、入库 58,730 条。差额全是**停牌时间、复牌时间都为空**的老记录——
它们全部排在导出最末尾（最早一条带日期的是 2007-11-02），简称多是「G 康佳Ａ」「S ST…」这类 2005~2006 股改时期的写法。
没有日期时键只剩"代码+期限"，同一只票的几条撞成一个、后写的覆盖前面的。

查过之后决定**不修**（用户同意）：
- 全量导出里被覆盖的 7,244 行，3,080 行跟留下的那条一字不差（纯重复）；其余 4,164 行只是简称或原因不同；
- 没有任何日期，对不上哪一天，判据本来就跳过它们，也没法拿日K核对真假；
- 深交所能用的停复牌数据实际从 2007-11 起，这一段一条没丢。

上交所取回 > 入库是另一回事：它按"与这个月有交集"返回，长期停牌在好几个月里重复出现，按键去重是对的。

## 3. 分层

| 层 | 类 |
|---|---|
| Logic | `SuspensionRow`（模型，按接口原样）、`ISuspensionProvider` / `ISuspensionRepository`、`SuspensionRule`（判据）、`SuspensionFetchPlan`（问哪些月） |
| Remote | `SseStockSuspensionProvider` / `SseFundSuspensionProvider`（共用 `SseSuspensionProviderBase`）、`SzseSuspensionProvider` |
| Sqlite | `Suspension` / `SuspensionFetchMonth` 两张表、`SqliteSuspensionRepository`、`SqliteSuspensionLookup`（给一批 Bar 代码查全天停牌日，两个体检共用） |
| Tasks | `SuspensionTask`（【停复牌】，一路接口一个月一批落库） |
| Scheduling | `FetchActionId.StepSuspension`，日更组、排在【当日完整性体检】之前 |

**按接口原样存、不展开成按天**：深交所长期停牌的「停牌」和「复牌」常隔好几个月，抓一个月的时候配不上对。

**UPSERT 的键不含结束日**：上交所还在停牌的记录复牌后才补上结束日。键含结束日的话，那条"没有结束日"的旧行永远留着，
这只票就一直被判成还在停牌。

## 4. 抓取节奏

- 「日常增量」：没问过的月份 + **最近两个月每轮重问**（还在停牌的复牌后才补结束日；深交所复牌记录记在复牌那个月）。平时每天 6 个请求。
- 「首次整段回补」：从 2004-01 起每个月重问，三路共约 800 个请求、1 秒一个，十几分钟。一个月一批落库，停在哪都不丢。
- 一路出错不连累另外两路；有一路出错整项报失败（绿勾会盖住"那一路今天没取到"）。

## 5. 谁在用

- **【当日完整性体检】**（`SqliteDayCompletenessAuditor.CheckBars`）：个股三口径、ETF 两条线当天缺日线的，全天停牌的剔出待办，
  汇总写"（N 只停牌）"。指数不查。
- **【全库数据体检】**（`FullAuditTask.ScanScope`）：历史空洞里全天停牌的日子扣掉，扣完为空就不进名单，
  汇总写"另有 N 只共 M 天是官网记载的全天停牌"。
- 停复牌表空着 / 查询出错 ＝ "不知道谁停牌"，行为跟没有这个功能时一样。
