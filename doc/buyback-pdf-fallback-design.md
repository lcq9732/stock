# 回购公告正文：东财取不到时退回巨潮 PDF 设计方案

2026-10-22 · 状态：方案待确认，未写代码

## 1. 起因

【回购公告进展】的正文全靠东财公告接口（`np-anotice` 找 art_code → `np-cnotice` 取纯文本）。
10-22 08:28 那轮 10 条全部 `connection forcibly closed by the remote host`，提前收工——东财一限流，
这一项就整天拿不到数值（累计股数/金额、价格区间）。

官方渠道是巨潮：搜索那一步本来就走巨潮，每条命中都带 PDF 原件链接
（`http://static.cninfo.com.cn/finalpage/…PDF`，库里 `source_url` 列 2627 条全有），只是没用来取正文。
回购进展公告一般一两页，项目里已有 `StockPlatform.Pdf.PdfLineExtractor`（PdfPig，读不动退 pdftotext）。

东财 APP 本地缓存只有标题、只覆盖看过的票，不可用（10-22 查过）。

## 2. 结论

新增巨潮 PDF 这条正文通道，**东财取不到时自动退回它**。先离线比对证明两条通道抽出来的数值一致，再上线。

## 3. 改动

### 3.1 新数据源类（`StockPlatform.Data/Remote`，照"一个数据源一个类"的规矩）

- `CninfoPdfAnnouncementDetailFetcher`：按 PDF 链接下载 → `PdfLineExtractor` 取文字行 → 拼成正文。
  - 自带限速器（单并发、1 秒间隔），跟东财那条互不牵连；`static.cninfo.com.cn` 是静态文件服务。
  - PDF 不落盘（不像监管指标要留着重解析），内存里解析完就丢。
  - 返回的 `ArtCode` 记成 `cninfo:<公告ID>`（从 URL 末段取），这样"已取到正文"的判据
    （`GetFetchedKeys` / `GetMissingDetail` 看 `art_code` 非空）不用改，日志和库里也分得出正文是从哪来的。
- 接口：现有 `IAnnouncementDetailFetcher.FetchDetailAsync(code, title, date)` 拿不到 PDF 链接。
  加一个可选参数 `pdfUrl`（默认 null）——东财那条忽略它，巨潮那条只用它。调用方传 `hit.PdfUrl` / `old.SourceUrl`。

### 3.2 组合类：先东财、不行再巨潮

- `FallbackAnnouncementDetailFetcher(primary, secondary)`：
  - 东财**抛异常**（网络/限流）→ 用巨潮；
  - 东财**返回 null**（在该股最近 100 条公告里没匹配上）→ 也用巨潮——这正是首轮只能回看 90 天、
    以及那批"标题全角括号配不上"空壳的根因，PDF 链接直接来自搜索结果，不需要匹配；
  - 东财成功就不碰巨潮，请求量不变。
- 东财一旦连续失败（同一轮里连着 3 次抛异常），本轮后面的直接走巨潮，不再每条先撞一次东财——
  省掉每条 12 秒超时 + 两次重试的等待。
- 【回购公告进展】的"连续 10 条失败就收工"改成**两条都失败**才算一次失败。

### 3.3 配置开关（`fetcher-settings.json`，JSONC 自带说明，照抄去掉 `//` 就能用）

```
//"AnnouncementDetailSource": "eastmoney",           // 只用东财（改之前的行为）
//"AnnouncementDetailSource": "eastmoney+cninfo",    // 东财优先，取不到退回巨潮 PDF【比对通过后的默认】
//"AnnouncementDetailSource": "cninfo",              // 只用巨潮 PDF
```

### 3.4 范围

- **只给【回购公告进展】接上**。【中标/订单公告】也用同一个东财正文通道，但它抽的是订单金额，
  PDF 文字能不能抽对要单独比对；这次装配时给它的仍是纯东财，不动。
- `PlanAnnouncementExtractor` 原则上不改；比对发现 PDF 文字的排版（换行切断数字、表格列串行）让它抽错时，
  先在**拼正文那一步**做归一化（去掉行内换行、全角转半角），尽量不碰抽取规则本身。

## 4. 比对：样本怎么取

### 4.1 基准

库里 2614 条有东财正文（`art_code` 非空）的回购公告，抽取结果就在行里（东财正文本身没存）。
每条都有巨潮 PDF 链接。比对＝用 PDF 正文重抽一遍，跟库里那一行逐字段对。

### 4.2 抽样（共约 300 条）

按阶段分层，每层再按交易所（沪/深/北）和月份摊开，避免全是同一种格式：

| 阶段 | 库里（有东财正文） | 其中有数值的 | 抽样 |
|---|---|---|---|
| 进展 | 1411 | 累计金额 955 | 100 |
| 方案 | 556 | 资金区间 491 | 60 |
| 首次回购 | 374 | 累计金额 249 | 60 |
| 完毕 | 227 | 累计金额 132 | 40 |
| 达标 | 38 | 20 | 20 |
| 终止 | 8 | 5 | 全部 8 |

每层里**有数值的和没数值的都要抽**：后者是东财抽不出来的，正好看 PDF 能不能抽出来（可能更好，也可能是公告本来就没有）。
另加 10 条已知难样本：标题带「（修订版）」的、全角括号的、北交所的、B 股的。

### 4.3 比对字段与判定

逐字段：`as_of_date`、`cum_shares`、`cum_amount`、`price_low`、`price_high`、`pct_of_capital`、
`plan_cap_price`、`plan_amount_low`、`plan_amount_high`（`stage` 只看标题，两边必然一致，不比）。

- 数值相等（容差 1e-6）才算一致；一边有值一边 null 算不一致。
- **每一条不一致都要逐条看原文定性**：PDF 抽错（改归一化再比）/ 东财抽错（记下来，说明 PDF 更好）/
  两边都对但口径不同（比如万元/元）。没解释清楚的差异不上线。
- 上线门槛：PDF 抽错的为 0；东财有值、PDF 抽不出的不超过 1%，且逐条说明原因。

### 4.4 在哪跑、发多少请求

- 300 个 PDF 下载，单并发 1 秒间隔，约 5–6 分钟，打 `static.cninfo.com.cn`，不碰东财。
- **要在本机跑**（PDF 解析要本机的 pdftotext），所以要等你说抓取空闲时再跑，跑之前先问你。
- 比对脚本放 scratchpad、只读生产库，结果写成一份差异清单给你看，不写库。

## 5. 测试

- `CninfoPdfAnnouncementDetailFetcher`：用几份真实回购公告 PDF 做夹具（比对时顺手存进测试资源），
  验正文拼接和 `ArtCode` 形状。
- `FallbackAnnouncementDetailFetcher`：东财抛异常 → 走巨潮；东财返回 null → 走巨潮；东财成功 → 不碰巨潮；
  东财连续 3 次失败 → 后面直接巨潮。
- 【回购公告进展】：两条都失败才计入"连续失败"。
- 配置三个取值各一条装配测试。

## 6. 不在本次范围

- 【中标/订单公告】接巨潮 PDF（要另做一轮比对）。
- 已入库的旧空壳用 PDF 回补：上线后回补那一段自然会走组合类，不用另做。

## 7. 比对结果（2026-10-22，298 条，PDF 全部下载成功、全部读得出字）

工作目录在会话 scratchpad 的 `buyback_pdf_compare`（脚本、PDF 缓存、report_*.md、diffs_*.csv），改拼法可离线重比、不再联网。

| 取字 + 拼正文 | 有差异的公告 | 说明 |
|---|---|---|
| PdfPig + 按行换行拼 | 50 / 298 | PdfPig 会把「元/股」的斜杠排错位置（变成「元股/」），价格、金额抽不出 |
| **pdftotext + 按行换行拼** | **43 / 298** | 最干净；差异主要是折行把「最低价」拆成「最低」+「价为」 |
| pdftotext + 去换行（数字间留空格） | 112 / 298 | 救回不少被折行拆开的值，但北交所模板里会把「交易均价」等误当成最高价 |
| 换行拼为主、缺的字段用去换行补 | 101 / 298 | 多出来的大多是东财没抽到、PDF 抽到的值 |

pdftotext + 按行换行拼那 43 条差异的定性（逐条对过原文）：

- **PDF 漏抽 39 处**：值在原文里，被折行拆开了关键词。可修（拼正文时处理折行），但上面那行说明简单去换行会带进新错。
- **两边都在原文、取了不同句子 16 处**：上交所新版公告开头多了一张汇总表（累计股数/金额/价格区间），东财正文里没有这张表，
  两边按"第一个匹配"取到的不是同一句。例：600636 当日回购 272,851 股 vs 累计 20,011,090 股。
- **东财的值在 PDF 原文里根本没有 7 处**：东财那条**匹配错了公告**——
  920717：PDF（截至 08-04）累计 40,497 股，库里是 1,978,500 股；
  920768：PDF 说截至 07-31 还没开始买，库里是 492,760 股。**这是生产库里现有的错数据**，跟 PDF 兜底无关。
  （更正：起初以为是"配到别的月份"，细查是同一只票几天内连发同名公告时，"±3 天取最新那篇"配到了隔几天的另一份，
  不限于北交所。已于 2026-10-22 修复（commit 1d24c9b：只认东财早一天/同一天，并一次性清掉回购 19 行、中标订单 4 行）。）
- **截至日期不同 6 处**：东财正文里没有"截至"那句时退回了公告日，PDF 里有真正的截至日。

另有约 40 处"东财没抽到、PDF 抽到"的累计股数，抽查 12 条：累计股数全对（东财那边漏抽），
最高价里北交所模板有 3 条取错（取到了交易均价那一类数）。

**结论：现在不能直接上线 PDF 兜底**——抽数规则是照着东财纯文本调的，换成 PDF 文字后不等价，达不到 §4.3 的门槛。
反过来，比对也暴露出东财这条路本身的两个问题：连发同名公告时配错篇（已修，见上）、上交所新版汇总表东财正文里没有。
