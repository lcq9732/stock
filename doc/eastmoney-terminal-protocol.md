# 东财终端私有协议逆向记录（2026-09-21 ~ 09-22）

## 结论：此路不通，别再走

> **行情数据包是加密的。** 协议框架已完全解出，但 payload 熵 7.9991、字节分布完全均匀、
> 所有已知压缩算法全部失败 —— 是加密，不是压缩。再往下就是逆向 `mainfree.exe` 的加密算法
> （IDA/x64dbg 级别，几天到几周），而拿到的是**我们已经能通过 clist 接口拿到的同一份数据**，
> 只是不受限流。**成本收益不成立，判定不做。**

这份文档记的是过程中解出来的东西 —— 协议框架、抓包方法、日志用法都是真成果，
以后若要查东财终端跟服务器要了什么，仍然用得上。

---

## 1. 为什么做这件事

分档资金流全市场快照有两条来源：

| 来源 | 精度 | 覆盖 | 问题 |
|---|---|---|---|
| clist 接口（`push2delay`） | **精确到元** | 全市场 | **限流**，一轮只放过约 16 页 / 共 60 页 |
| 终端「数据导出」 | **只有 3 位有效数字**（净额最大误差 0.46%） | 5576 只 | 精度不够做分析，用户已否决 |

所以想从终端的网络流量里直接拿**精确且不受限流**的那一份。结论是拿不到。

## 2. 抓包方法（零安装，可复用）

Windows 自带 `pktmon`，不需要 Wireshark/npcap。**要管理员权限**。

```
pktmon filter remove
pktmon filter add p1870 -t TCP -p 1870        # 按端口
pktmon filter add emip  -i 114.80.72.71       # 或按 IP
pktmon start --capture --pkt-size 0 --file-name x.etl --file-size 3000
pktmon stop
pktmon etl2pcap x.etl -o x.pcapng
pktmon filter remove ; pktmon unload          # 收尾，别留着
```

### 三个必须知道的坑

1. **`--pkt-size 0` 必须给**。默认只记每个包的前 128 字节，等于只有包头没有数据。
2. **别加 `-p 80` 全抓**（除非确认我们自己的 Fetcher 没在跑）。09-21 那轮抓到
   968,008 个包 / 1.27GB，其中**东财只占 677 个**，99.9% 是 Fetcher 打新浪的流量，
   还会混进无关的 HTTP 流量。
3. **必须在终端冷启动时抓**。数据只在**启动后首次加载**时传一次：
   - 点「数据导出 → 导出所有数据」**不发任何网络请求**（数据早在内存里）
   - 切标签、滚动、F5 都只拉可见的那一屏
   - 09-21 那晚抓了三轮共 936KB，正确重组后**总共才 3 万字节**，全是心跳
   - 09-22 冷启动抓一轮：**4.4MB**，这才是对的量级

### 退出终端的坑

**点窗口右上角 X 只是最小化到托盘，进程不退**（`mainfree.exe` 还在），`WM_CLOSE` 同样不退。
要真重启得**右键托盘图标 → 退出**。没真退 = 没有首次加载 = 白抓。

### 时间窗口

终端显示的是**上一交易日的收盘终值，一直到次日开盘（9:25）才变**。
所以“今天不抓就没了”是错的，**次日开盘前抓，拿到的还是前一天的**。

## 3. 东财终端的网络形态

进程：`C:\eastmoney\dfcf\mainfree.exe`（另有 `stockway.exe`）

| 通道 | 端口 | 说明 |
|---|---|---|
| 私有二进制协议 | `1861` `1862` `1863` `1864` `1870` `1890` | 行情主通道。**`1870` 是 app 服务器** |
| 私有协议**跑在 80 端口上** | `80` | ⚠ 不是 HTTP！借端口穿防火墙，行情软件常见做法 |
| 其它 | `9696` `5656` | |
| HTTPS 短连接 | `443` | 大量短连接（每条约 6.8KB），CDN 配置/更新/日志 |

⚠ **80 端口那两条最大的流里没有一个 `HTTP/1.1` 响应头** —— 一开始按 HTTP 解析得到
“响应体 0 字节”，差点误判成配置下载。实际上 `61.129.249.89:80`（449KB）和

服务器 IP 每次启动会变，但都在这几个网段：`61.129.` / `114.80.` / `47.107.` /
`14.103.` / `101.226.` / `101.96.` / `120.53.`。

**不是 UDP**：`Get-NetUDPEndpoint -OwningProcess <pid>` 查过，两个进程一个 UDP 端点都没有。

## 4. 包结构（已完全解出）

```
[PkgSize : uint32 小端][MsgId : uint16][flags/保留 : 11 字节]  = 17 字节头
[payload : PkgSize 字节]
```

头长 17 字节这个数是从日志反推出来的 —— 日志里每条响应都记了 `PkgSize` 和 `Tail`，
两者恒差 17：

```
PkgSize=239507, Tail=239524   -> 17
PkgSize=161,    Tail=178      -> 17
PkgSize=9,      Tail=26       -> 17
```

按这个结构切 `61.129.249.89:80` 那条 449,573 字节的流：
**解出 64 个包，100% 覆盖，零残留**。`61.129.248.99:80` 解出 20 个包，同样 100% 覆盖。

### payload 内层还有一层小头

以 `MAINCAPFLOWDETAIL` 那个包为例，payload 前 18 字节：

```
09 00 00 00 | 01 | 89 a7 03 00 | 01 | 5d 00 40 00 00 00 00 | <加密数据>
                   ^^^^^^^^^^^
                   0x0003a789 = 239497 = PkgSize - 10，内层数据长度
```

## 5. `Runtime.log` 是逆向这类协议的金钥匙

`C:\eastmoney\dfcf\Logs\Runtime.log`（GBK 编码）里，**每个请求和响应都记了元信息**：

```
CEA-SendRequest, servertype=app, msgid=REQID_QUOTE_HS_RANK_EX, MagicId=0(CategoryId=...), nPkgSize=67
CEA-RecvResponse: ServerType=app, RespType=REQID_TYPE_MAINCAPFLOWDETAIL, PkgSize=239507, bCompress=0, Tail=239524, Time=47ms
```

**要查终端跟服务器要了什么、要了多大，直接读日志就行，不用抓包。**

### 关键的请求类型

| RespType | 含义 | 本次大小 |
|---|---|---|
| **`REQID_TYPE_MAINCAPFLOWDETAIL`** | **主力资金流明细** <- 就是我们要的 | **239,507 B** |
| `REQID_QUOTE_HS_RANK_EX` | 沪深排行（资金流向页用的就是它） | 分批 |
| `REQID_TYPE_GSS_BUFFER_LIST` | 港股列表 | 342,834 B |
| `REQID_TYPE_COMMON_COMPRESS` | 通用压缩包 | 64,777 B |
| `REQID_TYPE_VAR_LIST_REQ` | 品种列表 | 45,768 B |
| `REQID_TYPE_NEW_SHORT_DECISION` | 短线决策 | 16,470 B |

ServerType 分工：`app` 行情、`mine` 资料（财务/除权/资讯）、`nsl` 行情列表缓存、
`his` 历史K线、`gss` 港股、`extd` 扩展数据、`zxfw` 资讯服务。

## 6. 解出来的内容清单（09-22 冷启动那轮，4.4MB）

| 流 | 原始 | 解压后 | 是什么 |
|---|---|---|---|
| `61.129.248.99:80` | 397KB | **1.9MB** | 港股行情（含 `HSI`），zlib |
| `61.129.249.89:80` | 449KB | 124KB 可解 + **239KB 加密** | 涨跌停价表 + **资金流明细（加密）** |
| `101.226.30.151:1870` | 82KB | 297KB | 资讯/公告推送，zlib |
| `61.129.129.208:1870` | 33KB | 168KB | 同上 |

### 顺带解出的一个真结构：涨跌停价表

```
<ID : uint32><45 30 00 00 00 : 常量 5 字节><涨停价 : float32><跌停价 : float32>   每条 17 字节
```

判据是**两个 float 的比值恒为 1.222 = 1.1 / 0.9**。124KB / 17 约 7300 条，正好是全部标的数。
ID 步长 0x40，是内部编号不是股票代码。

## 7. 加密的证据（决定性）

对 `MAINCAPFLOWDETAIL` 那 239,507 字节：

| 检验 | 结果 | 说明 |
|---|---|---|
| 整体熵 | **7.9991** bits/byte | 8.0 = 完全随机 |
| 256 个字节值 | 全部出现 | |
| 出现次数 | 最少 843、最多 1028、均值 936 | **完全均匀** |
| `0x00` 出现 | 946 次，约等于均值 | 明文二进制里 `0x00` 远高于均值；压缩数据也会略高 |
| zlib / raw deflate / gzip × 10 个偏移 | **全部失败** | |

压缩数据熵也高，但总能被对应算法解开、字节分布会有偏。**两条都不符合 -> 是加密。**

## 8. 走过的弯路（别重复）

1. **按 ASCII 股票代码搜数据流** —— 错的。A 股记录用**内部 ID**（步长 0x40），
   代码表在本地 `data/StkQuoteListNsl/StkQuoteList_V10_*.dat` 里，协议只传 ID。
2. **不分方向直接拼接所有包载荷** —— 得到 152KB 的假象。
   必须**按 TCP 流分方向 + 按 seq 去重**重组，正确结果是 3 万字节。
3. **精确匹配 float32** —— 若东财存 float32，`486386960` 会舍入成 `486386976`，
   字节完全不同，精确搜永远搜不到。要做**近似匹配**（相对误差 1e-6 内）。
   （本次两种都试了，都没命中，因为数据是加密的。）
4. **按 HTTP 解析 80 端口的流** —— 那不是 HTTP，见第 3 节。
5. **点导出想触发请求** —— 不发请求，见第 2 节。

诊断丢包用 TCP seq 覆盖检查：本次**零空洞、零丢失字节**，数据是完整的，
所以“搜不到”不是抓残了。

## 9. 替代方案（本来就该走的路）

| 路径 | 精度 | 说明 |
|---|---|---|
| **clist 跨轮续抓**（`push2delay`） | 精确到元 | 每轮约 16 页 / 共 60 页，3~4 轮攒满。**现行方案** |
| **逐股 `push2his/fflow/daykline`** | 精确到元 | 120 个交易日窗口，半年内都能补；只给净额+占比，**没有各档流入/流出分量** |
| 终端「数据导出」 | 3 位有效数字 | 有流入/流出分量和集合竞价，但精度不够做分析。**已否决，只当存档** |

**各档流入/流出分量和集合竞价只有 clist 当天快照有，漏一天永久空一天** ——
这是唯一有时效压力的部分。
