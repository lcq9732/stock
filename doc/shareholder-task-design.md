# 【拉取股东数据】迁到新任务框架（2026-09-18 设计，待确认）

## 0. 起因：跟分红一模一样的病，还没治

分红那一项刚迁完（见 doc/dividend-task-design.md）。扫一遍 orchestrator，
`RunFetchShareholderInternalAsync` 是**同一个形状、同一个病**：

| 事实 | 位置 |
|---|---|
| 每轮取全量名单（在市个股 5565 只）从头抓，没有任何"已抓过就跳过" | `FetchOrchestrator.cs:4154` |
| 失败名单写在 `await Task.WhenAll(tasks)` **之后**，取消直接冒泡、走不到 | 同上 |
| 一只票 **2 个请求**（股东页 + 流通股东页），全市场 11130 个请求、约 1 小时 | `SinaShareholderProvider.GetAsync` |

也就是说：**它今天被限流打断，会重演 09-18 凌晨分红那一幕**——
抓到的数据在库里，但"抓到哪了""哪些失败了"一个字都没留下，重新执行等于从头再来。

### 0.1 还有一颗已经写在注释里的雷

`SinaShareholderProvider.GetAsync` 的注释（原作者自己标的）：

> ⚠ 这里一只票要发**两个**请求…调用方是 `Task.WhenAll(全部股票)`，所以实际执行顺序是
> "所有票的第 1 个请求 → 所有票的第 2 个请求"，前半程谁都不完成、一条都写不进库。
> 现在没暴露成问题，只因为股东用的是 3 并发/1 秒、轮一圈快；**一旦这个接口也需要降速，
> 就会立刻变成"跑几百个请求、零写入、零进度"**。

迁成"一批 30 只"之后这颗雷顺手拆了：批内的两个请求在同一只票的 async 里连续发，
批间落库，任何时刻停下来都有完整的批已经进库。

## 1. 现状盘点（正式库实测，只读）

```
ShareholderCount   260,839 行 / 5,557 只票
TopShareholder   5,566,643 行
上次全量抓取       2026-09-02（5552 只），另 5 只停在 07-18
在市个股 5565 只：有数据 5552、一行都没有 13
```

### 1.1 关键：股东数据有**报告期**，判据可以比分红精确得多

```
每票最新报告期：2026-06-30 有 5513 只（半年报），其余零散
落在标准季末的：5521 / 5557 = 99.4%（全表 96.0%）
```

⇒ 现在库里就是"半年报那一期已经全抓齐了"。**下一期（2026-09-30 三季报）要到 10 月底才披露，
在那之前一个请求都不用发**——这不是"多久没抓了"的时间水位线，是"数据源有没有新东西"。

### 1.2 判据要用 `ShareholderCount` 的报告期，不能用 `TopShareholder` 的

两表最新报告期**不一致的有 7.9%**（5557 只里 441 只），方向是十大股东更"新"：

```
000034  户数 2026-06-30   十大股东 2026-08-17
000048  户数 2026-06-30   十大股东 2026-08-26
000100  户数 2026-06-30   十大股东 2026-08-21
```

那些额外期次是**不定期的股东名单变动公告**（增发、协议转让之后），不是季度期。
拿 `TopShareholder.max` 去跟"应有季度期"比，会因为它偏高而**把该抓的票判成已经很新** ⇒ 漏抓。
所以判据取 `ShareholderCount.max(report_date)`（99.4% 是规整季末），跟 target 同口径。

两张表"只有一张有数据"的票是 **0 只**，所以不用担心一表缺失导致判据失真。

## 2. 判据：照抄财务那一套，一行请求都不用发

`FinancialFetchPlanner` 已经把这件事解决过一遍，直接复用它的三个部件：

```
某票该抓  ⟺  ShareholderCount.max(report_date) < target
             且 不是"已经不交易了"

target   = 这只票**已披露**的最新报告期
           （SqliteEarningsScheduleRepository.GetLatestDisclosedPeriodByCode）
           查不到记录的（新股/B股/老退市股）退回法定截止日
           （FinancialFetchPlanner.LatestExpectedReportPeriod）

停牌豁免 = 最近一年一根日K都没有的跳过（财务那条实测筛掉 106 只、只误伤 0 只）
           判据自愈：哪天恢复交易，K线一到就自动回到待抓名单
```

为什么按**实际披露日**而不是法定截止日：66% 的公司挤在截止日前五天披露，
等截止日过完再认这一期，5478 只会同一天涌进队列（财务那边踩过，注释里写着）。

⚠ 兜底方向只能是"多取"：查不到披露记录就按法定截止日算，**绝不能因为查不到而漏掉一只**。

### 2.1 时间兜底：覆盖那 4% 不定期披露

光看报告期，那 4% 的不定期期次（股东名单变动公告）永远等到下个季报才抓到。
所以再加一条：**`fetched_at` 超过 100 天没抓过的也抓**（约一个季度）。
最坏情况一季度全刷一遍，跟现在"用户手动季度点一次"的节奏一致，只是自动了。

这条同时兜住另一个风险：【拉取财报预约日】好几天没跑成时，`disclosed` 字典是空的
（那时 target 退回法定截止日，本来就偏保守）。

### 2.2 不做索引法

分红那次加了东财公告索引，这次**不做**，理由：

- 本地判据已经零请求回答了"谁要抓"（报告期 + 实际披露日），索引省不掉什么；
- 东财股东户数 `RPT_HOLDERNUM_DET` **只到 2013**（新浪 2001 起，实测 600519 东财 63 期 / 新浪 77 期），
  当索引也只能覆盖那 4% 不定期披露，收益远小于分红那次；
- 少一个源依赖就少一处会坏的地方。

## 3. 不新建状态表

分红那次必须建 `DividendFetchState`，因为"没分红的票一行都不写"——"没抓过"和"抓了没有"
分不开。股东这边不存在这个问题：水位线直接读 `ShareholderCount` 的
`max(report_date)` / `max(fetched_at)`，历史数据天然就是水位线，**不用播种**。

已知代价：那 13 只"一行都没有"的在市股（新股居多）每轮都会被抓一次（26 个请求）。
不值得为它们单开一张表。

## 4. 批的粒度：30 只一批

一只 2 个请求，限流 3 并发/1 秒 ⇒ 一批 30 只≈20 秒；全量 5565 只≈186 批≈60 分钟
（跟目录里的估时 1.5 小时一致，**吞吐不变**，只是落库切成了批）。

`TItem` = 一只票的结果（含失败的那只，状态要落库）：

```csharp
record ShareholderOutcome(string Code, ShareholderData? Data, bool Ok, string? Error, bool RateLimited);
```

一批落库＝逐只 `ReplaceByCode`（它本身是"删该 code 旧行 + 写新行"的一个事务）。
⚠ **空结果不写**：`Counts.Count > 0 || TopHolders.Count > 0` 这个判断必须原样带过去，
否则限流返回空页面时会把那只票的历史股东数据整只删掉。

### 4.1 不设人为的每轮上限（2026-09-18 用户定）

原稿写了 `MaxCodesPerRun = 1200`，**去掉**。分次是为限流付的税，不是目标：
能一轮跑完就一轮跑完。

- 季度披露期 5513 只同时到期 ⇒ 一轮 11026 个请求、3 并发/1 秒 ⇒ **约 60 分钟**，
  跟目录里的估时（1.5 小时）一致，一轮跑得完。
- 真撞上限流，由**熔断 + 断点续跑**自然分次：连续 3 批全军覆没就收工记成「跳过」，
  下一轮从没抓过的那些接着走。**这正是这次迁移换来的东西**——
  有了续跑，"分次"不需要预先规划，被打断即分次。
- 财务那项之所以要 `MaxPerRun = 300`，是因为它的接口配额极严（约 10 请求/分钟），
  一轮跑完要几小时、中间什么都干不了。股东是 3 并发/1 秒，不是同一个量级，别照抄。

骨架给的 `MaxItems`（本轮几批）和 `Deadline`（空窗截止）照旧生效——那是**调度侧**
按空闲窗口传进来的，不是任务自己给自己设限。`SupportsPartialRun` 仍设 true，
「空闲时」触发就能用上。

自选/底仓/主动仓的票排最前（复用 `FinancialFetchPlanner.ReadWatchedCodes` 的做法）——
被 `Deadline` 截断时先保住真会被拿来分析的那些。

⚠ 同一条原则也适用于分红那一项：它现在有个 `MaxCodesPerRun = 400`
（doc/dividend-task-design.md §17.2）。日常有索引法兜着、基本碰不到，
但季度性全刷会被它切成多轮。那一项归另一个会话，这里只记一句。

## 5. 限流熔断：跟分红一致

连续 3 批（90 只）**全部失败且沾限流** ⇒ 停止本轮，返回
`TaskRunResult.Skipped("新浪在限流，本轮停在 N/M")`。

`Skipped` 而不是 `Failed`：它的语义是"这一轮根本没开工"，
计划项的 `AlreadyRanOn` 不认它，限流过去今天还能再来。

## 6. 模式映射

| 模式 | 含义 |
|---|---|
| `Incremental`（默认） | 报告期落后的 + 100 天没抓过的，**不设人为上限**（见 §4.1） |
| `FirstBackfill` | 无视判据全市场重抓（强刷出口） |
| `FillBacklog` | 只补 `Todos[FetchShareholder].failed`，**任务自己补**（`HandlesBacklog = true`） |
| `SpecificDay` | 不支持（股东页是全历史，没有"某一天"） |

`RetryTaskIds.Shareholder` 的取值 `"FetchShareholder"` **不动**（已等于枚举名，
manifest 里现有待办键继续认得出来）。

## 10. 要你拍板的两处

1. **时间兜底 100 天**——它跟限流无关，管的是"多久整轮重刷一遍"：
   太长会让那 4% 不定期披露的股东名单变动等一个季度才入库；太短会让整轮全刷变频繁
   （一轮 60 分钟）。100 天≈一个季度，跟"季度数据"的节奏对齐。
2. **退市股要不要纳入**（§7.2）。默认不动。

（每轮上限那条已按"能一轮跑完就一轮跑完"定了，见 §4.1。）

## 12. 纳入退市股（2026-09-18 当天追加）

### 12.1 为什么值得做：数据源真有，而库里几乎全空

沙箱实测新浪股东页对退市股**有完整数据**：

```

000004  股东总数 110 期  最新 2026-09-09
300029  股东总数 78 期   最新 2026-04-30
000638  股东总数 96 期   最新 2026-07-29
```

而库里 **337 只退市股只有 5 只有股东数据**（分红那一项 2026-09-06 纳入退市股之后，
337 只的分红数据是齐的——两项的口径本来就该一致）。

十大流通股东里的「香港中央结算」是北向持股的唯一来源，退市股缺这一块，
等于那段历史的北向分析只看得见活下来的票。

### 12.2 口径：跟分红一致，用 `StockMeta type='delisted'`（337 只）

不用财务那边的"2016 年后退市"（249 只）：这两项都是"逐只抓全历史"的慢数据，
而且实测新浪对老退市股也有数据，多那 88 只的成本是每年 176 个请求。

⚠ 名单是【补全退市名单】(`StepDelistedSupplement`) 往 `StockMeta` 写进去的，
所以目录里给这一项挂上了那条软依赖——**那一项没跑过，这边就少抓那批票，而且不报错、只是少**。

### 12.3 判据：退市股只走自己那一档，**不看"报告期落后"**

这一条是实测之后改的，原稿（"靠停牌豁免挡住"）是错的：

```
337 只退市股：
  有日K且很旧  307 只  → "一年没成交"的豁免生效
  一根日K都没有 18 只  → lastBarByCode.TryGetValue 直接 false，豁免**压根不触发**
  今年刚退市    12 只  → K线还在一年内，豁免也不触发
```

那 30 只会每轮被判"报告期落后"（退市公司的法定报告期早停了，这个判据对它们永远成立）
⇒ 每轮白抓 60 个请求、永远抓不完，日志上还一直挂着"待抓 30 只"。

所以改成：**退市股"从没抓过"立刻抓；抓过之后不看报告期，只按 `DelistedStaleDays`（365 天）重刷。**

代价说清楚：退市股**仍会披露**股东户数（实测 000004 最新到 2026-09-09），
所以它们退市前后那一两期最长晚 365 天入库。可以接受——退市股的股东数据是给回测
消除幸存者偏差用的历史资料，不需要季度级新鲜度。**不接受的话把那一档调短就行**
（`DelistedStaleDays` 一个常量）。

### 12.4 首轮成本

332 只从没抓过 × 2 请求 ≈ 664 个请求、约 4 分钟。之后每年一轮。

### 12.6 顺带修掉计划顺序（`PlanTemplateTests` 抓出来的）

加完软依赖之后全量测试红了一条：

```
「季度定期」里【补全退市名单】要排在【拉取股东数据】前面——后者用的是前者产出的东西
```

原来 `PeriodicOrder` 里它排在股东和分红**后面**。这不是形式问题：排在后面的话，
同一轮里那两项用的永远是上一轮的旧名单——**新退市的票会少抓一整轮，而且不报错、只是少**。
分红 09-06 就纳入退市股了，也一直在这个顺序下跑。

已前移，并把这条依赖写进 `PeriodicOrder` 的注释（那里原本列着"顺序上有两条依赖"，现在三条）。
