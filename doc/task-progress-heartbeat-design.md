# 任务进度上报改成按时间：【回购公告进展】被掐断的那条路

2026-10-24。起因是【回购公告进展】"总失败"，查下来是两件不同的事，这份方案只管第二件。

---

## 一、现象

日志里两类，**第一类不是 bug**：

```
[02:30:17] ⚠ 东财公告正文连续 10 条取不到，判断它当前不通（多半是限流），重抽停在第 213/300 条
[02:30:17] ⏸ 【回购公告进展】本轮没开工——已取到的 27 条已入库。先接着跑后面的项，
           都跑完了再回头试它（每次至少隔 15 分钟）。
```

这是 `AbortAfterConsecutiveFailures = 10` 在按设计干活，记的是「跳过」不是失败。它每轮都触发，
是因为积压大（2675 条回购公告里 2226 条没正文，7~9 月那 1858 条一条都没取到），
单轮几百个请求打同一个接口，撞限流是必然——那是另一笔账（减请求量/拉长节奏），不在这里谈。

**第二类是真问题**：

```
[02:58:47] ⏱ 【回购公告进展】10 分钟没有任何进展，判定卡住已掐断，
           最后一句是「回补 6 条只有标题、没取到正文的旧记录…」
```

卡在**回补**那段，而那段的进度是按条数报的：

```csharp
private const int ProgressEvery = 20;
...
if (_refillTried % ProgressEvery == 0 && _refillTried < stale.Count)
    Report($"回补 {_refillTried}/{stale.Count}…");
```

那轮只回补 6 条，`6 < 20`，**整段一次都不报**。

算一下为什么 6 条能耗掉 10 分钟（按超时和重试的节奏估，不是实测）：一条要两个请求，
HttpClient 超时 12 秒，RateLimiter 的快速重试是 2 秒、10 秒两档，走满约 96 秒/条，
6 条 ≈ 9.6 分钟——刚好顶穿这一项 `MaxQuiet: 10 分钟` 的阈值。

而注释里按**正常情况** 1.3 秒/条估算，6 条 8 秒钟就过去了，怎么看都不需要心跳。
两种情况差 70 倍，**按条数报就是在赌单位耗时**。

## 二、原则

> 任务要定时发出信息表示自己还在工作，除非它**真的**卡住了。

这条要拆成两半才站得住：

- **定时**——静默时长必须封顶，且这个上限跟单位耗时无关；
- **还在工作**——信号必须由"确实又往前走了一步"触发。

第二半不能省。纯定时器喂看门狗等于把看门狗关掉：一个真卡死的任务会靠自己的定时器
把自己"证明"成健康的。

## 三、骨架里已经有了，不用新发明

这件事 2026-09-08 就想清楚并拆成了两个东西，这次只是**没用上**：

| 组件 | 干什么 | 通道 |
|---|---|---|
| `ProgressThrottle` | 在**推进点**调用，到点才真报 | `IProgress<string>` → **喂看门狗** |
| `Heartbeat` | 纯定时器，证明进程还活着 | `FetchOrchestrator.Liveness` → **只进日志** |

`ProgressThrottle` 的类注释写的正是上面那条原则：

> 问题是单位耗时差得很远……于是静默时长完全不可控，实测能哑到 2 分 24 秒——而这正是判断
> "卡没卡死"要看的量。按时间报就把这个量钉死了：**最长静默＝间隔，跟单位耗时无关**。

`Heartbeat` 的注释则守住了另一半：

> 它不是心跳……绝不能喂给 `QuietWatchdog`，否则看门狗就成了摆设：一个真卡死的任务会靠
> 自己的定时器把自己"证明"成健康的。

两者的分工正好对应原则的两半。**循环在转 → 走到调用点 → 定时有心跳；真卡在某一条里
→ 到不了调用点 → 没有心跳 → 该掐就掐。**

现在全仓只有 `AdjSeriesRebuildTask` 和 `BoardIndexTask` 用了它。用法就一行：

```csharp
var tick = new ProgressThrottle(ProgressSink);
...
tick.Report(() => $"回补 {_refillTried}/{stale.Count}…");
```

## 四、改什么

> **⚠ 动手时发现方案这一节说错了一件事（2026-10-24）**
>
> 主循环和重抽**早就不会被看门狗掐断**了——2026-10-22 已经给它们加了 `else ReportQuiet(...)`，
> 每条都喂狗，那里的 `% 20` 只控制**日志密度**、不控制喂狗：
>
> ```csharp
> if (doneToday % ProgressEvery == 0 && …) Report(msg, _parsed, _hits);   // 日志
> else                                     ReportQuiet(msg, _parsed, _hits); // 喂狗
> ```
>
> **唯独回补段没有那个 else 分支**，日志稀疏＝喂狗也稀疏——被掐断的正是它，跟日志里
> "最后一句是「回补 6 条…」"对得上。
>
> 所以这一节的实际内容是两件事，不是一件：
> - **修 bug**：回补段补上 `ReportQuiet`（真正解决被掐断）；
> - **改善可观测性**：三段的日志节奏从按条数换成按时间——慢的时候 20 条可能要半小时才
>   出一行，人看着就是没动静。这件事不影响喂狗。
>
> 另外实现上没有直接用 `ProgressThrottle.Report(…)`：主循环的日志要带 Done/Total 进度计数，
> 而那个方法走 `IProgress<string>`，计数会在那一层丢。改成给 `ProgressThrottle` 加一个
> `TryTick()`（到点就消费掉这一次），调用方自己决定调带参数的 `Report` 还是 `ReportQuiet`：
>
> ```csharp
> var msg = $"…";
> if (_tick.TryTick() && done < total) Report(msg, done, total);
> else                                 ReportQuiet(msg, done, total);
> ```

### 1. `PlanWatchTask` 三处循环换成按时间（主改动）

| 位置 | 现在 | 改后 |
|---|---|---|
| 主循环取正文 (line 296) | `doneToday % 20 == 0` | `tick.Report(…)` |
| 回补空壳 (line 364) | `_refillTried % 20 == 0` | 同上 |
| 按新规则重抽 (line 456) | `done % 20 == 0` | 同上 |

阶段收尾那几句（"回补完成 N/M"）用 `ReportNow`，它们本来就该无条件出现。

注意主循环那处同时带了进度计数（`Report(msg, _parsed, _hits)`），换的时候别把进度条参数丢了。

### 2. 把限速器的 `OnStatus` 接出来

`RateLimiter` 在长暂停期间每 30 秒报一次"仍在主动暂停"，注释写得明白：

> 没这个的话，一次长暂停是静默的，看起来跟程序挂了一模一样。

但 `EastMoneyAnnouncementDetailFetcher` 没有订阅它，`IAnnouncementDetailFetcher` 上也没有
这个事件——**报了没人听**。于是"我在主动休息 15 分钟"和"我卡死了"在看门狗眼里一模一样。

改法：接口上加 `event Action<string>? OnStatus`，fetcher 把 `_rateLimiter.OnStatus` 转发出去，
任务订阅后接到自己的 `Report`。这跟别的 fetcher（`IBarDataFetcher.OnStatus`）是同一套做法，
不是新花样。

⚠ 这一条**不是**"用定时器喂狗"的后门：限速器的暂停是它自己安排的、有明确终点的等待，
它知道自己在等什么、还剩多久；跟"调用进去就没出来"是两回事。

### 3. 回补段补上提前收工

主循环和重抽都有"连续 10 条取不到就判定东财不通、本轮收工"，回补段没有——
失败只往 `_warnings` 里塞，所以东财不通时它不早退，只会一路耗到被掐断。
加上同一个计数器和同一个 `_aborted` 语义即可。

## 五、测试

现有 `PlanWatchHeartbeatTests` 有一条 **`单天只有几条时_不刷屏`**，钉的是旧语义
（条数少就不报）。按时间之后"报不报"不再由条数决定，这条要改写成按间隔表达：

- `ProgressThrottle` 的间隔是构造参数，测试可注入
  - 间隔给一个很大的值 → 快的时候一句不报（不刷屏，保住原意图）
  - 间隔给 `TimeSpan.Zero` → 每推进一步都报（慢的时候不会静默）
- 新增：回补只有几条、但每条都很慢时，**仍然有上报**（这正是被掐断的那个场景）
- 新增：回补段连续失败到阈值就收工，结果是 `Skipped` 而不是跑满

`QuietWatchdogTests` 那边不用动，看门狗本身没改。

## 七、风险

- 按时间报之后，**快循环的日志行数会变少**（原来每 20 条一行，现在 30 秒一行）。
  这是想要的效果，但如果有人靠日志行数判断进度，观感会变。
- `ProgressThrottle` 用 `DateTime.Now`，改系统时间会影响它；现有两个用户也一样，不单独处理。
- 回补段加了提前收工之后，积压清得更慢（东财不通时直接不干了）。这是对的取舍：
  原来那种"慢慢耗到被掐断"的收尾，本轮做的事一样没保住，还白占了十分钟联网源。
