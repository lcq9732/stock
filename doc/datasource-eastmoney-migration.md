# 腾讯/新浪能否换成东财：评估结论与实施方案（2026-09-10）

原问题是"能不能把 Tencent + Sina 全部换成东方财富"。逐项评估 + 沙箱实测之后**范围收敛到两项**：财务报表、行业分类。其余要么换了掉数据，要么换了没收益。

| 项目 | 结论 | 理由一句话 |
|---|---|---|
| **财务报表** | ✅ **做** | 摆脱中文行名匹配这个静默失败源；退市股/银行/券商统一；字段 40 → 200+ |
| **行业分类（大类）** | ✅ **做** | 覆盖率 58% → 接近全市场 |
| 股票列表 + 流通市值 | ❌ 放弃 | 数据等价、请求数持平，新浪合并不掉（还要供分红/指数成分/银行PDF），净收益为零 |
| ETF 名单 | ❌ 放弃 | 同上，还多出 60 只差额要查 |
| **日K（三种复权口径）** | ❌ **只能腾讯**，见第 1 节 | 量上堵死，与口径无关 |
| 资金净流入 NetInflow | ❌ 不换 | 口径不可复现，1386 万行历史作废且不可重建 |
| 分红送配 / 配股 | ❌ 不换 | 东财 56973 行 vs 库里 80021 行，退市股大面积缺 |
| 指数成分（716 个） | ❌ 不换 | 东财只有 5 个指数的成分表 |
| 银行监管 PDF | ❌ 不换 | 东财没有同口径原文 |
| 全市场日K对账 | 🔧 另立需求 | 59 个请求换一份全市场体检，属于体检工具不属于换源 |

---

## 1. 日K为什么只能用腾讯，不能用东财

> 这一节是长期结论，以后再问"K线能不能换东财"直接看这里。

### 1.1 前提：前复权和后复权都必须从源取，不能本地算

用户 2026-09-10 定论。所以任何 K线方案都必须能提供**三套口径**（不复权 / 前复权 / 后复权），少一套就出局。

- 新浪：**只有前复权一种口径**，直接出局（2026-09-10 已据此把 `BarSource=Tencent` 的"回退新浪"拆掉——新浪成交量是股、腾讯主板是手，回退一次就往那只票历史里掺一段异口径的行）。
- 东财：`push2his .../stock/kline/get` 支持 `fqt=0/1/2`，三套都给，**口径能力没问题**。
- 腾讯：`newfqkline` 三套都给。

所以口径不是筛选条件，量才是。

### 1.2 决定性原因：push2his 扛不住这个量

前后复权都要取 = 每天 5900 只 × 2 = **11800 个逐股请求**（不复权那套若也走它就是 17700）。而 push2his 有两个**互相独立**的熔断触发点：

| 触发点 | 实测 | 表现 |
|---|---|---|
| 累计请求数 | 用户环境 2026-09-04：**连发 16~35 个就被切**，触发的是累计数不是速率 | 程序现配每 15 个主动歇 2 分钟，摊下来约 **11 秒/只** |
| 单次响应大小 | 沙箱 2026-09-10：3 行 ✅、243 行（1年）✅、约 730 行（3年）❌、`beg=0` / `lmt=100000` 立刻 ❌ | 切后整族域名（含编号镜像 7/21/41/82）一起返回 0 字节，1~3 分钟自愈 |

按现有耐受度算：**11800 × 11 秒 ≈ 36 小时**。K线是每天必须当天跑完的活，放不进这个预算。

对比腾讯 `newfqkline`：单页 640 行、全历史约 10 页/股、跑了一年多没有这类熔断，退市股完整历史也能拉。

**结论：东财 fqt=1/2 的复权口径就算跟腾讯逐行一致也没用——量先撑不住。** 这个结论不依赖口径比对，所以不需要等那组比对数据。

### 1.3 顺带记录的两个事实

- 全量回补更不可行：按"1 年一段"切片，15 段/股 × 5900 只 × 3 口径 ≈ **26 万请求**，每段都在熔断线附近蹭。
- `EastMoneyBarFetcher` 现在的 URL 写死 `lmt=100000` + `fqt=1`，正是必被熔断的形态，且只支持前复权。**`BarSource="EastMoney"` 这个选项目前实际不可用**，`FetcherSettings.cs` 里那段"沙箱实测可达"的注释容易误导，建议补上响应大小这条。

### 1.4 那 59 个请求的快照还有什么用

`push2delay .../clist/get` 一次 59 页能拿全市场当日 OHLCV（`f17`开 `f15`高 `f16`低 `f2`收 `f18`昨收 `f5`量 `f6`额 `f8`换手 `f124`时间戳），但它是**行情列表，只有当天、只有原始价**，替代不了 K线源。它真正的用武之地是**每日对账**：不写 `Bar` 表，只跟腾讯当天写进去的值比，能一次查出全市场级的漏抓、成交量单位错、盘中值被固化（库里现在还有 5350 行盘中污染）。这属于体检需求，另行排期。

## 2. 要做的两项：实施方案

两项互相独立，可以分开做、分开验收、分开上线。

### 2.1 财务报表：新浪 TSV → 东财 F10

#### 收益（按价值排序）

1. **解析可靠性**。现在是拿中文行名匹配（"营业总收入"/"营业收入"、银行叫"业务及管理费用"…），报表版式一改就静默丢科目——之前漏配银行行名，42 家银行的成本收入比整类算不出来。东财是固定英文列名 + 显式 null。
2. **覆盖**。银行/券商不用再维护备选名表（600036 用同一张 G 表返回 102 期，`ORG_TYPE=银行`）；退市股同样有（300104 乐视网 71 期）。
3. **字段 40 → 203/319/254 列**。⚠ **近期兑现不了**：`FinancialKeys` 只有 60 个 key，换源不会自动多出指标，要先扩 key 才用得上。算期权，不算当期收益。

#### 已验证的等价性（2026-09-10）

600519 / 2026-06-30，东财 vs 库里新浪值：

| 科目 | 东财 | 库里（新浪） |
|---|---|---|
| 营业总收入 `TOTAL_OPERATE_INCOME` | 92278072083.21 | 92278072083.21 |
| 营业成本 `OPERATE_COST` | 9473762565.88 | 9473762565.88 |
| 归母净利 `PARENT_NETPROFIT` | 44516880421.86 | 44516880421.86 |
| 基本EPS `BASIC_EPS` | 35.57 | 35.57 |
| 研发费用 `RESEARCH_EXPENSE` | 114926219.6 | **（空）** |

单位同为元，103 期报告期**无重复行**。最后一行正是"东财更全"的具体例子。

#### 接口

```
GET https://datacenter.eastmoney.com/securities/api/data/v1/get
    ?reportName=RPT_F10_FINANCE_GINCOME | GBALANCE | GCASHFLOW
    &columns=ALL&pageSize=500&pageNumber=1
    &filter=(SECUCODE="600519.SH")&sortColumns=REPORT_DATE&sortTypes=-1
```

一次拿全部报告期（茅台 103 期，`pages=1`），3 请求/股，与新浪持平。

#### 落地步骤

1. **先做映射表核对（纸面工作，最花时间的一步）**：60 个 `FinancialKeys` ← 东财列名，逐个人工确认。已知要小心的：
   - `TOTAL_OPERATE_INCOME`（营业总收入）vs `OPERATE_INCOME`（营业收入）—— 银行/券商两者含义不同，别接反。
   - 资产负债表/现金流量表的列名同样要逐个核，不能靠名字像就映射（东财字段命名误导已有三次踩坑记录）。
   - 现金流量表附注科目：确认东财是否单列，避免与正表重名混淆。
2. **新增 `EastMoneyFinancialProvider : IFinancialProvider`**（`GetAllAsync(code)` 签名不变），走 `datacenter.eastmoney.com/securities`（注意与现有 `EastMoneyDataCenterClient` 的 `datacenter-web` **不是同一个 host**，需要确认客户端能否自定义 host，否则新写一个轻客户端）。
3. **配置开关** `FinancialSource = "sina" | "eastmoney"`（JSONC 模板里写成一行去掉 `//` 就能用）。
4. **样本验收**：随机 200 只（含 20 家银行、10 家券商、20 只退市股）× 全部报告期 × 60 个 key，与库里逐格比对，单位换算后容差 0。每条差异都要给出原因，说不清就不上线。
5. **全量切换**：`FinancialKeys.Version` 4 → 5。现有增量逻辑会自动把全部 5788 只判为"科目集落后"重抓，且**版本落后不认停牌豁免**（见 `FetchOrchestrator` 里那段判据），正好是要的行为。1.7 万请求，datacenter 最宽松，跨天分轮跑。
6. **旧数据处理**：`SqliteFinancialRepository` 本来就是"按股票整只 `DELETE` 再插入"，重抓天然整只替换，不会新旧混。切换前 `VACUUM INTO` 导出一份 `FinancialReport` 留档（1760 万行），验收通过再删。
7. **回滚**：开关改回 `sina` + `Version` 回退 + 从留档恢复。旧 `SinaFinancialProvider` 不删，类注释里写明退役原因。

#### 为什么必须全量重抓而不是只换增量

同一张表里前后期来自不同源，同比/环比会出现口径断层，而 `FinancialReport` 没有 `source` 列，事后分不出哪行是谁给的。

### 2.2 行业分类：新浪大类 → 东财大类（两所门类保持不动）

#### 现状与最小改动

现在是"两所官网门类（19 类，覆盖全市场）+ 新浪大类（84 类，覆盖 58%）"合并。**只换后半截**：`StockIndustry` 的 `ClassCode`/`ClassName`（门类，单字母 A~S）继续来自两所，`MajorName`（大类）改由东财供。这样三个字段都齐，改动面最小，两所那一路还能继续当交叉校验。

#### 接口

```
GET https://datacenter.eastmoney.com/securities/api/data/v1/get
    ?reportName=RPT_F10_ORG_BASICINFO
    &columns=SECUCODE,SECURITY_CODE,CSRC_INDUSTRY_NAME,BOARD_NAME_2LEVEL
    &pageSize=500&pageNumber=N&sortColumns=SECURITY_CODE&sortTypes=1
```

- `CSRC_INDUSTRY_NAME` 直接是**"门类-大类"两级**："金融业-货币金融服务"、"制造业-酒、饮料和精制茶制造业" → 取破折号后半段作 `MajorName`。
- 全市场 `count=24810`，`pageSize=500` → 约 50 页（新浪那条是 ~90 个请求且只覆盖 58%）。
- 含老股/退市股（000003 有值）。

#### 落地步骤

1. **抽基类**：把"两所门类"那段从 `ExchangeSinaIndustryProvider` 提到 `IndustryProviderBase`，子类只实现"大类从哪来"。新增 `ExchangeEastMoneyIndustryProvider`。
2. **过滤与分页护栏**：只收 `.SH/.SZ/.BJ` 且 6 位数字的行（`count=24810` 含非 A 股/历史行）；`sortColumns` 带 `SECURITY_CODE` 保证唯一序；行数比库里少 5% 以上整轮放弃。
3. **配置开关** `IndustrySource = "sina" | "eastmoney"`。
4. **建议同时给 `StockIndustry` 加 `source` 列**——现在这张表主键是 `code`、逐条 `INSERT OR REPLACE`，**东财没覆盖到的票会残留新浪旧值**，加了列才分得出哪行是谁给的。
5. **验收**：全市场逐股比对现有 `StockIndustry`，输出两张清单——"新浪有东财无"、"两者大类不同"。前者应接近 0，后者要抽查确认是东财更准。
6. **旧数据**：快照表，验收通过后整表覆盖；表里只有"当前分类"没有时点维度，旧值无留存价值。切换那次建议先清表再全量写，避免残留混源。
7. **回滚**：开关改回 `sina`，重跑一遍（1~2 分钟）。

### 2.3 两项的共同护栏

- 东财所有分页都带唯一次键（`sortColumns=X,SECURITY_CODE`）+ `count` 对账，否则跨页重复+遗漏且不报错。
- 新表上线带批内主键去重自检并打印重复样例 key。
- 开关都能改 `fetcher-settings.json` 后重启回退，旧 Provider 类不删。
- 落地前用 Debug 实例（独立数据目录）在**用户环境**复核 datacenter 连续 500 页的稳定性——本文可达性结论来自沙箱出口，不等于公司网关下的表现。

## 3. 放弃项的理由（备查）

### 3.1 股票列表 + 流通市值、ETF 名单

`push2delay clist` 实测可用（全市场 `total=5912`、ETF `total=1598`），数据等价、请求数持平（55 → 59）。第一版把"通道合并、少一个厂商"算作收益，**但新浪合并不掉**——分红、指数成分、银行 PDF 还得靠它。所以换了只是把一个正常工作的接口换成另一个，还要付等价性验证的成本和新风险。净收益零甚至为负，放弃。

（若将来决定做 §1.4 的日K对账，列表和市值会随那批请求顺带拿到，届时再一并考虑。）

### 3.2 资金净流入 NetInflow

库里存的是新浪 `netamount`（全档合计）。实测东财分档是**零和拆分**：

```
600519 2026-09-09  主力 -277123472  中单 +277191968  小单 -68489  → 合计 ≈ 7 元
新浪同日 netamount = -688364328
```

主力+中+小恒等于 0，任何组合都造不出新浪那个数。换源 = 换定义，1386 万行历史（2010 起）作废，而东财逐股只给 120 天，**永远重建不回来**。

要统一到东财口径只有一条路：消费端改用已在库的 `NetInflowDetail`（东财主力净额），把 NetInflow 冻结成历史表。那是分析口径变更，不是数据源迁移。

### 3.3 分红送配 / 配股

- `RPT_SHAREBONUS_DET` 全量 `count=56973`，库里新浪 **80021 行**（含退市股 4765 行）。
- 退市股抽查：000033 / 600145 / 300216 **全空**，002681 有 7 行。
- 分红是**复权因子的输入**，缺一条除权记录，那只票的复权序列整段错且不报错。
- 配股 `RPT_F10_DIVIDEND_ALLOTMENT` 存在（万科 1997/1999 都在），但比例只在 `EVENT_EXPLAIN` 文本里（"每10股配2.73股"）要正则解析，新浪那边是结构化列。

保留新浪。东财这张表适合当**交叉校验源**（多给 `EX_DIVIDEND_DAYS`、除权后 10/30 日涨跌幅），跑一次比对能反查新浪的漏。

### 3.4 指数成分（716 个）

`RPT_INDEX_TS_COMPONENT` 只有 5 个 TYPE：沪深300(300)、上证50(50)、中证500(500)、科创50(50)、深证50(50)，合计 4930 行。`clist?fs=i:1.000300` 返回的是指数自己不是成分股。新浪 `vII_NewestComponent` 是唯一可用源。

### 3.5 股东数据（可换增量，暂不做）

十大流通股东东财与库里**逐行一致**（600519 count=940，最早同为 2003-12-31）；十大股东 872 vs 库里 870（差 2 行待查）；股东户数东财只到 2013（新浪 2001 起）。可以只换增量、历史留库，但收益仅是"JSON 替代 HTML 解析"，优先级低于财务和行业，本轮不做。
