# 剩下 7 项迁到新任务框架 · 设计方案

2026-09-21 起草，**等确认后再动产品代码**。

K线六项迁完之后（见 [bar-tasks-migration-design.md](bar-tasks-migration-design.md)），
计划里是 **38 项新框架 / 16 项老方式**。这份说剩下那 16 项里**真该迁的 7 项**怎么迁。

---

## 0. 为什么是这 7 项，另外 9 项为什么不迁

| 分类 | 项 | 判断 |
|---|---|---|
| **该迁（本文档）** | 板块成分股、拉取个股行业与题材、拉取市场事件、中标/订单公告、拉取业绩预告/快报、概念和行业板块、拉取财报预约日 | 联网、有"跑一段停一段"的诉求 |
| **按设计不该迁** | 【重新拉取失败】 | **元动作**：遍历各任务的待办再转交回去。它本身不是"一项数据"，而且已经通过 `ITaskBacklogRunner` 跟新框架对接好了 |
| 同上 | 【拉取区间数据】【重取前复权】 | **跨多项的复合动作**（区间那个要串个股三口径 + ETF + 指数 + 退市股 + 资金流）。它们该不该拆是另一个设计题，不是"迁移" |
| **迁了收益很小** | 板块指数合成、ETF指数映射、回填水位、重解析已有PDF、导入手工数据、优化数据库 | 全是**本地计算、不联网、一次性**。新框架给的三样好处（批边界收尾、自己补待办、统一心跳）基本用不上 |

> 例外值得单独看一眼：**【板块指数合成】** 是 2026-09-11 那次 WAL 撑到 162 GB 的元凶
> （单事务写 468 万行）。把它改成分批落库确实有价值，但那是"改写入方式"、顺带迁框架，
> 不是为迁而迁——单独开一题。

## 1. 这 7 项的三条共性（决定整批形状）

### 1.1 **它们互不共用内核**——跟K线六项最大的不同

K线六项共用 `ProcessOneStockAsync`，而那个内核还有八处别的调用方，所以必须先抽判据、
再整批迁（见那份文档 §0）。这 7 项各有各的 provider 和表，**可以一项一项独立迁、独立验证、
随时停**。风险小得多，也不需要"先抽内核"那一步。

### 1.2 **七项都没有待办**——`HandlesBacklog` 一律 false

`RetryTaskIds` 里没有它们任何一个的条目，也就是说**没有任何地方会为它们产生待办**。
所以这批不涉及待办接管，`FetchMode.FillBacklog` 分派到它们时本来就是空转。

> ⚠ 顺带查出一处**空头支票**：`FetchMarketEvents` 在 catalog 里声明了
> `SupportedModes: ... | FetchMode.FillBacklog`，可它既没有 taskId、也没有任何待办来源。
> 界面上那个模式下拉因此多了一个选了没用的选项。要么删掉这个声明，要么给它真做一套待办
> （比如"某一年切片抓失败了记下来"）。**建议删声明**——这三张表是 UPSERT 幂等的，
> 重跑一次增量就把缺的补上了，不值得再养一份待办。

### 1.3 **四项的 provider 是"回调落库"形状**，跟骨架对不上

`FetchStockBoardMap` / `FetchMarketEvents` / `FetchEarningsForecast` / `StepBoardList`(push2 那条)
的 provider 签名都是这样：

```csharp
await provider.FetchAsync(start, end, batch => repo.Upsert(batch), progress, ct);
```

——**provider 自己翻页、自己回调落库**，一次调用跑完整段。而骨架是"子类 yield 一批、骨架存一批"。

**统一答案：这类任务自己存，`yield` 的单元定成"可以安全停下的边界"**（一张表 / 一段 / 一个
年份切片 / 一个板块）。已有两处先例走的就是这条路：`NetInflowTask.FillDaysAsync`、
`BarFetchTaskBase.FillValueAsync`——它们都在 `FetchAsync` 里自己调 `SaveBatchAsync`。

不去改 provider 的签名：那要动四个 provider 加各自的分页/重试逻辑，收益只是"形状更漂亮"，
而**回调落库本身是对的**——它保证了"抓一页落一页、中途停不丢"。

## 2. 逐项设计

### 2.1 【板块成分股】`StepBoardMembers` —— 最该迁、形状最贴合

**现状**：`FetchBoardMembersCoreAsync`（约 140 行）。逐板块抓、**逐板块落库**，
已经有一套很完整的土办法：

- 按"上次抓到的只数"**先小后大**排序（大板块要翻 40 页、最容易失败，先把小的收干净）
- 未抓过的按中等（200 只）对待，排在已知小板块之后
- 新鲜度跳过（`GetBoardsWithFreshMembers`）
- **连续失败 15 个就判定被限流、提前收尾**（阈值跟 `RateLimiter` 熔断对齐）
- terminal 通道下不发请求，所以 push2 熔断不能拦它
- 进度文本回传界面（"已抓 144/1000，还剩 856"）

**一批＝1 个板块**（落库粒度本来就是它）。

**迁移收益**：`MaxItems`/`Deadline` 直接变成"本轮抓 N 个板块就干净收尾"——现在只能靠
连续失败熔断或人点停止。这一项估时 20 分钟、跨好几轮才抓得完，正是"空闲时补"最该服务的对象。

**判据抽进 Logic**：
- `BoardMemberPlanner.Order(boards, freshCodes)` —— 先小后大 + 未知按 200 + 稳定次序
- 连续失败熔断复用 `HfqProbeGate` 的形状，或单独一个 `ConsecutiveFailureGate`（阈值 15）

**要原样保住**：terminal 通道那道例外、逐板块落库（断点粒度）、失败原因当场进日志、
`_memberProgressText` → `TaskRunResult.Progress`。

---

### 2.2 【拉取个股行业与题材】`FetchStockBoardMap`

**现状**：一次 provider 调用，内部分批回调；**快照语义**——拿到第一批才 `ClearAll()`，
这样接口挂了库里旧数据还在。

**一批＝provider 的一次回调批**（任务自己存，见 §1.3）。

**要原样保住**：
- `ClearAll` 的时机（第一批到手才清）——这是"接口挂了不丢数据"的唯一保护
- 取消时那句"已落库的部分有效；这张表是快照，下次重新全量取"

**迁移收益**：中途停止有干净的边界；心跳统一。**不设 `MaxItems`**——快照语义下"只做一半"
没有意义（下次还是全量重取）。

---

### 2.3 【拉取市场事件】`FetchMarketEvents`

**现状**：三张表各跑一段——机构调研（`OrgSurvey`）、股东增减持（`HolderChange`）按水位线
+ **回看 30 天**（兜公告补发/修订）；限售解禁（`ShareLift`）**全量重取**、不传日期。

**一批＝一张表**（3 批）。粗，但诚实：这三张各自是独立的一段，停在表边界最干净。

**判据抽进 Logic**：`MarketEventWindowRule.Start(fullBackfill, isFirstRun, watermark, floor, lookbackDays)`
——现在那三支 if 藏在 `RunOne` 局部函数里。

**要原样保住**：
- **主键重复告警必须收进 errors**（`OnWarning`）——注释里写着它是"数据静默丢失的唯一早期信号"
  （龙虎榜席位曾丢 7.5% 且不报错）
- 整段回补那句**净增对账**（"补回此前遗漏的 N 行"/"没有净增，说明此前没有跨页遗漏"）——
  这个数本身就是结论
- 一张表失败不拖垮另外两张

**顺带**：删掉 catalog 里那个 `FetchMode.FillBacklog` 声明（§1.2）。

---

### 2.4 【中标/订单公告】`StepAnnouncements`

**现状**：按**自然年切片**（`CalendarYearSlicer`，不切会被搜索源的翻页上限静默截断），
每片交给 `AnnouncementFetchOrchestrator.RunAsync`。关键词为空＝空跑。

**一批＝一个年份切片**。日常回看 14 天时只有 1 片，跨年补历史时才有多片。

**模式**：增量（回看 14 天）/ 只抓某一天——两个都已经在，照搬。

**要原样保住**：关键词为空时 `NothingToDo` 并说清楚原因；单片失败不带倒后面的年份。

**迁移收益**：最小的一项（日常 1 片）。迁它主要是为了**把 `AnnouncementFetchOrchestrator`
这条路也纳进统一的心跳/日志规矩**——它现在是另一个 orchestrator，自成一套。

---

### 2.5 【拉取业绩预告/快报】`FetchEarningsForecast`

**现状**：两段（预告 / 快报），各自水位线（`GetLatestForecastNoticeDate` /
`GetLatestExpressUpdateDate`），各自 try——**快报失败不该把已经抓好的预告一起算失败**
（快报是非强制披露、覆盖面小）。

**一批＝一段**（2 批）。

**要原样保住**：两段各自 try 的边界；首次全量那句"约 400 页"的提示。

---

### 2.6 【概念和行业板块】`StepBoardList`

**现状**：三级回退——① 东财终端本地文件（不联网）② 行情中心菜单 JSON（1 个请求拿全量）
③ push2 分页（`BoardListFetchLoop`：按页续传 + 暂存区提交）。最后再跑一次**不联网的层级树导入**
（不管名单成没成功都跑）。

**一批**：正常路径（①②）是"一次拿全量"＝1 批；退到 ③ 才有多批（按页）。

**⚠ 绝对不能动的语义**：`BoardListFetchLoop` 的暂存区。半截列表得存下来（否则没法续），
但**半截列表绝不能进正表**——`Board` 是快照语义，"这一轮没出现的板块＝已下架"会连成分股
一起删掉，而成分股约 2500 个请求、跨好几轮才攒得齐。这段逻辑已经单独成类、有单测，
迁移时**原样调用，一个字不改**。

**迁移收益**：正常路径就 1 个请求，收益很小。迁它的理由是**它跟【板块成分股】是一对**
（同源同时点，见 `FetchBoardListNamesAsync` 的注释），两项一起迁，那条"名单和成分来自两个源
会对不上"的约束才好在一个地方说清楚。

---

### 2.7 【拉取财报预约日】`FetchEarningsSchedule`

**现状**：先问数据源有哪些报告期（通常 1~4 个），逐报告期抓。抓之前记下旧的有效日期，
抓完对一遍——**改期是这个任务最该报出来的事**。

**一批＝一个报告期**。

**要原样保住**：改期对账那一段。

**迁移收益**：最小（估时 20 秒）。排在最后，或者干脆不迁。

## 3. 落地顺序

一项一个 PR 式的小步，每步独立编译 + 单测 + 离线实机验证：

| 步 | 项 | 收益 | 风险 |
|---|---|---|---|
| ① | 板块成分股 | 最高（20 分钟的活终于能分批） | 中（判据多，但都有注释） |
| ② | 拉取个股行业与题材 | 高（8 分钟，快照语义要小心） | 低 |
| ③ | 拉取市场事件 | 高（6 分钟，顺带删空头支票） | 低 |
| ④ | 中标/订单公告 | 中 | 低 |
| ⑤ | 拉取业绩预告/快报 | 中 | 低 |
| ⑥ | 概念和行业板块 | 低（跟①配对才做） | **中**（暂存区语义） |
| ⑦ | 拉取财报预约日 | 最低 | 低 |

**建议先做 ①②③**，跑一轮真库验证；④⑤⑥⑦ 看情况再说——⑦ 甚至可以不做。

### 两处自查出来的错

1. **我把 `FillBacklog` 判成"空头支票"时，漏看了两个测试**。删掉声明后它们红了。查下来是
   **测试陈旧**：那个声明原本服务于大宗交易的残缺日，而大宗 2026-09-17 已拆成独立任务
   （`RetryTaskIds.BlockTrade`），从那以后确实没有任何地方往 `FetchMarketEvents` 名下记待办。
   所以删除是对的，两个断言是 09-17 那次拆分时漏改的——已更新并写明原委。
2. **关键词解析器带副作用**（实机验证才露出来）：registry 那条总分支给**每一项**都填
   `TaskRunArgs.Keywords`，而 `ParseAnnouncementKeywords` 在关键词为空时自己写日志。
   于是【概念和行业板块】【板块成分股】各打了一句"「关键词」格是空的，这一轮不抓中标/订单公告"。
   已拆出不写日志的 `AnnouncementKeywordsOf`，总分支**按动作过滤**只给公告那一项填；
   空关键词由那个任务自己报。单测照不出这类问题。
