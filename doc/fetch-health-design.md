# 抓取行为健康体检设计方案

> 状态：**已实现**（2026-09-18）——见 §8。实机验证那一步我做错了一次，也记在 §8.3。
> 起因：【当日完整性体检】收尾后剩下的那块空白。它查"库里数据齐不齐"，
> 而"某一项连着几轮没跑成"至今没有任何地方会说一声。
> 当初把公告、业绩预告那批从体检里收窄掉时写的理由就是
> "这一项连着几天没抓成该由计划的运行记录回答"（见 day-completeness-check-design.md §3.4 类 3），
> 但那个回答的人一直没出现。

---

## 1. 问题

### 1.1 两类失效，只有一类有人管

| 失效 | 谁发现 | 例子 |
|---|---|---|
| **数据不齐** | 【当日完整性体检】（2026-09-16/17 做的） | 今天融资余额只有沪市 |
| **抓取行为异常** | **没人** | 【龙虎榜席位】连着 5 轮失败、【分红送配】每轮都被前置拦、某一项一直排不上 |

第二类现在只能靠人主动去翻计划页的状态列——而那里只显示**上一次**的结果，看不出"连着几轮都这样"。
一项昨天失败、今天失败、明天还会失败，界面上永远只是一行"✘ 失败"，跟偶发失败长得一模一样。

### 1.2 为什么体检接不了这个活

体检查的是**库里有没有数据**。抓取行为出问题时，它报出来的是"融资余额不齐"——
对，但那是结果不是原因，人还得自己去翻日志找"为什么不齐"。而且有一大类失效体检根本看不见：

- 数据源改了接口 → 这一项每轮都失败，但库里**旧数据还在**，体检查"最新一天有没有"可能仍然过关
  （比如整段回补类的项）；
- 一项被长任务挤掉、连着几天没排上 → 它抓的那类数据体检压根不查（公告、业绩预告那批）。

## 2. 已经有的材料

这一版的设计尽量不新增存储，因为需要的东西基本都在：

| 材料 | 在哪 | 用途 |
|---|---|---|
| 每项上次的开始/结束/结局/错误数/摘要 | `FetchPlanItem.LastStart/LastEnd/LastOutcome/LastErrorCount/LastMessage`（进 `fetch-plan.json`） | 判据的输入 |
| **唯一的结果落账点** | `PlanRunner.Finish()` | 将来要记滚动历史，钩子就在这一处 |
| 当日报告 `plan-yyyy-MM-dd.txt` | `logs/`，一天一份，每项一行 | 给人复盘；**不作为判据输入**（文本格式会变） |
| 轮次锚点 | `FetchPlanItem.RoundAnchor` / `FetchPlanGroup.DueAnchorAt`（2026-09-18 刚补齐） | 判"第几期"的基准 |
| 滚动样本的先例 | `FetchPlanItem.RecentDurationsSec`（最近 5 轮耗时，已进 json） | 第二步要加"最近 N 轮结局"时照这个形状 |

## 3. 判据：最后一次成功落在**第几期**之前

### 3.1 为什么不能按天数（实测）

生产计划里 46 个启用项，"距上次开跑多少天"的实测分布：

| 天数 | 项 |
|---|---|
| 0 天 | 日更组 28 项 + 早间组 1 项 + 季度组当天跑的 4 项 |
| 1~8 天 | 季度组 3 项（客户供应商、子公司、公司档案…） |
| **14~16 天** | 季度组 7 项（行业分类、指数成分/权重、股东、监管指标…） |

季度组那些 16 天没跑的**全是正常的**——月度项本期跑完就等下个月。
一刀切按天数：阈值给 3 天，季度组全误报；给 40 天，日更项停两周都不吭声。

### 3.2 判据

> **这一项最后一次成功，是在多少期之前？超过它自己频率对应的上限就报。**

"期"由组的重复规则定义，正好复用刚补齐的轮次锚点：

```
periodsBehind(item, now):
    anchor = 当期锚点（RoundAnchor）
    往回数 N 期的锚点 A(N)：EveryWorkday = 往前 N 个工作日的同一时刻
                            Weekly / Monthly = 往前 N 周 / N 个月的应跑时刻
    找最小的 N 使得  (LastStart ?? LastEnd) >= A(N)   且  LastOutcome == Ok
    找不到（或从没成功过）→ 返回上限 + 1（报"从没成功过"）
```

阈值按频率配，都留了实测余量：

| 频率 | 上限 | 现状最坏 | 余量 |
|---|---|---|---|
| 每工作日 | **3 期** | 0 期（28 项全是昨晚跑的） | 很大 |
| 每周 | 2 期 | — | — |
| 每月 | 2 期 | 0 期（季度组本期都跑过了） | 很大 |

日更取 3 而不是 2：一项周五失败、周末不跑、周一补跑成功是正常节奏，2 期会在周一早上误报。

### 3.3 三种"没成功"要分开措辞

`LastOutcome` 已经分得很细，报的时候不能都写成"失败"——处理方式完全不同：

| 结局 | 说法 | 该做什么 |
|---|---|---|
| `Failed` | 连着 N 轮失败 | 看日志里的错误，多半是数据源变了 |
| `Skipped` | 连着 N 轮没开工 | 熔断没恢复、或硬前置一直失败——**去看前置** |
| `Cancelled` | 最近 N 轮都被手动停止 | 要么它真的太慢该调整，要么就该取消勾选 |
| 没有记录 | 从没成功过 | 新加的项还没跑过？还是每次都没轮到 |

### 3.4 不判的

- **没启用的项**：用户刻意关掉的，报了就是噪声。
- **手动 / 仅一次**：它们没有"期"可言（`DueAnchorAt` 给 `MinValue`），谈不上"连着几期没跑"。
- **今天刚加进计划的项**：没有 `LastStart` 但也还没轮到过——判据里"从没成功过"要跟
  "这一期还没轮到"区分开，后者不报。

## 4. 报在哪

### 4.1 一轮收尾时

`PlanRunner.LogRoundSummary()` 是天然的时机——它本来就在总结这一轮。在现有那句
"成功 N 项、失败 N 项"后面加一段：

```
===== 今天的计划跑完了：成功 27 项、失败 1 项。明细见 …plan-2026-09-18.txt =====
⚠ 抓取健康：2 项连着几轮不正常——
   【龙虎榜席位】连着 4 轮失败（最后一次成功 09-14），最近一条错误：…
   【拉取分红送配】连着 3 轮被手动停止（上次跑了 4 小时 56 分）
```

同一段也写进当日报告文件末尾（那份是给第二天早上复盘看的）。

### 4.2 界面

计划页那一列现在显示"上次 09-18 02:25 ✔ 成功"。健康信息**不另开一列**，
挂在同一行的 tooltip 里多一句"连着 N 轮没成功"就够——真正需要被看见的是日志那一段。

### 4.3 不做的

- **不新增任务项**。这不是"跑一次查一下"的活，它的输入就是刚跑完的那一轮，做成任务反而要人记得点。
- **不自动补、不记待办**。这四类的处理方式完全不同（改配置、改数据源、取消勾选、看前置），
  塞进【重新拉取失败】补不对——跟体检第③④段一个道理。
- **不弹窗**。无人值守跑到半夜，弹窗没人看，还会挡住后面的执行。

## 6. 第二步（要动存储才能做的，这一版先不做）

判据 3.2 只用得上"最后一次成功是什么时候"，答不了这两个问题：

- **时好时坏**：一项最近 5 轮成功 2 次——按 3.2 它是健康的（最后一次成功在 1 期内），
  但 60% 的失败率显然不正常。
- **长期带错完成**：`LastErrorCount > 0` 连着好几轮（实测现在就有两项："完成，但有 2 条错误"）。

这两个都需要**滚动历史**。形状照 `RecentDurationsSec` 抄：`FetchPlanItem.RecentRuns`
存最近 10 轮的 `(时刻, 结局, 错误数)`，在 `Finish()` 里追加。代价：

- `fetch-plan.json` 变大约 46 项 × 10 条 ≈ 十几 KB，可接受；
- ⚠ `FetchPlan.CarryOverRunRecords`（重建计划时搬运行记录）**必须跟着搬这个新字段**，
  否则"重建一次计划、健康历史清零"，而那正是最该看历史的时候。

## 7. 验收标准

单测（判据层，跨期场景全靠它）：

1. 日更项最后一次成功在 1 期前 → 健康；
2. 日更项最后一次成功在 4 期前 → 报，期数算对；
3. **月度项 16 天没跑但本期已成功 → 健康**（3.1 那条实测，一刀切按天数会在这里误报）；
4. 月度项上上期才成功过 → 报；
5. 未启用 / 手动项 → 不判；
6. 从没跑过但这一期还没轮到 → 不报；
7. `Skipped` / `Cancelled` 各自的措辞对得上。

实机（Debug 实例）：

8. 伪造几项的 `LastStart`/`LastOutcome`，跑一轮计划，日志末尾出现健康告警且点名正确；
9. 全部健康时**一个字都不报**（这一段不能变成每天都有的噪声）。

## 8. 实现结果（2026-09-18）

### 8.1 设计里漏掉的一件事：判据需要一个新字段

§3.2 写"用现有数据就能算"，实现时第一条测试就把它推翻了：

`FetchPlanItem` 只记**最近一次**运行。最近一次是失败时，"上一次成功在什么时候"**彻底查不到**——
而"连着几期没成功"恰恰是这套告警的全部价值。没有它，判据只能退化成"要么本期成功、要么久到不知道"，
数不出"连着 3 期"。

所以加了一个字段 `FetchPlanItem.LastOkAt`（最后一次成功的开跑时刻），在 `PlanRunner.Finish()` 里
**只在成功那一刻推进**。一个 `DateTime`，比 §6 说的滚动历史轻得多，而判据立刻完整。

两处配套，漏一处就白加：

- `FetchPlan.CarryOverRunRecords` 要搬它——否则"重建一次计划、健康历史清零"，
  而那正是最该看历史的时候；
- **升级的空窗**：老计划文件没有这一列，读出来是 null。判据对"null 且最近一次不是成功"的项
  **不下结论**，等它下次成功把基准记上。宁可空窗一轮，也不能升级当天把一堆项报成"从没成功过"。
  （最近一次就是成功的那些不受影响：直接拿 `LastStart` 当基准，等价且准确。）

### 8.2 落地的文件

| 文件 | 改动 |
|---|---|
| `src/StockPlatform.Scheduling/FetchPlan.cs` | `FetchPlanGroup.PeriodStartAt`（往回数 N 期的期起点）、`FetchPlanItem.LastOkAt`、`FetchPlanItem.PeriodsSinceLastOk`、`CarryOverRunRecords` 带上新字段 |
| `src/StockPlatform.Scheduling/PlanRunner.cs` | `Finish` 推进 `LastOkAt`；`LogRoundSummary` 后接 `LogHealth`；`AppendReportLines` 把告警写进当日报告 |
| `.../StockPlatform.Tests/FetchHealthTests.cs` | **新增** 17 个用例 |

`PeriodStartAt` 跟 `DueAnchorAt` 的两点区别写在代码注释里，这里只记要点：**不带 `StartedSince` 那道闸门**
（那是给排期用的，健康判据要数的恰恰是"中间那些没开工的期"），**不算收盘那个补充到点**
（否则"连着 3 期"到底是一天半还是三天要靠猜）。

### 8.3 验证

- 单测 17 条，含两条编排级的（用假的 `execute` 委托驱动真的 `PlanRunner` 跑一轮）：
  一轮收尾报出病人、**全都健康时一个字都不报**。全量 **1,738 个全过**。

- ⚠ **实机验证这次没做，而且是因为我做错了一次**：为了造"连着几期失败"的场景，
  我把【拉取龙虎榜席位】等项设成启用——**启用的项会被调度真的执行**，于是 Debug 实例
  真发了一轮请求（9 天、约 18 页，写了 4240 行）。已停掉、删掉那些行、还原计划文件。

  教训写进测试注释了：**这一段不能拿真程序造场景**。健康判据不需要项被执行，
  而启用是它被执行的充分条件。用假 `execute` 驱动 `PlanRunner` 才是对的路子——
  既覆盖编排，又一个请求都不发。

  真实触发会在今晚日更的收尾自然发生（那时全部项应该都是健康的，即"一个字都不报"）。

### 8.4 这一版之后还剩什么

§6 那两条仍然要滚动历史才能做（时好时坏、长期带错完成），没动。
现在的判据答的是"上次成功是几期之前"，答不了"最近 5 轮里成功了几轮"。
